# Решение: несколько детей (и взрослых) под одним клиентским аккаунтом

**Дата:** 2026-09-04
**Статус:** предложение, готово к решению
**Контекст:** родители хотят управлять несколькими детьми из одного Telegram-аккаунта; отдельно — у тренеров есть смежные тарифы («ребёнок + родитель со скидкой»). Нужно решить домен, миграцию и стоит ли это делать вообще.

---

## 0. Короткий ответ

**Делать, но не то, что описано в примере.** Задача — не «почему при вводе второго ребёнка имя перезаписывается» (это не совсем так — см. §1), а **«в системе физически нет понятия „кого я записываю", есть только „кто я"»**. Это разные вещи: `clients.telegram_id` — это логин, а не человек, которому оказывается услуга. Как только это разделить, проблема решается расширением одной таблицы и не трогает 90% системы: бронирования, абонементы, сертификаты, заметки, теги, историю — они уже все ключуются по `client_id`, не по `telegram_id`.

Второй вопрос — «смежные тарифы» (ребёнок+родитель в одной записи) — **другая по природе задача** (мультиучастник одной брони), она НЕ решается тем же механизмом и не должна решаться сейчас в полном виде. Рекомендация — узкая версия (см. §6), не полноценная модель участников.

---

## 1. Уточнение факта: что происходит на самом деле

Проверено по коду (`webapp.py:437` `_ensure_client_for_webapp_miniapp` → `get_or_create_client` в `client_use_cases.py:306`).

Описанный сценарий не совсем то, что в коде:

```python
if has_saved_name:
    return await get_or_create_client(session, catalog_tid, vk_user_id=vk_uid, phone=phone)
    # first_name / last_name даже не передаются дальше
```

Если у аккаунта уже есть сохранённое имя (после первой записи первого ребёнка), то **имя второго ребёнка, введённое в форму записи, никуда не сохраняется вообще** — оно просто отбрасывается. Профиль не «перезаписывается» — он остаётся именем первого ребёнка, а бронь второго ребёнка молча уходит в тот же `client_id`.

Итог тот же, что вы описали, но чуть хуже: **не перезапись, а потеря данных.** История занятий действительно общая, потому что в модели `1 Telegram-аккаунт = 1 clients-строка = 1 человек, которому оказывают услугу`. Это и есть корень, и его надо чинить именно на этом уровне, а не патчем формы.

## 2. Где на самом деле проходит граница системы (проверено по БД)

Ключевая находка, которая радикально снижает стоимость решения:

| Что | Ключ сегодня | Нужно менять? |
|---|---|---|
| `bookings` | `client_id` | **Нет** |
| `pass_instances` (абонементы) | `client_id` | **Нет** |
| `certificate_instances` | `client_id` / `activated_client_id` | **Нет** |
| `trainer_client_notes`, `trainer_client_tags`, `trainer_client_entries`, `trainer_client_roster` | `client_id` | **Нет** |
| `client_requests` | `client_id` | **Нет** |
| `client_trainer_edges` (мой тренер, сохранённые, счётчики) | **`telegram_id`** | **Да** |
| `trainer_ratings` | **`client_telegram_id`** | Желательно, не блокер |
| `client_sessions` (шаги бота, выбранный город/тренер) | `telegram_id` | Нет — это состояние устройства/сессии, а не человека |

Вывод: **вся коммерческая история (деньги, брони, абонементы, заметки тренера) уже устроена правильно** — по «профилю», а не по «логину». Не так устроено только то, что отвечает за «кто мой тренер» и «что я сохранил» — это исторически привязано к Telegram-аккаунту, потому что раньше аккаунт и профиль были одним и тем же.

Это значит: **90% системы не мигрирует вообще.** Мигрирует одна таблица (`client_trainer_edges`) плюс добавляется одна новая.

## 3. Домен: что на самом деле две разные вещи

```
Account (логин)              Profile (получатель услуги)
─────────────────           ──────────────────────────
Telegram/VK identity          clients-строка
"кто держит телефон"          "кому оказывается услуга"
1 на человека с телефоном     может быть без телефона вообще
                               (сегодня это уже поддержано:
                               clients.telegram_id nullable,
                               "trainer-added offline client")
```

Сегодня в коде эти две вещи считаются одним и тем же — отсюда и баг. Дальше всё строится на этом разделении.

### Важно: половина инфраструктуры для этого уже случайно существует

`ClientFamilyAccessMember` уже умеет ровно то, что нужно, только **в обратном направлении**: сегодня это «несколько Telegram-аккаунтов → один профиль» (второй родитель видит того же ребёнка). Нужное — «один Telegram-аккаунт → несколько профилей» (один родитель ведёт двух детей). Это зеркальные грани одной и той же связи many-to-many, и решать их двумя разными таблицами — плодить сложность на пустом месте. Правильно — **обобщить в одну таблицу**, которая закрывает сразу оба случая, включая ваш «самый серьёзный сценарий» (2 родителя × 2 ребёнка) бесплатно, потому что это просто ещё несколько строк в той же таблице.

## 4. Предлагаемая модель

### Новая таблица

```sql
CREATE TABLE client_profile_links (
    id               SERIAL PRIMARY KEY,
    account_telegram_id  BIGINT NOT NULL,          -- логин: тот же ключ, что client_catalog_telegram_key()
    profile_client_id    INTEGER NOT NULL REFERENCES clients(id) ON DELETE CASCADE,
    role                  VARCHAR(16) NOT NULL DEFAULT 'guardian',  -- 'self' | 'guardian'
    is_default            BOOLEAN NOT NULL DEFAULT false,           -- какой профиль открывается первым
    created_at            TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (account_telegram_id, profile_client_id)
);
CREATE INDEX ix_client_profile_links_account ON client_profile_links (account_telegram_id);
```

Смысл строки: «этот Telegram-аккаунт может действовать от имени этого профиля».

* **`role = 'self'`** — профиль совпадает с самим аккаунтом (сегодняшний случай: `clients.telegram_id = account_telegram_id`). Бэкофилл создаёт эту строку для каждого существующего клиента автоматически — **ни один существующий пользователь не замечает изменения**.
* **`role = 'guardian'`** — аккаунт управляет чужим (обычно безтелеграмным) профилем: своим ребёнком.
* **`is_default`** — что открывается при заходе в приложение без явного выбора (обратная совместимость: у существующих аккаунтов это всегда их `self`-профиль).

### Что происходит с существующим `client_family_access_members`

**Не трогаем и не удаляем.** Это узкий, рабочий, отдельный кейс — «второй телеграм видит те же брони и абонементы того же ребёнка (общий client_id)», и это **не то же самое**, что «управлять несколькими разными профилями» (у которых разные `client_id`, разная история). Смешивать эти две модели в одну — усложнение без пользы. Они решают ортогональные задачи и обе остаются:

| Задача | Механизм |
|---|---|
| Второй родитель видит **ту же** запись/абонемент того же ребёнка | `client_family_access_members` (как сейчас) |
| Один аккаунт ведёт **нескольких разных** детей с раздельной историей | `client_profile_links` (новое) |
| 2 родителя × 2 ребёнка, каждый со своей историей | Оба родителя получают `client_profile_links` на оба детских `client_id` — просто 4 строки в новой таблице, `client_family_access_members` тут не участвует вообще |

Ваш «самый серьёзный сценарий» **не требует новой модели сверх этого**: это просто N строк в `client_profile_links`, где N = аккаунтов × профилей, к которым у них есть доступ. Взрослый, который сам тренируется — это тоже профиль (его собственная `clients`-строка с `role='self'`), поэтому «родитель тоже ходит к тренеру» ничего не усложняет — это просто ещё одна строка `role='self'`, которая и так появляется автоматически.

### Создание профиля ребёнка

Когда родитель в записи нажимает «Записать другого» / «Добавить ребёнка»:

1. Создаётся новая `clients`-строка: `telegram_id = NULL`, `phone_normalized = телефон родителя` (важно для тренера — контакт остаётся реальным), `first_name/last_name` = введённые в форму (то, что сегодня отбрасывается).
2. `INSERT INTO client_profile_links (account_telegram_id, profile_client_id, role) VALUES (parent_tid, new_id, 'guardian')`.
3. Бронь создаётся сразу с `client_id = new_id`, а не с `client_id` родителя.

Второй родитель добавляется к тому же ребёнку так же, как сегодня работает семейный доступ, но через `client_profile_links` (см. §5) — без второй сущности.

## 5. Разрешение «действующего профиля» — единственное новое понятие в API

Сегодня почти 40 мест в `webapp.py` делают `telegram_id = client_catalog_telegram_key(principal)` → `get_client_id_by_telegram_id(session, telegram_id)`. Это единая точка, через которую проходит вся идентификация клиента.

**Меняется одна функция, а не 40 endpoint'ов.**

```python
async def resolve_acting_client_id(
    session: AsyncSession,
    account_telegram_id: int,
    requested_profile_id: int | None,   # из заголовка X-Profile-Id или query ?profile_id=
) -> int:
    """
    Явно запрошенный профиль — только если аккаунт имеет к нему доступ (client_profile_links).
    Иначе — is_default профиль аккаунта. Иначе — старое поведение (self по telegram_id),
    что покрывает 100% сегодняшних пользователей без единой лишней строки в БД.
    """
```

Технически: там, где сегодня написано `get_client_id_by_telegram_id(session, telegram_id)`, становится `resolve_acting_client_id(session, telegram_id, requested_profile_id)`. Это механическая правка в ~40 местах, но она **одного типа** — не 40 разных решений, а одна замена, повторённая 40 раз. Существующие клиенты (99% пользователей на первом этапе — все, у кого один ребёнок или взрослый сам себе клиент) не почувствуют разницы: `requested_profile_id = None` → тот же `client_id`, что и сегодня.

### Что добавляется в клиентское приложение

* **Переключатель профиля** — не новый экран, а шапка/чип на клиентской главной: имя текущего профиля + список остальных + «Добавить ребёнка». Технически — Telegram `MainButton`/простой bottom sheet, ничего тяжелее того, что уже есть в `mini-app-client-shell.js`.
* Выбранный профиль хранится на клиенте (`localStorage`/`sessionStorage` в WebView) и передаётся заголовком на каждый запрос — сервер ничего не хранит про «текущий экран», только про то, **кому какие профили доступны** (`client_profile_links`).

## 6. `client_trainer_edges`: единственная таблица, которую надо по-настоящему мигрировать

Сегодня «мой тренер», «сохранённые тренеры», «счётчик занятий с тренером» лежат в `client_trainer_edges`, ключ — `telegram_id`. Если оставить как есть, то у второго ребёнка на хабе будет «мой тренер» первого — данные не смешаются в деньгах, но хаб будет врать. Это надо чинить, иначе фича не имеет смысла.

**Безопасная миграция в три шага, без окна простоя:**

1. **Добавить колонку** `client_trainer_edges.client_id INTEGER NULL REFERENCES clients(id) ON DELETE CASCADE`. Ничего не ломается — колонка nullable, старый код продолжает работать по `telegram_id`.
2. **Бэкофилл одним UPDATE**: `client_id = (SELECT id FROM clients WHERE clients.telegram_id = client_trainer_edges.telegram_id)`. Сегодня это отображение 1:1 и детерминировано — так как сегодня действительно 1 telegram = 1 client.
3. **Переключить чтение/запись на `client_id`** в `client_trainer_edge_use_cases.py`, `client_trainer_primary_graph.py`, `client_trainer_edge_repository.py` (три файла, не сорок). `telegram_id` в таблице не удаляем сразу — оставляем как исторический след ещё один релиз, дропаем отдельной миграцией после того, как убедились, что нигде не осталось чтения по нему.

`trainer_ratings.client_telegram_id` — аналогичный, но некритичный случай (оценка тренера). Можно оставить как есть в первой итерации: не блокер, ребёнок редко сам ставит оценку тренеру, а взрослый — это `role='self'`, для которого ничего не меняется.

## 7. Второй вопрос отдельно: «смежные тарифы» (ребёнок + родитель в одной записи)

Это **не та же задача**, и её нельзя решить тем же механизмом. Профили выше — это «два разных занятия, два разных слота, два разных человека». А «ребёнок + родитель со скидкой» — это **один слот, одно занятие, два тела**, и сегодня это уже существует как *ценовая метка* на брони (`bookings.price_tier_kind = 'adult_and_child'`), но **второй человек в системе невидим**: нет его брони, нет напоминания ему, нет истории занятий у него.

### Почему не строить это сейчас в полном виде

Полная модель («у одной брони несколько участников») требует таблицы `booking_participants` и переписывания довольно тяжёлой части системы: `bookings` — это машина состояний с 13 статусными полями (no-show, подтверждение, отмена, списание абонемента/сертификата, групповая ёмкость). Раздельное посещение/списание/неявка **на человека** внутри одной брони — совершенно другой контур, и вы сами явно спросили «стоит ли вообще это делать». Ответ: **не сейчас, отдача не оправдывает риск в этой системе состояний.**

### Что стоит сделать — маленькая, безопасная версия

Добавить один nullable столбец:

```sql
ALTER TABLE bookings ADD COLUMN companion_client_id INTEGER NULL
    REFERENCES clients(id) ON DELETE SET NULL;
```

Смысл: «кто был вторым участником» — **только атрибуция**, никакой отдельной логики статусов, списаний, напоминаний для второго человека. При записи по парному тарифу клиент опционально выбирает второго участника из своих же профилей (`client_profile_links` — родитель может отметить, что «сегодня со мной был Ваня»). Это даёт:

* правильную статистику по клиенту («сколько раз Ваня был на льду», включая парные занятия — важно для вех из плана роста);
* тренеру видно, кто фактически был на занятии, без переделки CRM;
* нулевой риск для существующей логики бронирования (поле не участвует ни в одном текущем расчёте).

Полноценных мультиучастников (раздельные подтверждения/неявки/абонементы на второго человека) — **не строить**, пока нет прямого запроса от тренеров, что это критично. Сегодня для этого нет даже намёка на спрос — это гипотеза внутри гипотезы.

## 8. Итоговый план

| # | Что | Риск | Блокирует остальное |
|---|---|---|---|
| **М1** | Миграция: `client_profile_links` (новая таблица) + бэкофилл `role='self'` для всех существующих `clients.telegram_id` | Нулевой — чисто аддитивно | Да, всё остальное на ней стоит |
| **М2** | `resolve_acting_client_id()` + замена ~40 вызовов `get_client_id_by_telegram_id` в `webapp.py` на неё | Низкий, механическая замена, обратная совместимость по умолчанию | Да |
| **М3** | Экран «Добавить ребёнка» + переключатель профиля в клиентском приложении | Средний (UI), но изолирован от бэкенда | Нет, можно параллельно с М4 |
| **М4** | Миграция `client_trainer_edges`: колонка `client_id`, бэкофилл, переключение 3 файлов на неё | Средний, но локализован | Нужен, чтобы «мой тренер» не врал по профилям |
| **М5** (опционально, отдельно) | `bookings.companion_client_id` — атрибуция парных тарифов | Низкий, чисто аддитивно, не трогает статусную машину | Независим от М1–М4, можно позже |

**Порядок:** М1 → М2 → М3 и М4 параллельно. М5 — отдельно, в любое время, не связан с остальным.

**Чего не делать:** не трогать `client_family_access_members` (работает, отдельная задача), не строить мультиучастников брони, не делать общий «граф домохозяйства» с ролями «муж/жена/ребёнок» — это красиво, но избыточно: `client_profile_links` с двумя ролями (`self`/`guardian`) покрывает весь описанный вами сценарий, включая двух родителей и нескольких детей, без единой дополнительной сущности.

## 9. Проверка на «самом серьёзном сценарии»

2 родителя (аккаунты A, B), 2 ребёнка (профили C1, C2), у каждого ребёнка свой тренер, у каждого родителя свой тренер:

```
clients:              A(self), B(self), C1, C2
client_profile_links: (A, A, self, default)
                       (B, B, self, default)
                       (A, C1, guardian)
                       (A, C2, guardian)
                       (B, C1, guardian)
                       (B, C2, guardian)
```

Родитель A открывает приложение → по умолчанию видит свой профиль (self) → переключается на C1 → видит **только** брони, абонементы, историю и «моего тренера» C1, потому что `client_trainer_edges` (после М4) и все брони/абонементы/заметки (уже сегодня) ключуются по `client_id = C1`, а не по `telegram_id = A`. Родитель B независимо видит те же C1/C2 через свои собственные `client_profile_links`-строки. Ничего не пересекается и не требует новых таблиц сверх одной.
