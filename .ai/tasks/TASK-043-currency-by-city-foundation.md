# Task

## Objective

Валюта в системе должна определяться городом, а не быть жёстко зашитым BYN. Для городов
Беларуси — белорусский рубль (с возможной сменой знака отображения), для Москвы/МО и
Санкт-Петербурга/ЛО — российский рубль. Это техническая база: сама сетка тарифов подписки
для российских городов — отдельная задача [[TASK-044]], гибкая сетка для небольших
белорусских городов — отдельная задача [[TASK-045]].

## Business Context

Расширение сервиса на Россию (пока Санкт-Петербург/ЛО и Москва/МО), сентябрь 2026 —
см. память `moscow-expansion-2026-09`. Все города пока в UTC+3, так что часовые пояса
не требуют изменений — только валюта. Источник задачи — прямой запрос владельца продукта:
"валюта в зависимости от города".

## Scope

### In Scope

- Поле "страна" у города (`cities.country`, например `BY`/`RU`) — валюта определяется
  через страну города, а не жёстким списком названий городов (решение владельца продукта).
- Backfill `country` для существующих строк `cities`: `RU` для уже заведённых в проде
  "Москва/МО" (id 30) и "Санкт-Петербург/ЛО" (id 31), `BY` для всех остальных — сидировать
  новые города не нужно, они уже есть (см. Facts).
- Функция резолва валюты по городу (`BY → BYN`, `RU → RUB`), единая точка входа.
- Замена жёстко зашитого `"BYN"` на резолв валюты в: форматировании сумм
  (`src/shared/byr_currency_display.py`), вызовах платёжного шлюза bePaid
  (`src/api/routes/webapp.py:3938,4132,9029`), дефолте `currency` в
  `SubscriptionTierPricing`/`SubscriptionModulePeriodPricing`.
- Смена отображения белорусского рубля на официальный знак НБРБ через шрифт-иконку
  (нужен файл шрифта — см. Q-004).

### Out of Scope

- Конкретные суммы подписки в рублях для Москвы/МО и обычных RU-городов — [[TASK-044]].
- Гибкая сетка цен для небольших белорусских городов (Бобруйск, Лида и т.д.) — [[TASK-045]].
- Множественный выбор города одним тренером (открытая, не связанная задача
  `TASK-014-onboarding-multi-city.md`) — сейчас у тренера один `city_id`, резолв валюты
  делается по нему.
- Проверка, поддерживает ли bePaid реальный приём RUB, — сознательно не исследуется в
  этой задаче по решению владельца продукта (2026-09-04), см. EDGE-001/Q-001.

### Implications

- Переименование API-полей `price_byn` → нейтральное имя — отдельное решение
  (см. DEC-001), т.к. эти имена используются в статических JS-файлах webapp
  (`static/webapp/*.js`) и переименование — breaking change для фронтенда. По умолчанию
  предлагается **не переименовывать** поля, а только сделать отображение
  валютно-зависимым (символ/код валюты резолвится отдельно от названия поля).
- Цены услуг/абонементов, которые тренер сам назначает клиентам (`trainer_services`,
  `TrainerPassProduct`), не требуют отдельной "сетки цен" — тренер вводит сумму сам,
  система лишь должна показывать правильный символ/код валюты по городу тренера/арены.
- `TrainerProfile.city_id` — один город на тренера, поэтому резолв валюты по трейнеру
  однозначен уже сейчас, без ожидания multi-city задачи.

## Decisions

### DEC-001
Не переименовывать API-поля `price_byn`/`price_child_byn`/`group_price_byn` в рамках этой
задачи — валютность делается через отдельный резолв символа/кода, а не через имя поля.
Reason: переименование — breaking change для статических JS вебаппа, не несёт ценности
для цели задачи (показать правильную валюту).

### DEC-002
`SubscriptionTierPricing`/`SubscriptionTierPeriodPricing`/`SubscriptionModulePeriodPricing`
получили новую колонку `price_group` (default `'BY_BASE'`, unique-констрейнты расширены на
неё), а не остались с прежним "одна строка на tier". `cities` получила отдельное поле
`price_group` (независимое от `country`) — сразу для обоих будущих потребителей:
[[TASK-044]] (RU_BASE/RU_MOSCOW) и [[TASK-045]] (BY_BASE/BY_SMALL).
Reason: обнаружено по ходу реализации — `subscription_tier_pricing.tier` имел UNIQUE-
констрейнт (ровно одна цена на tier глобально), без снятия этого ограничения TASK-044/045
были бы физически невозможны. Это не входило в исходный Technical Plan задачи (который
предполагал только "дефолт currency больше не фиксирован"), но является тем же самым
"техническая база" по духу — решено сделать здесь, а не как отдельную доп. задачу перед
TASK-044.

### DEC-003
Обнаруженный по ходу правки `trainer-card-shared.js` баг (`formatPriceByn: formatPriceByn`
— ссылка на несуществующую переменную, из-за которой весь `window.TrainerCardShared`
падал бы при загрузке) исправлен тут же, а не отдельной задачей.
Reason: файл, который я и так редактировал ради AC-005, был бы непроверяем без этого
фикса; сам файл сейчас нигде не подключён (`grep` не нашёл ни одного `<script src="trainer-
card-shared.js">` — мёртвый код), так что баг не имел прод-эффекта, но чинить его отдельной
задачей ради одной строки избыточно.

### DEC-004
После первой автономной реализации владелец продукта проверил вручную и увидел `BYN`
везде, включая после смены города на Москву. Причина — двойная: (1) `theme.css`,
`catalog-main.js`, `trainer-profile-main.js` подключены с версионным `?v=...` и отдаются
с `Cache-Control: immutable, max-age=1 год` (`src/api/app.py`) — правка файла без правки
версии в URL означает, что браузер (и любой прокси) продолжает показывать старое
содержимое бесконечно; (2) сам экран подписки и суффиксы цены в профиле изначально не
читали поле `currency`/`country` из ответа API вообще — валюта на бэкенде уже была верной,
но нигде не отображалась. Оба исправлены в этой же сессии (см. EDGE-003), версии
`?v=` подняты для всех трёх файлов во всех HTML, которые их подключают.
Reason: без поднятия версии in URL любой последующий фикс frontend-кода был бы невидим
для уже открывавших приложение браузеров — это не гипотетический риск, а то, что
владелец продукта реально увидел при проверке.
