# Task

## Objective

Сделать местом занятия арену конкретного слота/брони, а «основную площадку» тренера — только значением по умолчанию при заполнении. Клиент, который записывается с карточки арены X, должен либо попасть на X, либо явно увидеть, что место будет другим.

## Business Context

Это главный блокер карточки арены. Экран, где клиент выбрал каток у дома и нажал «Записаться», а занятие оформилось на другой конец города, теряет доверие в первый же день — и обесценивает весь эпик. При двух аренах в Минске это терпимо, при ~90 в Москве — массовый сценарий (`RESEARCH-ARENAS-SCALE-2026-09-02.md` §2.5, T-12/T-13).

## Scope

### In Scope
- `resolve_arena_for_client_self_booking` (`src/application/booking_use_cases.py:1042`): сегодня документировано и реализовано как «online slot **always** resolves to the trainer's primary venue», а фильтр по не-основной арене возвращает флаг `used_primary_despite_non_primary_filter`. Заменить на: место = арена слота; если у слота арены нет — арена по умолчанию из расписания тренера; если клиент фильтровал по арене X, слот на X и оформляется на X.
- `SQL_BOOKING_ARENA_DISPLAY` (`booking_use_cases.py:174`): убрать fallback «склеить все арены тренера через запятую» (`string_agg`) — при отсутствии арены у брони и у слота показывать «место уточняет тренер», а не перечисление всех катков. Затрагивает 6 мест использования этого SQL.
- Явное состояние в UI записи: если место всё же отличается от выбранной клиентом арены — сказать это прямым текстом до подтверждения, а не постфактум.
- Проверить и починить путь «клиент выбрал арену X → в карточке тренера ноль слотов» так, чтобы он не был тупиком: либо слоты есть, либо честное объяснение почему нет.

### Out of Scope
- Разделение витрины и допуска (`is_public`) — TASK-057.
- Мультигород тренера — TASK-058.
- Ручная запись тренером и постановка слотов на арену, к которой тренер не привязан — следствие TASK-057, не этой задачи.

### Уточнение по устаревшей находке
`RESEARCH-ARENAS-SCALE-2026-09-02.md` §2.5 утверждает, что клиентский листинг слотов «выкидывает слоты с `arena_id IS NULL`». На 2026-09-04 это уже не так: `GET /client/slots` (`src/api/routes/webapp.py:1456`) документирует и реализует «NULL slot venues resolve to the trainer schedule default arena for filtering and JSON». Проверить фактическое поведение перед правкой и не чинить то, что уже починено.

## Acceptance Criteria

### AC-001
Клиент, отфильтровавший каталог/открывший карточку арены X и записавшийся на слот, получает бронь именно на арене X.
Requirement: CONFIRMED
Verification method: automated/integration (слот на X → бронь с `arena_id = X`) + manual/exploratory

### AC-002
Если место занятия отличается от арены, из которой клиент пришёл, он видит это до подтверждения записи, а не после.
Requirement: CONFIRMED
Verification method: manual/exploratory + automated/unit (ответ API содержит признак расхождения, UI его показывает)

### AC-003
Место занятия в брони никогда не отображается как перечисление нескольких арен. При отсутствии арены у брони и у слота показывается «место уточняет тренер».
Requirement: CONFIRMED
Verification method: automated/integration (бронь без арены → строка-заглушка, а не список) + static analysis (в `SQL_BOOKING_ARENA_DISPLAY` нет `string_agg` по `trainer_arenas`)

### AC-004
Существующие сценарии записи (запись у своего тренера из hub, перенос записи, групповые слоты, ручная запись тренером) не меняют поведение — регрессий нет.
Requirement: CONFIRMED
Verification method: automated/integration (существующий набор тестов записи проходит без правок ожиданий)

### AC-005
Тренер с одной ареной и клиент без фильтра по арене видят ровно то же поведение, что и раньше — задача не создаёт нового трения для основного массового случая.
Requirement: INFERRED (следует из принципа «не ломать работающее»; отдельно владельцем продукта не формулировалось)
Verification method: automated/integration

## Edge Cases

### EDGE-001
Слот без арены у тренера с несколькими аренами: арена по умолчанию из расписания может не совпасть с ожиданием клиента, пришедшего с карточки конкретной арены.
Severity: HIGH
Status: OPEN

### EDGE-002
Тренер меняет основную площадку после того, как клиент записался — уже созданные брони не должны «переезжать».
Severity: MEDIUM
Status: OPEN

### EDGE-003
Формат «выездной тренер» (`arena_work_format=mobile`) — арены нет вообще; место должно быть честной заглушкой на всех экранах, включая уведомления.
Severity: MEDIUM
Status: OPEN

## Technical Notes
- `SQL_BOOKING_ARENA_DISPLAY` используется в 6 местах (`booking_use_cases.py:1888, 2251, 2635, 4287, 5430, 5605`) — менять один раз, проверять все шесть.
- Уведомления о записи содержат место занятия — правка отражается и в текстах пушей.

## Tests
- integration: запись со слота на арене X → `arena_id = X` (AC-001)
- integration: расхождение места → признак в ответе (AC-002)
- integration: бронь без арены → «место уточняет тренер» во всех шести местах (AC-003)
- regression: полный набор существующих тестов записи/переноса/групп (AC-004)

## Risks
