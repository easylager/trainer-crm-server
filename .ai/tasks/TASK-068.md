## Comprehension Tips

### Facts

- Профиль — одна длинная анкета: 7 `<details>` почти все `open`, плюс вкладки Статус/Настройки. Файлы: `trainer-profile.html` 521, `trainer-profile-main.js` 6111, `mini-app-trainer-profile.css` 3184.
- TTV-визард (4 шага: имя/город → телефон → услуги → арены) **переносит те же DOM-узлы**, не дублирует разметку. Каталожные поля (фото, «О себе», образование) в визарде нет, но в полном экране они стоят **перед** услугами и аренами и открыты.
- Один глобальный Save (`PATCH /trainer/profile`) собирает весь снимок, включая `arena_ids` с чекбоксов. Образование — отдельный side-save после.
- Три планки полноты: TTV 5 / submit 8 / full 11. UI ставит required-dot на description/education/experience/session/min-hours, хотя TTV и submit их не требуют.
- Арены в профиле: `GET /trainer/profile/arenas?city_id=` → плоский список чекбоксов **только имя**, без поиска, адреса, карты. При ≥2 выбранных — второй список радиокнопок «основная площадка».
- Создание арены (TASK-046) уже в коде: кнопка «Моей площадки нет в списке» → название+адрес → `POST arena-setup mode=create`. Плюс textarea в поддержку. После успеха `renderArenas()` **без** `loadArenasForCity` — новая строка может не появиться, а следующий Save перезапишет `arena_ids` с чекбоксов и снимет автопривязку.
- Онбординг (`trainer-onboarding.html`) — другой пикер: поиск по имени/городу, арены **всей платформы**, без создания (редирект «добавьте в профиле»).
- Каталог клиентов уже умеет поиск по имени+адресу и карту без кластеризации (`catalog-main.js`). TASK-054 (карта+кластеры+единый компонент) — `phase: plan`, зависит от TASK-051, кода нет.
- В RESEARCH-ARENAS-SCALE уже записаны T-6/T-7/T-8: один компонент поиск/карта/чипы; в профиле убить второй список радио; онбординг — сначала город.

### Patterns

- Выбор арены сейчас живёт в трёх несовместимых UI (профиль / онбординг / каталог) с тремя правилами видимости (`is_confirmed`).
- «Основная площадка» моделируется отдельным контролом, а не свойством выбранной арены.
- Создание арены и выбор арены — соседние блоки на одном экране, а не одно состояние поиска (нашёл / не нашёл).

### Zero-to-setup: проверенный путь нового тренера (2026-09-05)

Онбординг (`trainer-onboarding-main.js`) — один экран, не визард: услуги → длительность → арена (по умолчанию «Пока не указывать») → сетка недели → «Готово».
Гейт CTA: ≥1 услуга + ≥1 слот; арена опциональна (`syncCta` 954-959, `arenaStepValid` 942-946).

- **Город в онбординге не спрашивается вообще** и не пишется (`trainer_quick_setup_use_cases.py` — `city_id` отсутствует; комментарий 8-9 «города намеренно нет»). Список арен онбординга — **вся платформа**, без города (`webapp.py:8152-8156`).
- **Услуги пишутся без цен** (`_set_services`, `price_cents = NULL`, 357-384) — сознательное решение «цена — отдельный момент».
- Ссылка «Моей арены нет» в онбординге → редирект в профиль (`goAddMissingArena` 1258-1261). Комментарий обещает «в профиле город уже известен» — **это неверно**: город не спрашивался нигде, в профиле блок арен покажет «Выберите город».
- **Дедлока нет.** Дропдаун города синхронит `state.trainer.profile.city_id` сразу (`trainer-profile-main.js:5128`), `hasCity` читает его (5031) → кнопка создания появляется без Save; `arena-setup` принимает `city_id` из тела и сам пишет город в профиль (`trainer_arena_create_use_cases.py:168-179`). Арену можно создать без сохранения профиля.
- **Но Save мёртв не из-за города, а из-за цен.** Услуги из онбординга приходят отмеченными без цен → `domServicesPricesCoherent` (1083-1106) → `isFormValidForSave` false (1276) → глобальная кнопка «Сохранить» заблокирована для **любой** правки, включая город. Ощущается ровно как дедлок.
- **Баг потери арены (в проде).** `afterArenaSetupSuccess` (4703) зовёт `renderArenas()` без `loadArenasForCity` → новой арены нет в `state.arenasList` → `readFormSnapshot` собирает `arena_ids` **только из чекбоксов** (1723-1727) → следующий Save отправляет `arena_ids: []` → `set_trainer_arenas` заменяет набор → привязка стирается.
- Смена города обнуляет `state.trainer.arena_ids` и ставит dirty (5129-5132) — сохранение после смены города стирает связи на сервере.
- **Второй визард профиля недостижим.** `?onboarding=blocks` читается (2815), но **никто его не выставляет** — все переходы идут на голый `trainer-profile` (`trainer-home-main.js:1983, 2852, 2884`; `trainer-onboarding-main.js:1259`). 4-шаговый TTV-рельс (`PROFILE_TT_MINIMAL_WIZARD_ORDER`) — мёртвый код. Новый тренер всегда попадает в полную анкету из 7 секций без всякого ведения.
- Завершённость онбординга = наличие строк `trainer_schedule_templates`, не полнота профиля (`webapp.py:8222`).
- Онбординг перезаписывает `session_duration_minutes` при каждом сохранении (`_apply_profile_settings` 350) — повторный вход в онбординг сбрасывает значение из профиля.

## Decisions

- **DEC-001** — Карта в этой задаче не делается. Пикер профиля = город + поиск (имя/адрес) + чипы + создание. Карта остаётся за TASK-054 / табом «Лёд»; компонент проектируем так, чтобы карта добавлялась позже без переписывания. (Решение пользователя, 2026-09-05.)
- **DEC-002** — Главный источник «кипящей головы» — не длина формы, а два несогласованных визарда и недостижимое ведение: онбординг не спрашивает город, но отправляет за ареной в профиль, где город обязателен; ведение в профиле мёртвое. Лечим спину флоу, а не только блок арен.
- **DEC-003** — Приоритет — отсутствие регрессии. Слайс с багфиксами консистентности данных (reload после создания, `arena_ids` не из чекбоксов, необязательный `arena_ids` в PATCH) идёт **первым и отдельно** от редизайна UI.
- **DEC-004** — Цены в онбординге **не спрашиваем**. Онбординг остаётся без клавиатуры. Цены получают отдельный прозрачный момент после того, как расписание готово. (Решение пользователя, 2026-09-05.)
- **DEC-005** — Пустая цена перестаёт быть ошибкой и становится **состоянием «по запросу»**. Основание: бэкенд и все клиентские поверхности уже это поддерживают — каталог и карточка тренера показывают «по запросу» (`catalog-main.js:5039-5042`, `trainer-card-shared.js:14-15`), запись с `price_cents IS NULL` проходит без ошибки (`booking_use_cases.py:131-143`, `615-621`), строка «Стоимость» скрывается вместо «0 BYN» (`client-bookings.html:545-553`, `schedule-editor-main.js:482-488`), ни один гейт (TTV / submission / каталог / next_step) цену не требует (`trainer_profile_completeness.py`, `trainer_next_step.py:138-140`). Единственный, кто считает это ошибкой, — клиентская валидация профиля.
- **DEC-006** — Поэтому Save **не разрезаем на блоки**. Достаточно сделать валидацию честной: услуга без цены сохраняется как «по запросу», проверяется только формат заполненного числа. Это на порядок меньший радиус изменений, чем поблочное сохранение, и снимает ровно тот симптом «кнопка мертва из-за цен». Поблочное сохранение выкидывается из скоупа.
- **DEC-007** — Момент цен — **экран «Готово» онбординга**, а не карточка хаба. Расписание готово, ссылка на руках: там честная строка «клиент увидит „цена по запросу“» и кнопка «Указать цены», пропустить можно. Хаб не трогаем — в `trainer_next_step.py:138-140` осознанно решено не выносить цены на главный экран; существующие мягкие пуши D+1/D+8/D+21 (`trainer_profile_enrichment_use_cases.py:102-110`) остаются страховкой для тех, кто пропустил.
- **DEC-008** — Ведение больше не отправляет тренера в семисекционную анкету. `OB_FLOW_STEP_DEFS` + рельс (`profileBlockTourBuildWizardRail`) переиспользуются как **общий механизм сфокусированной задачи**: оверлей над одним блоком профиля с возвратом туда, откуда пришёл. Один механизм обслуживает «указать цены» (рельс `['services']`) и «дозаполнить витрину» после первой записи. Полная форма остаётся для просмотра и правок, но ни один ведущий сценарий в неё не бросает.
- **DEC-009** — Город спрашивается селектором **внутри шага «где вы тренируете»** в онбординге, без отдельного шага. Город существует ради арен (и валюты, TASK-043), поэтому живёт рядом с вопросом об аренах. (Решение пользователя.)
- **DEC-010** — Мёртвый 4-шаговый визард **оживляем как «дозаполнить витрину»** после первой записи, не на входе. На входе ведёт онбординг. (Решение пользователя.)

## Target Flow (DEC-001..010)

### Спина: ноль → работающий кабинет

1. **Онбординг, шаг «что тренирую»** — чипы услуг, без цен и без клавиатуры (как сейчас).
2. **Онбординг, шаг «где тренирую»** — селектор города внутри шага → арены **этого** города с поиском → «моей площадки нет» создаётся **здесь же** (эндпоинт `arena-setup mode=create` уже принимает `city_id`, новое API не нужно) → «пока не указывать» остаётся легитимным.
3. **Онбординг, шаг «когда»** — сетка недели (как сейчас).
4. **Онбординг, «Готово»** — ссылка ученику + честная строка «пока клиент видит „цена по запросу“» + кнопка «Указать цены» (сфокусированный оверлей на блоке услуг, возврат сюда же). Пропустить можно без вины.
5. **Дальше** — кабинет работает. Витрина каталога догоняется после первой записи тем же механизмом оверлея.

Ни одного редиректа в полную анкету по пути.

### Профиль

Два честных раздела вместо одной анкеты: **«Рабочее»** (город, арены, услуги и цены — влияет на записи, открыто) и **«Витрина»** (фото, о себе, опыт, образование — влияет только на каталог, свёрнуто, подписано «нужно для публикации в каталоге»). Настройки как есть. Красные точки только там, где есть настоящий гейт.

**Блок арен:** поиск по имени и адресу → выбранное чипами → звезда на чипе = основная (второй список радио уходит) → пустой поиск = «Добавить „…“» тем же экраном.

**Цены:** услуга без цены показывает не ошибку, а состояние «клиент видит: по запросу». Save не блокируется.

### Сфокусированная задача как механизм

`OB_FLOW_STEP_DEFS` уже реестр блоков, рельс — просто массив. Значит оверлей на один блок стоит почти ничего и даёт единый способ вести тренера: «указать цены» = рельс `['services']`, «дозаполнить витрину» = рельс из каталожных блоков. Возврат — туда, откуда пришли, а не в анкету.

### Anti-regression guardrails

1. `arena_ids` — из канонической модели состояния, не из DOM-чекбоксов; после создания арены перезагружать список города.
2. `arena_ids` в `PATCH /trainer/profile` сделать необязательным: блок не тронут — поле не отправляется, стейл-UI физически не может стереть связи. Отдельный тест.
3. Смена города не отправляет пустой `arena_ids` молча — предупреждение и явное действие.
4. Без скачков UI: дебаунс поиска, фиксированная минимальная высота списка, без полной перерисовки блока на каждый ввод, без кражи фокуса (в TASK-018 уже была «качка» от пересчёта высоты).
5. Флаг фичи, старый список как fallback, версионированный `?v=` на статике.
6. TTV-гейты не меняются: `analyze_tt_minimal_profile_readiness` (5 критериев) остаётся контрактом.

### Slices

- **S1 — консистентность данных, вид не меняется.** Reload списка арен после создания; `arena_ids` из канонической модели, не из DOM; `arena_ids` необязательный в `PATCH /trainer/profile`; смена города не отправляет пустой набор молча. Отдельный PR.
- **S2 — цена перестаёт блокировать.** Услуга без цены сохраняется как «по запросу» (DEC-005/006), в строке услуги честная подпись вместо ошибки. Малый радиус, снимает главный симптом.
- **S3 — блок арен в профиле.** Поиск имя+адрес, чипы, основная на чипе, создание как «не нашлось». За флагом, старый список как fallback.
- **S4 — разделение профиля.** «Рабочее / Витрина», честные required-точки, каталожные секции свёрнуты.
- **S5 — сфокусированная задача.** Оверлей на один блок (DEC-008) + «Указать цены» на экране «Готово» онбординга; пуши D+1/8/21 ведут в оверлей, а не в анкету.
- **S6 — онбординг: город и арены.** Селектор города в шаге «где тренирую», арены только этого города, инлайн-создание вместо редиректа в профиль.
- **S7 — витрина после первой записи.** Оживление рельса как «дозаполнить витрину» (DEC-010); удаление мёртвых стилей `.profile-block-tour-bar`.

## Technical Plan

Первый PR = S1 + S2 (DEC-003 + DEC-006). S3–S7 — следующие PR, этот план их не реализует.

### Approach

Серверный PATCH уже принимает `arena_ids: null` как «не трогать» (`TrainerProfilePatchBody`, `update_trainer_profile`). Дыра — клиент всегда шлёт `arena_ids` из DOM-чекбоксов. Чиним каноническую модель `state.trainer.arena_ids`, reload после create, omit если набор не менялся, confirm при смене города. Цены: услуга без заполненного числа = «по запросу»; валидируем только мусор в заполненном поле; отмеченная услуга уходит в PATCH даже с пустыми тарифами.

### Changes (S1+S2)

- `tests/api/test_webapp_trainer_profile.py` — create arena → PATCH без `arena_ids` сохраняет связь; PATCH `arena_ids: []` снимает; PATCH services без цен оставляет услугу.
- `static/webapp/trainer-profile-main.js` — канонические `arena_ids`; `afterArenaSetupSuccess` зовёт `loadArenasForCity`; city onchange с confirm; omit `arena_ids`/`primary_arena_id` если равны snapshot; цены «по запросу».
- `static/webapp/mini-app-trainer-profile.css` — подпись «клиент видит: по запросу».
- `static/webapp/trainer-profile.html` — bump `?v=` у JS/CSS.

### Data/API

Контракт PATCH не меняется. `arena_ids` omitted → None → `set_trainer_arenas` не вызывается. Пустой массив — явная очистка.

### Tests

- AC-001/002: integration create → PATCH omit → связь на месте; PATCH [] → нет связи.
- AC-003: PATCH services с пустыми `price_tiers` сохраняет `trainer_services` с NULL ценой.
- AC-004/009: ручная проверка подписи и Save после онбординга; TTV-модуль не трогаем.

## Acceptance Criteria

### AC-001
Созданная тренером арена сразу выбрана в блоке арен и **переживает последующее сохранение профиля** — привязка не пропадает.
Requirement: CONFIRMED (пользователь: «изменения не должны вести к неконсистентному состоянию данных»)
Verification method: automated/integration (create → PATCH → привязка на месте) + manual/exploratory

### AC-002
`PATCH /trainer/profile` без поля `arena_ids` не меняет привязки арен: устаревший или незатронутый экран не может стереть набор.
Requirement: INFERRED (способ реализации guardrail 2; сам запрет потери данных — CONFIRMED)
Verification method: automated/contract

### AC-003
Услуга без цены сохраняется как «по запросу»: кнопка «Сохранить» не блокируется отсутствием цены, и правка города или арен проходит независимо от того, заполнены ли цены.
Requirement: CONFIRMED
Verification method: automated/unit (валидация) + manual/exploratory (сценарий тренера сразу после онбординга)

### AC-004
В строке услуги без цены тренер видит состояние «клиент видит: по запросу», а не ошибку и не красную точку.
Requirement: INFERRED (следствие DEC-005 — «прозрачно», а не молча)
Verification method: manual/exploratory + design-review

### AC-005
Выбрать нужную арену в городе с ~50 площадками — не более трёх действий, без прокрутки полного списка; адрес виден рядом с названием.
Requirement: CONFIRMED
Verification method: manual/exploratory на реальных данных + design-review

### AC-006
Второй список радиокнопок «основная площадка» исчезает: основная отмечается на чипе выбранной арены.
Requirement: CONFIRMED
