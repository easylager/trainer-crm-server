# Task

## Objective

Заменить онбординг тренера: убрать анкету и модерационный гейт с операционной работы,
свести первый запуск к одному экрану без клавиатурного ввода и одной задаче — отправить
ссылку живому ученику.

Инвариант, из которого выводится всё остальное:

> Тренер работает с первой секунды. Ни одно поле не спрашивается, пока без него
> не ломается конкретное действие с конкретным живым человеком.

## Диагноз (что чинили)

1. Модерация висела на аккаунте, хотя нужна только каталогу → 3 уровня полноты профиля,
   5 статусов, 6 состояний доступа, `BOOKING_READY`, песочница, 7 текстов гейта.
2. Онбординг заполнял сущности (анкета 12 полей), а не проживал рабочий момент.
3. Шаг «первая запись» давал 3 равнозначные кнопки в момент максимальной неуверенности.

## Что получилось

| Момент | Поверхность | Что происходит |
|---|---|---|
| T+0 | чат | одно сообщение + кнопка «Начать» → `trainer-onboarding` |
| T+40с | mini app | один экран: услуги, длительность, сетка недели с предзаполнением. Ноль ввода |
| T+2мин | mini app | «N окон на две недели» + одна кнопка «Отправить ученику» |
| T+… | чат | ученик записался → существующий пуш тренеру |
| после | хаб | одна карточка «следующий шаг» вместо чеклиста |
| позже | хаб | площадка — при первой записи; каталог — после 5 занятий |

Имя и аватар берутся из Telegram и не спрашиваются никогда.

## Главная проверка

`tests/api/test_onboarding_v2_end_to_end.py` — сквозной тест инварианта:
тренер без модерации и почти без профиля проходит первый экран, его ученик по личной ссылке
видит слоты и может записаться, **и при этом тренера нет в публичном каталоге**.
Тот же сценарий проверен вручную на живом API.

## Найдено и починено по дороге

1. **Длительность занятия расходилась с расписанием.** У колонок `session_duration_minutes`
   (45) и `min_hours_before_booking` (3) есть DB-дефолты, поэтому они никогда не NULL.
   COALESCE оставлял 45, пока генерировались 60-минутные слоты; тренер узнал бы об этом
   только когда клиент записался не на то время. Длительность стала явным вопросом
   (три чипа) и пишется как ответ, а не как умолчание.
   Регрессия: `test_chosen_duration_wins_over_the_column_default`.
2. **`logger` не был определён в `trainer_handlers.py`**, хотя использовался — любая ветка
   с `logger.warning` падала бы `NameError`. Добавлен модульный логгер.
3. **`.ob-skip { display: block }` перебивал атрибут `hidden`** — кнопка «Позже» была видна
   на первом шаге.
4. **Приглашение ученику содержало две ссылки** и инструкцию «меню слева → Тренеры и запись».
   Осталась одна строка и одна ссылка.
5. **Фальшивая запись «Пример / Алексей К., подтверждено»** в хабе удалена: занимала место
   главного действия и учила несуществующему.
6. **Ссылка могла вести в пустоту.** Шаблон недели есть, а будущие слоты кончились —
   ученик открыл бы ссылку и не увидел времени. Добавлен шаг `refresh_week` перед
   предложением делиться ссылкой: обещание ссылки и реальность расписания обязаны совпадать.
7. **Две конкурирующие подсказки «что дальше»** (`buildHubNextBestHint` + ритм-хинт каталога)
   молчат, пока на экране карточка «следующий шаг».

## Сознательно НЕ сделано

- **Колонки `is_sandbox` в БД оставлены.** Удалён только путь их создания в онбординге.
  Вычищать флаг из ~20 SQL-запросов — отдельная задача с высоким риском и нулевой
  пользой для онбординга; существующие демо-строки должны остаться удаляемыми.
- **Статусы `pending_contract` / `pending_payment` оставлены в БД.** Они больше ничего
  не гейтят (маппятся в ACTIVE), но их удаление — миграция, не касающаяся онбординга.
- **`trainer-profile` (анкета) не переписывалась.** Она нужна только для каталога и теперь
  открывается по явному желанию тренера, а не по принуждению.
- **Триал остался 14-дневным.** Замена на «первые 20 записей» — продуктовое решение,
  зафиксированное в другом документе; менять его молча в рамках онбординга нельзя.

## Дополнение 2026-09-01: две реальные проблемы после ревью пользователя

### 1. Доска хинтов молчала для немодерированных тренеров

Найден в ходе проверки вопроса «куда пропала доска хинтов». Блок ритм-подсказок
(`_build_hub_rhythm_inbox_candidates` в `trainer_hub_action_inbox.py`) был гейтом
`if not active or not complete`, где `active` = «в каталоге». В v2 это ложно почти
всегда для рабочего тренера. Заменено на `has_schedule` (наличие расписания) —
тот же сигнал, что определяет первый шаг онбординга. Тот же баг был продублирован
в клиентском JS-фолбэке (`buildHubRhythmCandidates`) — исправлен и там; заодно
удалена мёртвая функция `onboardingAllComplete` (JS) и её Python-двойник.

Заодно удалён устаревший rhythm-хинт `share_link` (текст «Поделитесь пригласительной
ссылкой») — он дублировал карточку «следующий шаг» и был неработоспособен по той же
причине.

Тесты: `test_rhythm_hints_visible_for_unmoderated_trainer_with_a_real_schedule`,
`test_rhythm_hints_stay_silent_before_the_first_schedule` в
`tests/application/test_trainer_hub_action_inbox.py`.

### 2. Двойная ссылка в сообщении для ученика

`t.me/share/url?url=X&text=Y` — Telegram рендерит `url` отдельной строкой сверху
текста; `share_text` уже содержал ссылку внутри себя → дублирование. Убрано `url=`
из обоих мест шэринга (хаб, онбординг), остался только `text`.

Заодно переписан копирайт карточки `share_more`: «Так это и будет дальше» (калька)
→ «Ссылка работает для всех» / «Она не одноразовая — отправляйте её каждому новому
ученику». Пользователю объяснена механика: карточка держится по числу реальных
записей, а не по факту клика — это осознанное решение, не баг.

## Дополнение 2026-09-01: тумблер «одна / несколько площадок»

Реальный кейс от пользователя: у арены ТЦ Замок слоты начинаются в :15, не в :00 —
плоская почасовая сетка первого экрана создавала бы невалидное расписание. Плюс
тренеры, работающие на нескольких аренах в разные дни.

### Решение

- **Backend** (`trainer_quick_setup_use_cases.py`): `QuickSetupDay` получил
  `arena_id`. Новый `_day_grid()` резолвит per-day сетку (offset из
  `arena_schedule_presets`, зафиксированную длительность) и валидирует часы против
  реального окна арены. `_validate_and_link_arenas()` привязывает арены к тренеру
  (`trainer_arenas`) и выставляет `primary_arena_id`, только если площадка ровно
  одна и поле ещё не занято.
- **Новый helper** `get_arena_schedule_preset_raw` в `arena_schedule_preset.py` —
  пресет произвольной арены без требования привязки к тренеру (для списка выбора).
- **API**: GET `/trainer/onboarding/quick-setup` отдаёт список всех активных арен
  с их реальной сеткой, привязанные арены, `primary_arena_id`, `multi_arena`
  (производный флаг) и `arena_id` в каждом дне `week`.
- **UI**: тумблер «Пока не указывать / Одна площадка / Несколько площадок» на
  первом экране. «Одна» — поиск + список, переключение переносит уже отмеченные
  дни на новую арену (обрезая часы вне её окна). «Несколько» — сначала отмечаем
  площадки, затем табы над сеткой; день, занятый другой вкладкой, — read-only с
  подписью «занято: <арена>». Ярлыки часов показывают реальное смещение (`10:15`
  вместо `10`), кнопка «Показать больше часов» скрывается для арены с явным окном,
  зафиксированная длительность — текстовое пояснение вместо чипов.
- Режим при повторном открытии — не отдельный флаг, а производная от сохранённых
  данных: несколько разных `arena_id` в неделе ⇒ мульти-режим.

### Найденные по дороге баги

1. **`replace_templates_for_day` валидирует `duration_minutes` даже для пустого
   дня.** Установка `primary_arena_id` на арену с зафиксированной длительностью
   ломала запись ВСЕХ остальных дней недели (0 слотов), потому что для них
   передавалась глобальная длительность тренера, не совпадающая с фиксированной.
   Исправлено — длительность для пустых дней резолвится по актуальному
   `primary_arena_id`, а не вслепую.
2. **`.ob-chips[hidden]` перебивался `display: flex`.** Тот же класс бага, что
   раньше поймали на `.ob-skip` — гвард добавлен.
