# Task

## Objective

При переносе записи длительность, площадка, услуга и тариф должны остаться теми же,
что и в исходной записи — тренер меняет только дату/время.

## Business Context

Источник — `.ai/tasks/TASK-005-booking-reschedule-preserve-data.md`: «При переносе
записи теряется контекст (тариф, площадка, услуга)».

Бо́льшая часть брифа уже закрыта прежним коммитом (`d1d27a69`, 2026-05-02, до этой
сессии) — арена, услуга и тариф исходной записи уже переносятся по умолчанию
(`schedule-editor-main.js`, `openQuickBookProfileServiceStep`, ветки `srcBooking`).
Реально ломается только длительность — и не «теряется», а **молча подменяется** на
45 минут, если исходная запись была нестандартной длины.

## Scope

### In Scope

- `static/webapp/schedule-editor-main.js`: `openQuickBookModalFromHub` — предзаполнение
  длительности при переносе.

### Out of Scope

- Атомарность переноса на бэкенде (сейчас это два отдельных вызова — создать новую
  запись, затем отменить старую; при неудаче отмены обе остаются живы с тостом
  «не удалось отменить старую»). Это отдельная, более рискованная архитектурная правка
  (нужен новый транзакционный эндпоинт), не то, о чём просит бриф. Задокументировано как
  EDGE-002, чинить не будем в этой задаче.
- Площадка/услуга/тариф — уже работают, не трогаем (`openQuickBookProfileServiceStep`,
  ветки `srcBooking`).

## Comprehension Tips

### Facts

- Перенос: карточка записи → «Перенести запись» → `startRescheduleFromBooking(b)`
  (`schedule-editor-main.js:6371-6383`) → `openQuickBookModalFromHub(prefill)`
  (`:6328-6360`), где `prefill.durationMinutes = bookingDurationMinutes(b)` — реальная
  длительность исходной записи, посчитанная из `start_time`/`end_time`.
- `openQuickBookModalFromHub` делает `dur.value = String(pDur)` на нативном `<select
  id="quickBookDurationSelect">` (`schedule-editor.html:618-627`), у которого фиксированный
  список `<option>`: `45/50/60/70/75/90/105/120/180` (константа `SCHEDULE_DURATION_OPTIONS`,
  `schedule-editor-main.js:3702`). Если `pDur` не входит в этот список — присваивание
  `.value` браузером молча игнорируется, остаётся то, что было выбрано раньше (по
  умолчанию — 45, помечено `selected` в разметке). Итоговое значение при подтверждении
  читается прямо из DOM (`dur.value`) без сверки с исходной записью — тренер не видит
  предупреждения.
- В файле уже есть готовая функция `normalizeDurationToScheduleSelect(minutes)`
  (`:3704-3720`), которая «снэпит» произвольные минуты к ближайшему значению из
  `SCHEDULE_DURATION_OPTIONS` — но она используется только для дефолтной длительности
  профиля тренера (`applyScheduleDefaultDurationFromProfile`), не в сценарии переноса.
  Снэп меняет саму длительность (пример: 40 → 45), что при переносе — уже другая
  оговорённая длина сессии, а не только смена даты/времени.

### Implications

- Правильный минимальный фикс — не снэп, а возможность выбрать точное исходное значение:
  если `pDur` не входит в фиксированный список, временно добавить в `<select>` `<option>`
  с этим точным значением и выбрать её. Так перенос действительно меняет только дату/время,
  а не заодно округляет длительность.
- Нельзя плодить временные опции без очистки — на разных переносах за один сеанс страницы
  значение будет разным; нужно снимать предыдущую временную опцию перед добавлением новой.
- Если позже трейнер выберет арену с фиксированной длительностью пресета,
  `syncDurationUIFromScheduleGrid` уже принудительно перезапишет `dur.value` на
  длительность пресета — существующее и корректное поведение, не трогаем.

## Acceptance Criteria

### AC-001
Перенос записи длительностью, не входящей в стандартный список (например, 40 или
55 минут), сохраняет исходную длительность как выбранную по умолчанию в модалке переноса.
Requirement: CONFIRMED
Verification method: manual
Result: NOT_VERIFIED

### AC-002
Перенос записи стандартной длительности (45/60/90 и т.д.) не регрессирует — выбрана
именно она.
Requirement: CONFIRMED
Verification method: manual
Result: NOT_VERIFIED

### AC-003
Повторный перенос другой записи за тот же визит на страницу (без перезагрузки) не
накапливает старые временные `<option>` в селекте.
Requirement: INFERRED
Verification method: manual
Result: NOT_VERIFIED

## Edge Cases

### EDGE-002
Создание новой записи при переносе может пройти успешно, а отмена старой — упасть
(сеть/гонка). Сейчас это просто тост «Новая запись создана, но старую не удалось
отменить» без отката и без ретрая — обе записи остаются активными.
Severity: MEDIUM
Status: OPEN
Resolution: не в этой задаче — нужен отдельный транзакционный эндпоинт переноса на
бэкенде; риск регресса выше, чем то, что просит бриф.

## Technical Plan

В `openQuickBookModalFromHub`, в блоке `var dur = document.getElementById(...)`:
1. Посчитать `wanted = !isNaN(pDur) && pDur >= 15 ? pDur : (state.defaultSlotDurationMinutes || 45)`.
2. Если `SCHEDULE_DURATION_OPTIONS.indexOf(wanted) < 0` — убрать предыдущую опцию с
   `data-off-grid="1"` (если её значение не совпадает с `wanted`), добавить новую
   `<option value="wanted" data-off-grid="1">{wanted} мин</option>`.
3. `dur.value = String(wanted)`.
