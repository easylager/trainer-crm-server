# Feature Specification: Расширенный профиль тренера

**Feature Branch**: `005-trainer-profile-details`  
**Created**: 2026-03-24  
**Status**: Draft  
**Input**: User description: "Нужна доработка профиля тренера: для клиента важно видеть больше полезной информации, и для тренера важно показать больше деталей о себе."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Клиент осознанно выбирает тренера (Priority: P1)

Клиент открывает карточку тренера и видит не только базовые данные, но и структурированные дополнительные блоки (например: специализация, формат занятий, достижения, особенности работы), чтобы понять, подходит ли тренер под его запрос.

**Why this priority**: Это напрямую влияет на конверсию просмотра профиля в запись и снижает риск «слепого» выбора.

**Independent Test**: Можно проверить на одном тренере: карточка показывает новый расширенный набор данных, клиент способен принять решение без перехода во внешние источники.

**Acceptance Scenarios**:

1. **Given** клиент открыл карточку тренера, **When** профиль заполнен расширенными данными, **Then** клиент видит отдельные блоки «о тренере» в понятной структуре.
2. **Given** клиент сравнивает двух тренеров, **When** в карточках есть одинаковые типы новых полей, **Then** сравнение возможно без неоднозначной трактовки.
3. **Given** часть новых полей у тренера не заполнена, **When** клиент открывает профиль, **Then** интерфейс не ломается и не показывает технические заглушки.

---

### User Story 2 - Тренер гибко презентует себя в профиле (Priority: P2)

Тренер при заполнении/редактировании профиля может добавить дополнительные сведения о своей экспертизе и условиях работы через понятные контролы (выбор, перечисление, краткие описания в ограниченном формате).

**Why this priority**: Повышает качество самопрезентации и снижает барьер для обновления профиля.

**Independent Test**: Можно проверить в изоляции через создание/обновление одного профиля: тренер заполняет новые поля, сохраняет и видит их в своём профиле без потери ранее введённых данных.

**Acceptance Scenarios**:

1. **Given** тренер редактирует профиль, **When** выбирает/вводит новые атрибуты, **Then** изменения успешно сохраняются и читаются обратно.
2. **Given** тренер вводит некорректное значение в поле с ограниченным набором вариантов, **When** пытается сохранить профиль, **Then** получает понятную валидационную ошибку.
3. **Given** тренер уже имеет заполненный базовый профиль, **When** добавляет только один новый блок, **Then** остальной профиль не перезаписывается и не теряется.

---

### User Story 3 - Админ и продуктовая команда поддерживают качество данных (Priority: P3)

Система ограничивает свободный ввод там, где нужны сравнимые данные, и сохраняет совместимость со старыми профилями, чтобы качество карточек оставалось стабильным при росте базы тренеров.

**Why this priority**: Без единых правил заполнения качество данных быстро деградирует и ухудшает UX клиентов.

**Independent Test**: На выборке старых и новых профилей можно убедиться, что старые карточки читаются, а новые поля валидируются по согласованным правилам.

**Acceptance Scenarios**:

1. **Given** профиль создан до появления новых полей, **When** система отдаёт его клиенту, **Then** профиль остаётся доступным и не вызывает ошибок отображения.
2. **Given** новые поля имеют формат/лимиты, **When** приходит запрос на сохранение профиля, **Then** данные приводятся к единому виду или отклоняются с понятным сообщением.

### Edge Cases

- Тренер заполнил только часть новых полей: профиль сохраняется, клиент видит только доступные блоки без «пустых» технических секций.
- В справочном поле выбора вариант был удалён из актуального списка после сохранения в старом профиле: существующее значение читается корректно до явного изменения.
- Тренер пытается вставить слишком длинный текст в поле «о себе»: система ограничивает ввод и возвращает понятную ошибку.
- Профиль содержит смешанные данные (старый формат + новый): выдача профиля для клиента остаётся стабильной.

## Requirements *(mandatory)*

### Telegram / боты *(если фича затрагивает `src/bot/` или сообщения ботов)*

- Пользовательские тексты, inline/reply-клавиатуры, режим разметки и эмодзи **MUST** соответствовать [.specify/memory/constitution.md](../../.specify/memory/constitution.md) § VII.
- Если в боте появляется редактирование новых атрибутов профиля, выбор/подсказки по полям **MUST** быть сформулированы на русском и согласованы с терминологией карточки тренера.

### Mini App (`static/webapp/`) *(если фича затрагивает веб-экраны в Telegram)*

- Если новые поля выводятся в Mini App, повторяющиеся блоки профиля **MUST** использовать единый визуальный паттерн и токены из [.specify/memory/constitution.md](../../.specify/memory/constitution.md) § VIII.

### Functional Requirements

- **FR-001**: Система **MUST** поддерживать расширенный набор атрибутов профиля тренера, которые помогают клиенту оценить специализацию и формат работы тренера.
- **FR-002**: Система **MUST** предоставлять тренеру возможность заполнять и обновлять новые атрибуты профиля без потери существующих данных.
- **FR-003**: Для полей с ограниченным набором значений система **MUST** предоставлять список допустимых вариантов и отклонять недопустимые значения.
- **FR-004**: Клиентская карточка тренера **MUST** отображать новые атрибуты в структурированном, сравнимом формате.
- **FR-005**: Система **MUST** сохранять обратную совместимость для профилей, созданных до внедрения новых атрибутов.
- **FR-006**: Валидационные ошибки при заполнении новых полей **MUST** быть человеко-понятными и указывать, как исправить ввод.

### Key Entities *(include if feature involves data)*

- **TrainerProfileExtended**: расширенная модель профиля тренера с новыми полями самопрезентации (структурированные и текстовые атрибуты).
- **ProfileFieldOption**: вариант выбора для справочных полей профиля (например, образование/формат работы), используемый для единообразной валидации и отображения.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Не менее 90% протестированных карточек тренеров отображают новые блоки профиля без ошибок рендера и без пустых технических заглушек.
- **SC-002**: Не менее 95% валидных обновлений профиля с новыми полями сохраняются успешно с первой попытки в тестовом сценарии.
- **SC-003**: Не менее 80% участников продуктовой проверки подтверждают, что по обновлённой карточке легче принять решение о выборе тренера (по внутреннему UX-чеклисту).
- **SC-004**: Доля валидационных ошибок по новым полям, не содержащих понятной подсказки пользователю, равна 0 на приёмочном тестировании.
