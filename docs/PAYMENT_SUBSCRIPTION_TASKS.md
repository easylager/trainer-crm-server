# Задачи: подписки и оплата

Разбивка всего, что касается подписок тренеров и приёма платежей (абонементы, комиссия, выплаты), на отдельные задачи с зависимостями и критериями готовности. Архитектура: модуль внутри основного приложения (см. раздел 5 в PAYMENT_B2B_BELARUS_PLAN.md).

---

## Блок 1: Подписка тренера (модель и пробный период)

### Задача 1.1 — Модель данных подписки (БД + домен)

**Цель:** в БД и домене есть тарифы, подписки тренеров и счета; можно проверить «есть ли у тренера активная подписка».

**Scope:****
- Миграция: таблицы `subscription_plans`, `trainer_subscriptions`, `trainer_invoices` (поля по плану: plan_id, started_at, expires_at, status; invoice: amount_cents, period_start/end, due_date, status, paid_at, payment_external_id).
- Сиды или миграция: минимум два плана — «Пробный» (0 BYN, 14 дней, `is_trial = true`) и «Месяц» (X BYN, 30 дней).
- Доменные сущности/репозитории или use cases: получение активного плана по id, создание подписки, проверка `trainer_has_active_subscription(trainer_id)` (подписка с `expires_at > now()` и `status in ('trial', 'active')`).

**Зависимости:** нет.

**Готово когда:** миграция применена, сиды есть, из кода вызывается `trainer_has_active_subscription` и результат совпадает с данными в БД.

---

### Задача 1.2 — Выдача пробного периода при регистрации/одобрении тренера

**Цель:** при появлении тренера в системе (регистрация или смена статуса на «одобрен») у него автоматически создаётся подписка «Пробный» на 14 дней.

**Scope:****
- В месте, где тренер переводится в статус «активен» / «одобрен» (или создаётся как активный), вызвать use case «создать подписку» с планом «Пробный», если у тренера ещё не было подписки с `plan.is_trial`.
- Ограничение: пробный период один раз на тренера (проверка: уже есть запись в `trainer_subscriptions` с `plan.is_trial = true` — новый trial не создаём).

**Зависимости:** 1.1.

**Готово когда:** при одобрении тестового тренера в БД появляется запись в `trainer_subscriptions` с планом «Пробный», `expires_at = now() + 14 days`, `status = trial`. Повторное «одобрение» не создаёт второй trial.

---

### Задача 1.3 — Ограничения при отсутствии активной подписки

**Цель:** тренеры без активной подписки (истёк trial или не продлена платная) не показываются в каталоге и не могут принимать платежи за абонементы через платформу.

**Scope:****
- Каталог (API списка тренеров для клиентов): фильтр по `trainer_has_active_subscription(trainer_id) = true`. Тренеры в `past_due` или без записи не попадают в выдачу.
- API создания платежа за абонемент (и при необходимости за разовое занятие): перед созданием `pass_purchase` проверить подписку тренера; если нет активной — ответ 403 с текстом «Подписка не активна» (или аналог). В Mini App показывать сообщение «Оплатите подписку, чтобы принимать платежи».
- Единая точка проверки: одна функция/use case `trainer_has_active_subscription`, вызываемая и из каталога, и из API платежей.

**Зависимости:** 1.1.

**Готово когда:** при ручном переводе подписки тренера в past_due (или истечении expires_at) тренер исчезает из каталога и запрос «купить абонемент» у этого тренера возвращает ошибку; после продления подписки тренер снова в каталоге и платёж возможен.

---

### Задача 1.4 — Переход подписки в past_due и напоминания

**Цель:** по истечении срока подписки статус меняется на past_due; за 2–3 дня до окончания тренеру уходит напоминание в боте с кнопкой «Оплатить подписку».

**Scope:****
- Фоновая задача (cron/periodic): раз в день (или раз в час) выбирать подписки с `expires_at < now()` и `status in ('trial', 'active')`, обновлять `status = 'past_due'`.
- Вторая задача: за 2–3 дня до `expires_at` отправлять тренеру сообщение в Telegram (бот) с текстом «Подписка истекает DD.MM. Оплатите, чтобы оставаться в каталоге» и кнопкой (Web App или ссылка на оплату подписки). Не спамить: одну отправку на подписку (флаг `reminder_sent_at` в подписке или отдельная таблица отправок).
- Админка (опционально): список тренеров с датой окончания подписки и статусом; кнопка «Продлить вручную» (увеличить `expires_at` на месяц для тестов).

**Зависимости:** 1.1, 1.2.

**Готово когда:** по расписанию истёкшие подписки переходят в past_due; за 2 дня до конца тренер получает одно напоминание в боте с кнопкой.

## Блок 2: Приём платежей от клиентов (абонементы)

### Задача 2.1 — Интеграция с провайдером (bePaid): конфиг и адаптер

**Цель:** приложение умеет вызывать API провайдера (создание платежа, получение payment_url) в sandbox и prod; секреты и URL вынесены в конфиг.

**Scope:****
- Конфиг: `PAYMENT_PROVIDER=bepaid`, `BEPAID_SHOP_ID`, `BEPAID_SECRET_KEY`, `BEPAID_BASE_URL` (или отдельные переменные для sandbox/prod). Флаг `PAYMENT_SANDBOX=true/false` или отдельный URL для sandbox.
- Адаптер (интерфейс + реализация): например `PaymentGateway.create_payment(amount_cents, currency, description, tracking_id, return_url, notification_url, metadata) -> { payment_url, transaction_id }`. Реализация — HTTP-запрос к bePaid (документация провайдера). Ошибки провайдера пробрасывать с понятным кодом/текстом.
- Не вызывать из бизнес-логики провайдера напрямую — только через адаптер.

**Зависимости:** нет (можно делать параллельно с 1.x).

**Готово когда:** по вызову адаптера с тестовыми ключами sandbox возвращается `payment_url`; переход по нему открывает форму оплаты bePaid (sandbox). Конфиг читается из env.

---

### Задача 2.2 — Создание намерения оплаты (pass purchase intent) и переход на оплату

**Цель:** клиент в Mini App нажимает «Оплатить» за абонемент → бэкенд создаёт запись в `pass_purchases` со статусом `pending` и возвращает клиенту `payment_url`; клиент переходит на страницу оплаты провайдера.

**Scope:****
- Расширить (или добавить) use case: «создать намерение покупки абонемента»: вход — client_id (из сессии/initData), trainer_id, product_id, amount_cents. Проверки: тренер существует, продукт принадлежит тренеру, у тренера активная подписка (задача 1.3). Создать запись `pass_purchases`: status=pending, amount_cents, trainer_id, product_id, client_id, сохранить `tracking_id` (id покупки или uuid) для webhook.
- Вызвать `PaymentGateway.create_payment(amount_cents, BYN, description, tracking_id, return_url, notification_url, metadata: { purchase_id })`. В `return_url` — страница нашего Mini App (success) или отдельная страница «Оплата прошла».
- API для фронта: например `POST /api/webapp/client/pass-purchase-intent` с телом `{ trainer_id, product_id }` (amount и продукт берутся из каталога продуктов). Ответ: `{ payment_url, purchase_id }`. Фронт открывает `payment_url` в новом окне или редиректе.
- В БД в `pass_purchases` уже есть или добавить поля: `payment_external_id`, `platform_fee_cents`, `trainer_amount_cents` (заполняются при webhook).

**Зависимости:** 2.1, 1.3 (проверка подписки).

**Готово когда:** из Mini App можно инициировать оплату; в БД создаётся pending-покупка; фронт получает payment_url и редирект на bePaid; после оплаты пользователь возвращается по return_url (обработку успеха — следующая задача).

---

### Задача 2.3 — Webhook успешной оплаты и создание pass_instance

**Цель:** при успешной оплате провайдер шлёт webhook на наш бэкенд; мы обновляем покупку в `paid`, считаем комиссию и сумму тренеру, создаём `pass_instance` и при необходимости запись для выплаты.

**Scope:****
- Роут `POST /api/webhooks/bepaid` (или общий `/api/webhooks/payment`) — принимает тело от bePaid. Проверка подписи/секрета (если провайдер подписывает запросы). По `tracking_id` или `metadata.purchase_id` найти запись в `pass_purchases`; если статус уже `paid` — ответ 200, идемпотентность (не создавать второй pass_instance).
- При статусе «успех» от провайдера: обновить `pass_purchases`: status=paid, payment_external_id=transaction_id. Вычислить `platform_fee_cents = round(amount_cents * 0.02)`, `trainer_amount_cents = amount_cents - platform_fee_cents`, записать в покупку. Создать `pass_instance` (логика как в текущем `create_client_pass_purchase`, но без повторного списания денег — только запись). Добавить/обновить запись в таблице выплат тренеру за текущий период (trainer_payouts: увеличить amount_payable_cents, total_earned_cents и т.д.).
- Ответ webhook: 200 OK, чтобы провайдер не повторял запрос.

**Зависимости:** 2.2, наличие таблицы/полей для выплат (задача 2.4 может быть частично раньше).

**Готово когда:** после оплаты в sandbox тестовой картой webhook вызывается; в БД покупка в статусе paid, создан pass_instance, заполнены platform_fee_cents и trainer_amount_cents; данные по выплате тренеру обновлены. Повторная отправка того же webhook не создаёт дубликаты.

---

### Задача 2.4 — Учёт комиссии и таблица выплат тренерам

**Цель:** по каждой оплате фиксируется комиссия платформы и сумма к выплате тренеру; есть таблица/агрегат по периодам для выплат.

**Scope:****
- В `pass_purchases` поля: `platform_fee_cents`, `trainer_amount_cents` (заполняются в webhook, задача 2.3).
- Таблица `trainer_payouts`: id, trainer_id, period_start, period_end (например месяц), total_earned_cents, platform_fee_total_cents, amount_payable_cents, status (pending / paid), paid_at, payment_details (текст или реквизиты). При webhook — создать строку за период или обновить существующую (добавить к total_earned_cents, platform_fee_total_cents, amount_payable_cents).
- Use case или сервис: «получить выплаты тренера» (для API «Мои выплаты»), «сформировать отчёт выплат за период» (для админки/ручной выплаты).

**Зависимости:** 2.3 (логика в webhook).

**Готово когда:** после нескольких тестовых оплат в БД видны корректные суммы по тренерам и по периодам; комиссия 2% считается верно.

---

### Задача 2.5 — Фронт: оплата абонемента и успешный возврат

**Цель:** в Mini App (client-buy-pass) вместо мока — вызов API создания намерения, переход на payment_url; после возврата по success_url — показ «Оплачено», обновление списка «Мои абонементы».

**Scope:****
- Вызов `POST /api/webapp/client/pass-purchase-intent` с trainer_id, product_id (и initData для авторизации). Открытие `payment_url` (новое окно или текущее с редиректом). На странице success_url (наша страница или query-параметр на client-buy-pass) — показать «Оплата прошла», запрос списка абонементов и редирект или кнопка «В мои абонементы».
- Обработка ошибок: подписка не активна, продукт недоступен — показать сообщение из ответа API.

**Зависимости:** 2.2.

**Готово когда:** полный сценарий «выбрал абонемент → Оплатить → оплата в sandbox → возврат → вижу абонемент в списке» работает.

## Блок 3: Оплата подписки тренером

### Задача 3.1 — Выставление счёта за подписку (invoice)

**Цель:** система может сформировать счёт (invoice) за следующий период подписки и отдать тренеру ссылку на оплату или данные счёта.

**Scope:****
- Use case: «создать счёт за подписку»: вход — trainer_id, plan_id (например «Месяц»). Проверка: план не trial. Создать запись в `trainer_invoices`: trainer_id, subscription_plan_id, amount_cents, period_start, period_end, due_date, status=sent (или draft → sent при отправке). Ссылка на оплату будет вести на checkout с этим invoice_id в metadata.
- API для бота/кабинета: «получить текущий счёт к оплате» (последний invoice со статусом sent/overdue для тренера), «получить ссылку на оплату подписки» (создать invoice при необходимости и вернуть payment_url от провайдера с amount = plan.price_cents, description = «Подписка за период …», tracking_id = invoice_id или uuid, metadata.invoice_id).

**Зависимости:** 1.1, 2.1 (адаптер создания платежа можно переиспользовать для подписки).

**Готово когда:** по запросу для тренера с past_due создаётся invoice и возвращается payment_url; оплата в sandbox по этой ссылке возможна (обработка успеха — задача 3.2).

---

### Задача 3.2 — Webhook оплаты подписки и продление доступа

**Цель:** при успешной оплате счёта за подписку обновить invoice (paid), продлить подписку тренера (новая запись в trainer_subscriptions с status=active и expires_at = period_end).

**Scope:****
- В webhook провайдера различать тип платежа: по metadata (invoice_id) или отдельный notification_url для подписок. Найти invoice по tracking_id/metadata; если уже paid — 200, идемпотентность.
- Обновить trainer_invoices: status=paid, paid_at=now(), payment_external_id=transaction_id.
- Создать или обновить trainer_subscriptions: trainer_id, plan_id (оплаченный план), started_at=period_start, expires_at=period_end, status=active. Тренер снова в каталоге и может принимать платежи.

**Зависимости:** 2.3 (общий webhook или отдельный роут), 3.1.

**Готово когда:** тренер с past_due оплачивает подписку по ссылке (sandbox) → webhook → invoice paid, подписка активна до period_end; тренер появляется в каталоге и может принимать оплату за абонемент.

---

### Задача 3.3 — Бот: кнопка «Подписка» / «Оплатить подписку»

**Цель:** тренер в боте видит статус подписки и может перейти к оплате.

**Scope:****
- Команда или кнопка «Подписка»: сообщение с текстом «Подписка до DD.MM» или «Подписка истекла. Оплатите, чтобы оставаться в каталоге» и кнопкой «Оплатить подписку» (Web App или URL). Web App или API возвращает payment_url (задача 3.1); открыть в браузере или Mini App.
- Показ счёта: при необходимости вывести «К оплате X BYN за период с … по …» и кнопку «Оплатить картой» (payment_url).

**Зависимости:** 3.1.

**Готово когда:** тренер нажимает «Оплатить подписку», переходит на checkout, оплачивает (sandbox); после webhook подписка продлевается (проверено в 3.2).

## Блок 4: Отчётность и выплаты

### Задача 4.1 — API и экран «Мои выплаты» для тренера

**Цель:** тренер видит оборот, удержанную комиссию и сумму к выплате за период, историю выплат.

**Scope:****
- API: `GET /api/webapp/trainer/payouts` (или в существующем роутере тренера). Ответ: текущий период (total_earned_cents, platform_fee_total_cents, amount_payable_cents), список прошлых периодов со статусом (pending / paid) и paid_at.
- Mini App или раздел в веб-кабинете тренера: блок «Финансы» / «Выплаты» — те же данные в читаемом виде (BYN, даты).

**Зависимости:** 2.4.

**Готово когда:** тренер в личном кабинете (или по API) видит корректные суммы после тестовых оплат.

---

### Задача 4.2 — Админка: отчёт по выплатам и ручная отметка «выплачено»

**Цель:** админ может сформировать отчёт «кому сколько платить» за период и после перевода отметить выплату как выполненную.

**Scope:****
- Экран/страница: выбор периода (месяц); таблица тренеров с суммой к выплате (amount_payable_cents), статусом. Кнопка «Отметить выплату» (ввод реквизитов/комментария, смена статуса на paid, paid_at=now()).
- Опционально: экспорт в CSV/Excel для бухгалтерии.

**Зависимости:** 2.4.

**Готово когда:** админ выбирает период, видит список тренеров и сумм; после ручного перевода может отметить выплату — в интерфейсе тренера статус меняется на «Выплачено».

### Задача 5.2 — Переключение на прод и первый реальный платёж

**Цель:** в проде используются боевые ключи и URL провайдера; webhook настроен на прод; проведён один-два тестовых реальных платежа с последующим возвратом при необходимости.

**Scope:****

- В личном кабинете провайдера: notification_url указывает на прод-сервер; проверка подписи webhook.
- Один-два реальных платежа (минимальная сумма), проверка прохождения webhook и появления записей в БД; при необходимости — возврат через провайдера.

**Зависимости:** 5.1.

**Готово когда:** прод принимает платежи; webhook в проде обрабатывается; тестовые реальные платежи прошли и при необходимости возвращены.
