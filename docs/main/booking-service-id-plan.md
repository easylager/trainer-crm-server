# План: обязательная привязка услуги к записи (booking.service_id)

**Цель:** У каждой записи (booking) всегда должна быть связь с услугой. Нельзя создать запись без услуги. Это нужно для корректной статистики выручки, отображения услуги в карточке записи и единообразия данных.

---

## 1. Текущее состояние

- В таблице **`bookings`** нет поля `service_id`.
- Услуга выводится только косвенно:
  - через **`client_request_id`** → `client_requests.service_id` (если запись с заявки);
  - через **сессию клиента** `selected_service_id` (для уведомлений; не хранится в записи).
- Создание записи идёт из нескольких мест; нигде не передаётся и не сохраняется услуга на уровне брони.

---

## 2. Изменения в БД и модели

### 2.1 Миграция

- Добавить в таблицу **`bookings`** колонку **`service_id`** (FK на `services.id`, nullable на первом этапе для обратной совместимости).
- Индекс: `ix_bookings_service_id` для выборок по услуге/статистике.

### 2.2 Обратная заливка (backfill)

- Для существующих записей заполнить `service_id`:
  - если есть **`client_request_id`** → взять `service_id` из `client_requests`;
  - иначе: взять **первую услугу тренера** (любая из `trainer_services` по `trainer_id`, например с минимальным `service_id` или по `sort_order`), т.к. исторически «одна цена/услуга» на тренера допускалась.
- После backfill можно сделать колонку **NOT NULL** отдельной миграцией и добавить проверку на уровне БД.

### 2.3 Модель

- В **`src/infrastructure/db/models.py`** в классе **`Booking`** добавить поле:
  - `service_id: Mapped[int] = mapped_column(ForeignKey("services.id", ondelete="RESTRICT"), nullable=False, index=True)`
  - После перехода на NOT NULL убрать `nullable=True` в миграции и здесь.

---

## 3. Use case: create_booking

**Файл:** `src/application/booking_use_cases.py`

- Добавить обязательный аргумент **`service_id: int`** в `create_booking(...)`.
- В **INSERT** добавить `service_id` в список колонок и значений.
- Проверка: услуга должна относиться к этому тренеру (существует строка в `trainer_services` для `(trainer_id, service_id)`). Иначе возвращать `None` или вызывать исключение — запись без валидной услуги не создаём.

---

## 4. Источники service_id по сценариям

### 4.1 Клиент записывается сам (Mini App)

**Эндпоинт:** `POST /api/webapp/client/booking`  
**Тело:** сейчас `slot_id`, `phone`, `comment`, `request_id?`.

- Добавить в тело запроса поле **`service_id: int`** (обязательное).
- Логика:
  - если передан **`request_id`** → взять **`service_id` из заявки** (проверить, что заявка принадлежит клиенту и тренер откликнулся); можно не требовать `service_id` в теле, а брать из заявки;
  - если без заявки (запись из каталога) → **`service_id` из тела** (клиент уже выбрал услугу в каталоге; на фронте брать из сессии/контекста и передавать в запросе).
- Валидация: `service_id` должен быть среди услуг выбранного тренера (`trainer_services`).
- Вызов: `create_booking(..., service_id=...)`.

### 4.2 Клиент записывается сам (бот)

**Обработчики:** `on_book_slot`, `on_booking_message` (финальный шаг создания записи), и др. места, где вызывается `create_booking`.

- В **state** бронирования хранить **`service_id`**:
  - при входе в сценарий записи (например, из каталога по кнопке «Записаться») брать **`selected_service_id`** из **client_sessions** и класть в `state`;
  - при записи по заявке — брать **`service_id`** из заявки и тоже класть в `state`.
- При вызове `create_booking(...)` передавать **`service_id`** из `state`.
- Сценарии «Повторить» / «Сделать регулярным» / «Слот освободился»:
  - для **повтора** и **регулярного** — брать **`service_id`** из **исходной записи** (после добавления поля в БД и в ответы API/use case, которые отдают данные брони);
  - для «слот освободился» — по возможности брать из контекста (например, из данных по слоту/ожиданию) или из первой услуги тренера как fallback только если контекста нет (лучше хранить service_id в wait_request, если нужно).

### 4.3 Тренер создаёт запись (расписание, Mini App)

**Эндпоинт:** `POST /api/webapp/trainer/booking`  
**Тело:** сейчас `slot_id`, `client_id`.

- Добавить в тело **`service_id: int`** (обязательное).
- На фронте (schedule-editor / экран «Записать клиента») перед отправкой запроса показывать **выбор услуги** тренера (список из `trainer_services` по текущему тренеру). Без выбранной услуги кнопку «Записать» не активировать / запрос не отправлять.
- Валидация на бэкенде: `service_id` ∈ услуги тренера. Вызов `create_booking(..., service_id=..., created_by_trainer=True)`.

### 4.4 Тренер создаёт запись из заявки (Mini App)

**Эндпоинт:** `POST /api/webapp/trainer/requests/{request_id}/book`  
**Тело:** `slot_id`.

- **Услуга уже есть у заявки.** В `create_booking` передать **`service_id` из заявки** (из `client_requests.service_id` по `request_id`). В теле запроса `service_id` не нужен.
- Убедиться, что при создании брони в API вызывается что-то вроде `get_request_client_for_trainer_booking` или аналог, откуда можно взять `service_id` заявки, и передать его в `create_booking`.

### 4.5 Тренер создаёт запись из заявки (бот)

**Обработчик:** `on_request_book_slot` (callback при выборе слота по заявке).

- При вызове `create_booking` передать **`service_id`** из **заявки** (данные заявки уже подгружаются в `get_request_client_for_trainer_booking` или в контексте; при необходимости расширить ответ, чтобы в нём был `service_id`).

### 4.6 Тренер создаёт запись из расписания (бот)

**Обработчик:** `schedule_create_booking_finalize` (выбор слота и клиента, затем создание записи).

- Сейчас тренер не выбирает услугу. Нужно добавить **шаг выбора услуги** в сценарий:
  - после выбора клиента (или после выбора слота) показать кнопки с услугами тренера (запрос к API или кэшу списка услуг тренера);
  - в callback или state сохранить `service_id`;
  - при финальном создании записи вызывать `create_booking(..., service_id=..., created_by_trainer=True)`.
- Альтернатива: если у тренера одна услуга — подставлять её автоматически без шага выбора.

### 4.7 Recurring (автозаполнение недели)

**Файл:** `src/application/recurring_use_cases.py`  
**Функция:** создание записей при «применении шаблона» недели.

- В **`recurring_client_slots`** при необходимости добавить **`service_id`** (миграция + модель), чтобы у каждого регулярного слота была услуга. Тогда при вызове `create_booking` для такого слота передавать этот `service_id`.
- Если не хотим менять recurring сразу: временно брать **первую услугу тренера** из `trainer_services` при создании записи из recurring (одна запись = одна услуга по умолчанию).

## 5. API и фронт

### 5.1 Клиентский Mini App (запись на занятие)

- При открытии экрана записи (выбор слота и т.д.) в запросе создания брони всегда передавать **`service_id`**:
  - из текущей сессии каталога (**selected_service_id**), если запись из каталога;
  - при записи по заявке — можно брать из заявки на бэкенде (тогда в теле можно не дублировать), но фронт может передать для единообразия.
- Валидация: не отправлять запрос без выбранной услуги (в каталоге услуга уже выбрана до перехода к тренеру).

### 5.2 Тренерский Mini App (расписание / запись клиента)

- **Список услуг тренера:** использовать существующий или новый эндпоинт (например, список услуг с ценами для тренера).
- В экране «Создать запись» (выбор слота → выбор клиента → **выбор услуги** → подтверждение):
  - добавить шаг или поле **«Услуга»** с выпадающим списком / кнопками услуг тренера;
  - в `POST /trainer/booking` передавать **`service_id`**.

### 5.3 Тренерский Mini App (заявки → записать клиента)

- При записи по заявке **не спрашивать** услугу у пользователя — брать из заявки на бэкенде и передавать в `create_booking`.

---

## 6. Отображение услуги

- Во всех местах, где показывается запись (клиентские записи, тренерские записи, уведомления), брать **название услуги** из **`bookings.service_id`** → `services.name` (JOIN), а не из заявки/сессии.
- Обновить выборки в **booking_use_cases** (list_bookings_for_client, list для тренера, get_bookings_pending_notification и т.д.): добавить в SELECT и маппинг **service_id** и **service_name** через `bookings.service_id` → `services`.

---

## 7. Статистика выручки

- В **stats_use_cases** считать выручку по **реальной цене услуги** по каждой записи:
  - по `bookings.service_id` и `bookings.trainer_id` брать **price_cents** из **trainer_services**;
  - суммировать по занятиям за период.
- Убрать приближение «средняя цена × количество» в пользу «сумма (price_cents по каждой записи)».

---

## 8. Порядок внедрения (краткий)

1. Миграция: добавить **`bookings.service_id`** (nullable), индекс.
2. Backfill: заполнить **service_id** из заявки или первой услуги тренера.
3. Модель **Booking**: добавить поле **service_id**.
4. **create_booking**: добавить параметр **service_id**, проверка по **trainer_services**, INSERT с **service_id**.
5. **API client booking**: обязательный **service_id** (из тела или из заявки); валидация; вызов **create_booking** с **service_id**.
6. **API trainer booking**: обязательный **service_id** в теле; валидация; вызов **create_booking** с **service_id**.
7. **API trainer request book**: брать **service_id** из заявки, передавать в **create_booking**.
8. **Бот — клиент**: во все вызовы **create_booking** передавать **service_id** (из state/сессии/заявки).
9. **Бот — тренер**: при записи из заявки — **service_id** из заявки; при записи из расписания — шаг выбора услуги + **service_id** в **create_booking**.
10. **Recurring**: передавать **service_id** (из recurring или первая услуга тренера).
11. Списки/детали записей: везде выводить **service_name** из **bookings.service_id**.
12. Статистика: пересчёт выручки по **bookings.service_id** + **trainer_services.price_cents**.
13. Миграция: сделать **bookings.service_id** NOT NULL.
14. Фронт: тренерский Mini App — экран/шаг выбора услуги при создании записи из расписания.

---

## 9. Риски и замечания

- Старые записи без заявки после backfill получат «первую услугу» тренера — исторически может быть неточно, но для отчётов и единообразия приемлемо.
- Recurring: если не добавлять **service_id** в **recurring_client_slots**, при автозаписи можно подставлять первую услугу тренера; при добавлении поля в recurring станет точнее.
- Все новые записи после внедрения будут создаваться только с явным **service_id**; отказ от создания записи без услуги станет правилом на уровне кода и (после NOT NULL) на уровне БД.
