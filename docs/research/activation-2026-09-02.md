# Исследование: как система ведёт тренера от первой записи к полному использованию

Дата: 2026-09-02 · Метод: разбор кода (`src/application`, `src/bot`, `static/webapp`, миграции), без прогона на живых данных.
Продовых данных в этой среде нет — в локальной БД 2 тестовых тренера, `pending_profile`. Все выводы ниже выведены из кода и перепроверены по конкретным строкам; ни одна цифра не выдумана.

---

## 1. Что уже построено

Онбординг v2 сделан хорошо и его трогать не надо. Один экран (`trainer-onboarding.html` + `trainer_quick_setup_use_cases.py`): чипсы услуг, длительность, площадка, предзаполненная сетка недели → пишутся услуги, шаблон недели и две недели слотов → экран 2 с одной кнопкой «Отправить ученику». Ноль ввода с клавиатуры. Имя берётся из Telegram, фото — из аватара, цены/город/био/телефон отложены до события, которое их делает нужными.

Дальше тренера ведут **семь независимых механик**:

| Поверхность | Где | Триггер | Что говорит |
|---|---|---|---|
| Карточка «следующий шаг» | `trainer_next_step.py` | состояние чеклиста | ровно одна из 5: настроить неделю → обновить слоты → отправить ссылку → (после 5 записей) каталог |
| Ритм-инбокс хаба | `trainer_hub_action_inbox.py` + дубль в `trainer-home-main.js:1501` | счётчики чеклиста | подтвердить записи, заявки, ученики без следующей записи, пустые недели, шаблон, рефералы, заметки |
| Day Canvas | `trainer-home-main.js:634+` | пустой день | «Сегодня свободно» + 3–4 плитки действий |
| Реактивация онбординга | `trainer_onboarding_recovery_use_cases.py` | D+1/D+3/D+7 от привязки | называет, что мешает: пустая анкета / поле / не отправлено / нет записи |
| Обогащение профиля | `trainer_profile_enrichment_use_cases.py` | D+1/D+8/D+21 от первой записи | тарифы и «что не входит», мягко, отменяется при первой цене |
| Care Pulse | `care_pulse_use_cases.py` | тишина, окно 12:00–14:00 | план на завтра / открытые слоты / уснувший клиент / среда |
| Дайджест | `trainer_digest_use_cases.py` | утро + воскресенье | цифры дня и недели |
| Триальная каденция | `notification_loops.py:2101+` | D−2 / D−1 | ROI-рекап и «что выключится завтра» |

То есть каркас есть, и он неплохой. Проблема не в отсутствии механик, а в трёх вещах: **половина каналов выключена именно для новых тренеров**, **обучения фичам не существует как класса**, и **эффективность всего этого не измеряется ничем**.

## 2. Реальные проблемы

### P1 — Утренний дайджест и Care Pulse выключены для всех новых тренеров ⚠️ главная

```sql
-- src/bot/notification_loops.py:2727   (кандидаты дайджеста)
AND t.status = 'active'
-- src/application/care_pulse_use_cases.py:407   (кандидаты care pulse)
WHERE t.status = 'active'
```

После онбординга v2 `trainers.status` означает **«карточка прошла модерацию каталога»**, а не «тренер работает» — это прямо записано в `trainer_access_state.py` и в шапке `trainer_onboarding_checklist.py`. Новый тренер остаётся `pending_profile`, и продукт **специально** не гонит его в каталог раньше 5 реальных записей (`CATALOG_INVITE_MIN_BOOKINGS = 5`, `trainer_next_step.py:22`). В `active` его переводит только админ вручную (`admin_handlers.py:2262`).

Итог: **весь пробный период (14 дней, миграция `0177_welcome_trial_14_days`) тренер не получает ни одного утреннего дайджеста и ни одного care-pulse**. Два из трёх ambient-каналов, которые как раз и создают привычку открывать приложение каждый день, молчат ровно для того сегмента, ради которого они писались. Единственное, что до него доходит, — серия реактивации D+1/3/7, и то только пока у него нет ни одной записи.

Этот же класс бага уже ловили точечно: `TASK-011` завёл серию реактивации именно потому, что «все существующие циклы уведомлений адресованы активным тренерам». Починили один цикл, класс остался.

### P2 — Тренер не видит, что идёт триал

В хабе нет ни слова про пробный период: `grep "пробн|trial"` по `trainer-home-main.js` и `trainer-home.html` даёт один комментарий про песочницу. Полное перечисление того, что открыто, тренер видит **один раз, в день 0**, в `TRAINER_WELCOME_TRIAL_ACTIVATED` (`messages.py:2288`): «CRM, онлайн-запись, абонементы, сертификаты, аналитика и группы». Это худший возможный момент — человек ещё не получил ни одной записи, читает список как рекламу и забывает.

Дальше — тишина до D−2. То есть 11 дней тренер не знает ни что часы идут, ни что он попробовал 2 функции из 6.

### P3 — Обучения фичам не существует как механики

Ни одна из подсказок (`trainer_next_step.py`, `trainer_hub_action_inbox.py`, дайджест, care pulse) **никогда** не упоминает абонементы, сертификаты, группы, постоянных клиентов, статистику, семейный доступ. Полный список ритм-подсказок: `catalog_publication`, `referral_growth`, `open_loop_no_next`, `open_loop_free_next`, `slots_this_week`, `slots_next_week`, `template`, `client_notes`. Всё остальное живёт в шторке «Ещё» — 8 строк с голыми названиями (`mini-app-trainer-shell.js:143-150`), без причины на них нажать. FAQ (10 статей) спрятан ещё глубже — внутрь community-шторки «Развиваем платформу вместе» (`trainer-home.html:520`).

При этом в данных **уже лежат все триггеры**, по которым фича становится очевидно нужной:

| Сигнал (данные есть сейчас) | Что предложить |
|---|---|
| 3+ записи с одним клиентом в одно и то же время, нет строки в `recurring_client_slots` | «Сделать постоянным клиентом» — слот сам бронируется каждую неделю |
| 5+ `completed` с одним клиентом, нет `pass_instances` | Абонемент: занятия спишутся автоматически, остаток видно в карточке |
| 2+ клиента на один слот / услуга с capacity>1 | Группы |
| Первая закрытая неделя с ≥3 занятиями | Статистика: сколько провёл, сколько наличными |
| Первый выданный абонемент | Сертификаты как подарочный сценарий |
| Клиент без Telegram в CRM | Уже есть (`open_loop_no_telegram`) |

Ни один из этих запросов не написан. Это самая большая незанятая площадь: механика доставки готова (инбокс + пуш), не хватает правил.

### P4 — Ритм-подсказки существуют в двух реализациях и уже разъехались

Сервер: `_build_hub_rhythm_inbox_candidates` (`trainer_hub_action_inbox.py:184-400`). Клиент: `buildHubRhythmCandidates` (`trainer-home-main.js:1501-1830`, ~330 строк). Клиентская версия называется «фолбэк», но содержит подсказки, которых на сервере нет (`open_loop_pending`, `open_loop_free_next_growth`) и не содержит гейта, который на сервере есть: реферальная программа на сервере показывается только после первой записи (комментарий на `trainer_hub_action_inbox.py:236-241` прямо объясняет, почему), а в JS она выдаётся сразу, как только есть расписание. Любая правка копирайта или логики требует двух синхронных изменений; сейчас они уже не синхронны.

### P5 — «Не сейчас» живёт в localStorage

`hubRhythmDismissKey` (`trainer-home-main.js:1351`) кладёт отказы в localStorage. Следствия: смена устройства — всё возвращается; сервер не знает, от чего тренер отказался, поэтому пуши не могут это учитывать; ни один отказ не попадает в аналитику. Единственное исключение — приглашение в каталог, для него завели `trainer_profiles.catalog_invite_dismissed_at` (миграция `0182`). Это правильный паттерн, который не распространили на остальные.

### P6 — Эффективность ведения не измеряется ничем

* Воронка активации (`admin_analytics_use_cases.py:1464-1505`) считает `has_first_booking` только для `WHERE status = 'active'` (строка 1483), а весь блок proof-of-value — `WHERE t.status = 'active'`. После v2 это значит: **работающие тренеры в воронку не попадают**, дашборд показывает почти пустоту и уводит решения не туда.
* Телеметрия подсказок начата и брошена на полпути. Показ элементов инбокса трекается (`trainer-home-main.js:2528` → `POST /trainer/hub/inbox-event` → `audit_log("trainer.hub.inbox_item_shown")`), но именно это событие намеренно исключено из записи в БД (`ADMIN_TIMELINE_EXCLUDED_EVENT_TYPES`, `platform_audit_use_cases.py:67-71`) — оно живёт только в лог-потоке. Событий клика и отказа нет вовсе; карточка «следующий шаг» не трекается ничем; события «первое использование фичи» нет. Таблица `platform_audit_events` (миграция `0154`: `event_type`, `trainer_id`, `payload` JSONB, индекс по `(trainer_id, occurred_at)`) и труба до неё уже есть — не хватает событий и решения хранить их.
* Мы буквально не можем ответить: сколько тренеров дошло до первой записи за 24 часа, какая подсказка работает, сколько функций тренер попробовал к концу триала.

### P7 — Остатки старой модели, которые сейчас искажают поведение

* **Три уровня полноты профиля живы** (`trainer_profile_completeness.py`: 11 / 8 / 5 критериев). Формально они больше ничего не блокируют, но `tt_minimal_complete` до сих пор определяет стадию в серии реактивации (`determine_onboarding_stage`), то есть текст пуша зависит от метрики, которую продукт объявил неважной. Пункт #1 роадмапа не закрыт.
* **Песочница жива в коде** (`is_sandbox` в десятках SQL-фильтров, «тест»-пилюли в расписании и хабе, эндпоинт `POST /trainer/clients` с `is_sandbox`), но **точки входа в UI нет**: `hubQuickBookIsSandbox` нигде не присваивается `true` (все 20+ упоминаний — чтения и сбросы в `false`). Мёртвый путь, живая стоимость. Пункт #2 роадмапа не закрыт.
* **`has_any_booking` считает песочницу и отменённые записи** (`trainer_onboarding_checklist.py:313-320` — фильтров нет вовсе). Это флаг, который выключает карточку «отправьте ссылку ученику», включает реферальную подсказку и полностью останавливает серию D+1/3/7 (`trainer_onboarding_recovery_use_cases.py:145` — тот же незафильтрованный `NOT EXISTS`). То есть одна тестовая или сразу отменённая запись гасит всё ведение к первому настоящему клиенту. Рядом, в `real_bookings_count` и в milestone, песочница исключена — правила разъехались внутри одного файла.
* **Две конфликтующие модели доступа.** `trainer_access_state.py`: работать может любой привязанный, кроме деактивированного. `lifecycle_use_cases.py:74`: `LifecycleStage.ONBOARDING → frozenset()` — «ничего операционного», и в ONBOARDING попадает любой `pending_profile`, то есть все новые тренеры. Пока `trainer_can()` используется в двух местах, это не стреляет, но это мина под любую новую поверхность.
* **`LEAD_MODE` недостижим для нового тренера**: он требует `status = 'active'` + видимость в каталоге (`_derive_stage`). Тренер, у которого триал сгорел в `pending_profile`, не получает ни серии восстановления D+0/3/14/30, ни ритм-подсказок (`has_crm_subscription_access is False` → `return out`), ни дайджеста, ни care pulse. Полная тишина после дня 14.

### P8 — Мелкое, но врёт

`TRAINER_LINK_SUCCESS` (`messages.py:2259`) обещает «Чеклист "Первые шаги" — в "Обзор"». Чеклиста нет с переезда на одну карточку `trainer_next_step.py`.

## 3. Что делать — по порядку

### Волна 0. Развести «работает» и «в каталоге» (1–2 дня, максимальный эффект)

Один предикат «живой тренер» = привязан Telegram + не `deactivated` (+ опционально «есть шаблон или слоты»), и заменить им `status = 'active'` в:

1. `notification_loops.py:2727` — кандидаты дайджеста;
2. `care_pulse_use_cases.py:407` — кандидаты care pulse;
3. `admin_analytics_use_cases.py:1483` и блок proof-of-value — иначе воронка продолжит показывать пустоту.

Плюс добавить `NOT is_sandbox AND status NOT IN ('cancelled','declined')` в `has_any_booking` (`trainer_onboarding_checklist.py:313`) и в сегмент реактивации (`trainer_onboarding_recovery_use_cases.py:145`).

Это не новая функциональность — это включение уже написанного для тех, кому оно предназначалось.

### Волна 1. Начать измерять (2–3 дня)

Расширить **существующий** канал `POST /trainer/hub/inbox-event` (`webapp.py:3433`), а не строить новый:

* снять `trainer.hub.inbox_item_shown` с исключения из БД (или писать его в отдельную таблицу, если тревожит объём admin-таймлайна);
* добавить в allowlist `hint_clicked` / `hint_dismissed` и события карточки «следующий шаг» с `payload = {item_id, surface}`;
* `trainer.feature_first_use` с `payload = {feature}` — первый шаблон, первая ссылка, первый абонемент, сертификат, группа, постоянный клиент, открытие статистики;
* перенести dismiss на сервер: таблица `trainer_hint_dismissals (trainer_id, hint_id, until, dismissed_at)` по образцу `catalog_invite_dismissed_at`, и читать её и в хабе, и в пуш-циклах.

Метрики, которые после этого появятся: медиана «привязка → первая настоящая запись»; доля тренеров с ≥2 клиентами на 7-й день; **число функций, тронутых к дню 14** (главная метрика под задачу «умеет пользоваться большей частью»); CTR каждой подсказки.

Без этого шага волна 2 будет очередным набором догадок.

### Волна 2. Движок «фича в момент, когда она нужна» (основная работа)

Один серверный модуль (`trainer_feature_moments.py`) по образцу `trainer_next_step.py`: чистая функция «факты → максимум одна карточка», плюс SQL-сборщик фактов. Правила из таблицы в P3.

Дисциплина, без которой это превратится в спам:
* максимум **одна** обучающая карточка на экране и **не чаще одной в неделю** в боте;
* показывается только когда триггер уже сработал в реальности тренера («у Ани четвёртое занятие подряд» — не «попробуйте абонементы»);
* каждая — один раз; «не сейчас» уважается **на сервере** (волна 1);
* операционные и срочные подсказки всегда важнее обучающих — расширить существующий `HUB_RHYTHM_GROWTH_MAX = 2`, добавив категорию `education` с лимитом 1.

Доставка — уже существующие слоты: `kind: "education"` в инбоксе хаба + редкая «открытка» в бот по образцу `trainer_profile_enrichment_use_cases.py` (готовый шаблон: якорь-событие, шаги D+1/D+8/D+21, cancel-on-progress, идемпотентная таблица).

### Волна 3. Сделать триал видимой дугой (3–5 дней)

* В хабе — тонкая строка «День 5 из 14» и **что уже работает**, а не что не заполнено: «расписание ведётся · 3 записи · ссылка отправлена». Прогресс достижений, не чеклист анкеты.
* D−2 ROI-рекап (`trial_roi_recap_use_cases.py` уже собирает факты) дополнить одной строкой: «Вы ещё не пробовали абонементы — у Ани шестое занятие, их можно было списывать автоматически». Конкретика из его данных, не список модулей.
* Убрать перечисление всех модулей из `TRAINER_WELCOME_TRIAL_ACTIVATED` — в день 0 оно работает против режима работы.

### Волна 4. Один источник правды для подсказок (2–3 дня)

Сервер остаётся единственным местом, где решается, что показать. Клиент рендерит `action_inbox`. Клиентский `buildHubRhythmCandidates` (330 строк) удалить, оставив только состояние загрузки. Иначе всё, что построено в волне 2, придётся писать дважды.

### Волна 5. Догрести старое (по остаточному принципу)

Песочница целиком (пункт #2 роадмапа — путь уже мёртв, осталось вычистить); уровни полноты профиля — оставить один список полей для карточки каталога (пункт #1); привести `LifecycleStage.ONBOARDING` в соответствие с `trainer_access_state`; починить `TRAINER_LINK_SUCCESS`.

## 4. Порядок и почему именно такой

Волна 0 — потому что это самая дешёвая правка с самым большим эффектом: ежедневное присутствие уже написано и просто выключено не тем условием.
Волна 1 — потому что без неё нельзя отличить работающую подсказку от вредной, а обучающих карточек станет вдвое больше.
Волна 2 — собственно то, о чём задача: система, которая ведёт, не принуждая.
Волны 3–5 — усиление и уборка.

Чего делать **не** стоит: добавлять чеклист «заполните профиль на 80%», гнать в каталог раньше реального потока, и присылать обучение по календарю, а не по событию. Всё три уже пробовались в предыдущей модели и были из неё удалены осознанно.
