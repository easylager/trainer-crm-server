# План платежей для B2B-стартапа в Беларуси

Цели:
- **Клиенты** платят через платформу за абонементы и/или разовые занятия.
- **Платформа** автоматически удерживает комиссию (например 2%) и выводит остаток тренеру.
- **Тренерам** выставляются счета за подписку на платформу (месячная/годовая).
- Удобный UX оплаты и прозрачная отчётность.

---

## 1. Модели монетизации

| Направление | Кто платит | Кому | Как считаем |
|-------------|------------|------|-------------|
| **Комиссия с транзакций** | Клиент платит за абонемент/занятие через нас | Платформа берёт % (например 2%), остальное — тренеру | С каждой оплаты клиента |
| **Подписка тренера** | Тренер | Платформа | Фикс за период (месяц/год) или % от оборота |

Рекомендация для старта: **комиссия с транзакций 2–3%** + **подписка тренера** (фикс в BYN/месяц или бесплатно до N транзакций). Так проще объяснить тренерам и считать.

---

## 2. Приём платежей от клиентов (BYN)

### 2.1 Варианты в Беларуси

| Вариант | Плюсы | Минусы |
|---------|--------|--------|
| **bePaid** | Локальная система, карты + ЕРИП, API, есть [split payment](https://docs.bepaid.by/en/payment_management/split/) (разделение платежа маркетплейсом) | Каждый получатель по split должен быть отдельным «магазином» (Shop ID) — усложняет онбординг тренеров |
| **Один эквайринг (платформа)** | Один договор, один интегратор; клиент платит нам; комиссию считаем сами, тренерам — выплаты по реквизитам/договору | Нужен механизм выплат тренерам (см. ниже) |
| **ЕРИП через агрегатора** | Привычно для РБ, можно без карты | Обычно асинхронно (оплата не в реальном времени), нужен callback |

Для B2B-стартапа оптимально: **один договор эквайринга на платформу** (ИП/ООО), приём картой (и при желании ЕРИП). Деньги приходят нам; комиссия платформы и доля тренера считаются в нашей БД; тренерам — выплаты по реквизитам (раз в период) или, при наличии, через API выплат (если провайдер даст).

### 2.2 Схема «клиент платит → мы берём 2% → остальное тренеру»

1. **Одна точка приёма:** все платежи идут на счёт/мерчант платформы (один Shop ID / один договор эквайринга).
2. **В БД храним:**
   - `pass_purchases` / платежи за занятия: сумма, `trainer_id`, комиссия платформы (%), сумма к выплате тренеру.
   - Таблицу **выплат тренерам** (payouts): период, `trainer_id`, начислено, выплачено, статус.
3. **Комиссия:** например 2% от суммы чека. В коде: `platform_fee_cents = round(amount_cents * 0.02)`, `trainer_amount_cents = amount_cents - platform_fee_cents`. Сохраняем в транзакции и в отчётности тренера.
4. **Выплаты тренерам:** по реквизитам (расчётный счёт/карта), раз в неделю/месяц — по данным из нашей БД (накопленная сумма к выплате за период). Вариант «автовыплата» — только если выбранный провайдер (bePaid P2P или банк) даёт API выплат на карту/счёт и это устраивает по комиссиям и регуляторике.

Так можно сделать **без** split в bePaid: один платёж от клиента к нам, мы сами ведём учёт и делаем переводы тренерам. Split имеет смысл подключать, когда будет много тренеров и провайдер позволит «суб-мерчантов» без отдельного договора у каждого.

## 3. Подписка тренера на платформу (реализация + пробный период)

Тренеры пользуются платформой по подписке: без активной подписки — нет каталога, приёма платежей через нас и (по политике) части функций.

### 3.1 Модель данных

- **Тарифы (subscription_plans):** `id`, `name` (например «Месяц», «Год»), `price_cents`, `period_days` (30 / 365), `is_trial` (bool), `sort_order`. Вариант: отдельная запись «Пробный период» с `price_cents = 0`, `period_days = 14`.
- **Подписка тренера (trainer_subscriptions):** `id`, `trainer_id`, `plan_id`, `started_at`, `expires_at`, `status` (см. ниже), `payment_external_id` (если оплата через checkout). Один активный подписной период — одна запись; при продлении — новая запись или продление `expires_at` (зависит от логики).
- **Счета за подписку (trainer_invoices):** `id`, `trainer_id`, `subscription_plan_id`, `amount_cents`, `period_start`, `period_end`, `due_date`, `status` (draft / sent / paid / overdue / cancelled), `paid_at`, `payment_external_id`. Связь: оплата подписки может создавать/обновлять trainer_subscriptions и помечать invoice как paid.

**Статусы подписки:** `trial` — пробный период; `active` — оплаченный период; `past_due` — срок истёк, ожидаем оплату; `cancelled` — отменена (досрочно или не продлена).

### 3.2 Пробный период

- **При регистрации/одобрении тренера** создаём первую подписку с планом «Пробный» (0 BYN, например 14 дней): `started_at = now()`, `expires_at = now() + 14 days`, `status = trial`.
- В боте/кабинете показываем: «Пробный период до DD.MM. После этого — оплата подписки X BYN/мес.»
- За 2–3 дня до `expires_at` — напоминание + кнопка «Оплатить подписку». Если тренер не оплатил к `expires_at`:
  - Переводим подписку в `past_due` (или создаём новую запись с `status = past_due`).
  - Включаем ограничения (см. п. 3.4).
- После первой оплаты платного плана — следующие периоды только платные (пробный один раз на тренера). Флаг `trainer.used_trial = true` или проверка: «была ли уже подписка с plan.is_trial».

### 3.3 Как тренер платит за подписку (B2B, Беларусь)

| Способ | Реализация | UX |
|--------|------------|-----|
| **Счёт на оплату (ЕРИП/банк)** | Генерируем счёт (реквизиты платформы + назначение платежа, при необходимости ЕРИП-код). Отправляем тренеру в боте/email (PDF или ссылка). Тренер платит в банке/приложении. Оплату фиксируем вручную или по webhook/выписке (если банк/агрегатор даёт). | Привычно для ИП/ООО в РБ |
| **Карта в боте (recurring)** | Сохраняем карту (token/alias) через bePaid, списание раз в месяц по подписке. | Удобно, но нужна поддержка recurring у провайдера и согласие тренера |
| **Ссылка на оплату (разовый платёж)** | Каждый месяц отправляем тренеру ссылку на оплату (checkout bePaid на сумму подписки). Тренер платит картой один раз за период. | Проще всего реализовать первым шагом |

Рекомендация для старта: **ежемесячная ссылка на оплату** (разовый платёж за подписку) или **счёт на оплату по реквизитам** (если хотим минимум интеграций). Далее — сохранённая карта и автосписание, когда появится спрос и стабильный поток.

### 3.4 Ограничения при неуплате подписки

При `expires_at < now()` и статус подписки `past_due` (или отсутствие активной записи с `status in (trial, active)`):

- **Каталог:** тренера не показывать в выдаче клиентам (фильтр по «есть активная подписка»).
- **Приём платежей:** не создавать платежи за абонементы/занятия этого тренера (API возвращает ошибку «Подписка не активна»); в Mini App — сообщение «Оплатите подписку, чтобы принимать платежи».
- **Остальное:** запись на занятия, заявки, расписание — по желанию ограничивать (например только просмотр) или оставить, чтобы тренер мог оплатить подписку и продолжить.

Единая проверка в коде: `trainer_has_active_subscription(trainer_id)` — смотрит `trainer_subscriptions` на наличие записи с `expires_at > now()` и `status in ('trial', 'active')`. Эту проверку вызывать перед показом в каталоге и перед созданием платежа от клиента за этого тренера.

### 3.5 Автоматизация подписки

- За N дней до `expires_at` — напоминание в боте + кнопка «Оплатить подписку» (checkout или счёт).
- В день истечения — переход в `past_due` и применение ограничений (cron или фоновая задача).
- В админке: список тренеров с датой окончания подписки, статусом (trial / active / past_due), кнопка «Продлить вручную» (для тестов или исключений).

## 4. Пользовательский интерфейс оплаты

### 4.1 Клиент платит за абонемент/занятие

- **Сценарий:** в Mini App клиент выбирает абонемент или разовое занятие → «Оплатить» → переход на платёжную страницу (hosted checkout bePaid или своя форма с токенизацией карты).
- **UX:**
  - Одна страница/один шаг: сумма, краткое описание (абонемент X у тренера Y / занятие дата–время), способ оплаты (карта / ЕРИП при наличии).
  - После успешной оплаты — редирект в Mini App: «Оплачено. Абонемент в „Мои абонементы“» или «Занятие записано».
  - Чек/подтверждение на email или в боте (опционально).
- **Прозрачность:** на экране до оплаты можно показывать: «Сумма к оплате: X BYN (включая комиссию платформы 2%)» или просто «X BYN» — в зависимости от политики отображения комиссии.

### 4.2 Тренер платит подписку

- В боте: команда/кнопка «Подписка» / «Оплатить подписку» → сообщение с суммой и кнопкой «Оплатить» (Web App или ссылка на checkout).
- Либо письмо/сообщение со счётом: «К оплате X BYN за период с … по …», реквизиты или ссылка на ЕРИП.
- В личном кабинете тренера (если есть): раздел «Подписка», история счетов и оплат, следующий платёж.

### 4.3 Тренер видит свои финансы

- **Личный кабинет / раздел в боте:** «Финансы» или «Выплаты»:
  - Оборот за период (сколько клиенты заплатили через платформу).
  - Удержанная комиссия платформы (2%).
  - Сумма к выплате за период.
  - Статус выплаты (ожидает / выплачено от …) и история.
- Это повышает доверие и снижает вопросы «где мои деньги».

## 5. Отдельный сервис оплаты: имеет ли смысл?

**Кратко:** для текущего этапа (один мерчант, один провайдер, один продукт) **отдельный процесс/микросервис оплаты не обязателен**. Достаточно **чётко выделенного модуля (bounded context)** внутри основного приложения. Отдельный сервис имеет смысл при росте команды, масштабе или регуляторных требованиях.

### 5.1 Вариант A: Модуль оплаты внутри основного приложения (рекомендация на старт)

- Вся логика платежей, подписок и выплат живёт в **том же процессе**, что и API и бот: отдельные пакеты/слои (например `src/billing/` или `src/payment/`, `src/subscription/`), но один деплой, одна БД.
- **Плюсы:** проще разработка и отладка, одна транзакция БД (покупка + pass_instance + учёт выплаты), нет сетевых вызовов между сервисами, один конфиг и один лог. Быстрее выйти в прод и итерировать.
- **Минусы:** код оплаты и доменная логика (каталог, тренеры) в одном репозитории — важно держать границы: основной API вызывает use cases оплаты/подписки, а не лезет в таблицы платежей напрямую.

**Границы в коде:**  
- **Вход:** только через use cases (например `create_pass_purchase_intent`, `handle_payment_webhook`, `get_trainer_payouts`, `check_subscription`).  
- **Выход:** провайдер (bePaid) вызывается из одного адаптера (например `PaymentGateway` interface + bePaid implementation); конфиг (sandbox/prod, ключи) инжектится.  
- Каталог и «можно ли принять платёж за этого тренера» вызывают один метод подписки (`trainer_has_active_subscription`), не смотрят таблицы подписок сами.

Так вы получаете **архитектурную изоляцию** без отдельного процесса.

### 5.2 Вариант B: Отдельный сервис (отдельный процесс, своё API)

- Отдельное приложение (микросервис): свой репозиторий/контейнер, своё API (REST или внутренние события). Основное приложение создаёт «запрос на платёж» → сервис оплаты создаёт сессию у провайдера и возвращает URL; webhook приходит только в сервис оплаты; сервис при успехе шлёт событие/вызов обратно в основное приложение (создать pass_instance, обновить подписку).
- **Плюсы:** изоляция секретов и PCI-зоны, можно масштабировать или переписать платёжную часть отдельно, при аудите «всё платежи в одном сервисе».
- **Минусы:** две БД или общая (сложнее), распределённые транзакции или eventual consistency, отладка по двум логам, задержки и точки отказа сети. Для одного провайдера и одного продукта — избыточно на старте.

**Когда имеет смысл переходить к B:** несколько провайдеров/стран, отдельная команда под платежи, жёсткое требование «платёжный код не в одном процессе с основным приложением», или высокий объём транзакций с отдельным SLA.

### 5.3 Итог

- **Сейчас:** один процесс, изолированный **модуль** (папки, use cases, адаптер к bePaid), чёткие границы вызовов. Отдельное API оплаты в том же процессе допустимо (например префикс `/api/internal/billing` или отдельный router), если хотите явный контракт для фронта/бота.
- **Позже:** при росте — вынос в отдельный сервис без смены контрактов: то, что сейчас вызывается как use case, станет HTTP-вызовом или сообщением в очередь; webhook уже будет только в сервисе оплаты.

## 6. Технические шаги (по приоритету)

### Фаза 1: Приём платежей от клиентов (один мерчант)

1. **Договор эквайринга** (платформа как ИП/ООО): интернет-эквайринг (bePaid или банк), приём в BYN.
2. **Бэкенд:**
   - При создании покупки абонемента/занятия: запись в `pass_purchases` (или аналог для разового занятия) со статусом `pending`, сохранение `amount_cents`, `trainer_id`.
   - API создания платежа: вызов bePaid (или выбранного провайдера) → `payment_url` или checkout session → возврат клиенту.
   - Webhook от провайдера при успешной оплате: обновление статуса в `paid`, расчёт `platform_fee_cents` и `trainer_amount_cents`, создание `pass_instance` для абонемента (как сейчас по логике), при необходимости — создание/обновление записи о выплате тренеру (payouts).
3. **Фронт:** в client-buy-pass (и при оплате разового занятия) вместо «мока» — переход на реальный checkout или отправка на `payment_url`; после возврата по success_url — показ успеха и обновление «Мои абонементы».

### Фаза 2: Учёт комиссии и выплат

4. **Таблица/поля:** в транзакциях (pass_purchases и т.п.) — `platform_fee_cents`, `trainer_amount_cents`; таблица `trainer_payouts`: период, trainer_id, total_earned_cents, platform_fee_total_cents, amount_payable_cents, status (pending / paid), paid_at, payment_details (реквизиты/комментарий).
5. **Отчётность для тренера:** API и экран «Мои выплаты»: оборот, комиссия, к выплате, история.
6. **Выплаты:** процесс (ручной или полуавтомат): по отчёту из БД переводим тренерам на реквизиты; после перевода — проставляем status=paid и paid_at.

### Фаза 3: Подписка тренера

7. **Модель подписки:** таблица тарифов (plan_id, name, price_cents, period_month); таблица подписок тренера (trainer_id, plan_id, started_at, expires_at, status). При регистрации/онбординге — trial или первый период.
8. **Выставление счёта:** раз в период (cron или по событию) генерируем «счёт» (сущность invoice: trainer_id, amount, period, due_date, status). Отправка в бот + при желании email.
9. **Оплата подписки:** вариант A — ссылка на оплату (checkout на сумму подписки, в metadata — invoice_id); вариант B — счёт на оплату по реквизитам (генерация PDF/страницы с реквизитами). Webhook или ручное подтверждение оплаты → продление `expires_at`, смена статуса invoice на paid.
10. **Ограничения при неуплате:** при `expires_at < now()` и статус не продлен — в каталоге не показывать или не принимать платежи за этого тренера до оплаты подписки.

### Фаза 4 (опционально): Split и автовыплаты

11. **Split (bePaid):** если провайдер позволит регистрировать тренеров как суб-мерчантов (или упрощённые Shop ID), можно перейти на split: клиент платит один раз, bePaid сам распределяет на наш счёт (комиссия) и на счета тренеров. Требует уточнения условий у bePaid.
12. **Автовыплаты:** при наличии API выплат (bePaid P2P или банк) — выплата тренеру на карту/счёт по расписанию из нашей БД (сумма к выплате за период).

## 7. Юридические и операционные моменты (Беларусь)

- **Договор с тренером:** оферта/договор, в котором зафиксированы комиссия платформы с транзакций и условия подписки (сумма, период, последствия неуплаты). Желательно согласие на обработку данных и на выплаты (реквизиты).
- **Реквизиты для выплат:** при онбординге тренера собирать реквизиты для перевода (расчётный счёт ИП/ООО или карта для физлица) и хранить в зашифрованном виде; использовать только для выплат по отчёту из системы.
- **Чеки и отчётность:** при необходимости — формирование документов по требованиям РБ (например, при приёме оплаты от физлиц). Уточнить у бухгалтера/юриста под вашу организационно-правовую форму.
- **ЕРИП:** если подключаете приём через ЕРИП (через bePaid или банк), учесть асинхронность: клиент может оплатить позже; логика «бронь на N минут» или «оплата подтверждена по webhook» должна быть явно описана в UX.

## 8. Как тестировать: оплату, комиссию, подписку и пробный период

Чтобы не платить реальные деньги и не трогать прод, всё тестируем в **тестовом (sandbox) окружении** провайдера и на тестовых данных в БД.

### 8.1 Тестовое окружение провайдера (bePaid и аналоги)

- У bePaid (и большинства агрегаторов) есть **sandbox**: отдельный URL API и отдельные Shop ID / ключи. В коде переключаемся через конфиг: `PAYMENT_MODE=sandbox` или `BEPAID_BASE_URL=https://api.sandbox.bepaid.by/` и тестовые ключи.
- В sandbox **деньги не списываются** по-настоящему; транзакции помечаются как тестовые. Webhook’и приходят так же (или с флагом test).
- **Тестовые карты** провайдер даёт в документации (например успешная оплата / отказ / 3DS). Используем их в форме оплаты при прогоне сценариев.

Итог: один раз настроить конфиг на sandbox + тестовые ключи, все сценарии ниже гонять в тесте.

### 8.2 Сценарии тестирования

**A. Оплата абонемента клиентом**

1. В Mini App (или тестовый клиент) выбрать тренера и абонемент, нажать «Оплатить».
2. Убедиться, что создаётся запись в `pass_purchases` со статусом `pending` и уходит запрос в API провайдера (sandbox).
3. Перейти по `payment_url`, оплатить **тестовой картой** (успешный сценарий).
4. Проверить, что провайдер прислал webhook (успех); в БД: статус `paid`, создан `pass_instance`, заполнены `platform_fee_cents` и `trainer_amount_cents` (например 2% и остаток).
5. Проверить, что клиент видит абонемент в «Мои абонементы» и что тренеру в отчёте появилась сумма к выплате.

Повторить с тестовой картой «отказ» — платёж не должен перейти в `paid`, `pass_instance` не создаётся.

**B. Комиссия и выплаты**

1. Сделать несколько тестовых оплат за разных тренеров (в sandbox).
2. В БД или в разделе «Выплаты» проверить: по каждому тренеру сумма оборота, сумма комиссии (2%), сумма к выплате.
3. Проверить формирование отчёта/периода выплат (ручной запуск или cron): список тренеров с суммами к выплате.
4. Отметить выплату как выполненную (status=paid) и проверить, что в интерфейсе тренера отображается «Выплачено за период X».

**C. Подписка тренера и пробный период**

1. **Создание trial при регистрации:** завести тестового тренера (или перевести существующего в «только что одобрен»). Проверить, что создалась запись в `trainer_subscriptions`: plan = пробный, `expires_at` через 14 дней, `status = trial`. Тренер виден в каталоге и может принимать платежи.
2. **Истечение trial без оплаты:** в БД вручную выставить `expires_at` в прошлое и перевести статус в `past_due` (или запустить задачу «проверка истёкших подписок»). Обновить каталог/кэш — тренер не должен отображаться клиентам; при попытке оплаты абонемента у этого тренера — сообщение про подписку.
3. **Оплата подписки:** для тренера с `past_due` открыть «Оплатить подписку» → переход на checkout (sandbox), оплата тестовой картой. Webhook или ручное подтверждение → создаётся invoice paid, подписка продлевается (`expires_at` на месяц вперёд, `status = active`). Проверить, что тренер снова в каталоге и платёж за абонемент возможен.
4. **Напоминание:** за 2–3 дня до `expires_at` — проверить отправку напоминания в боте (ручной запуск джобы или подмена даты в БД для теста).

**D. Webhook без реальной оплаты**

- Если провайдер даёт способ **вручную отправить тестовый webhook** (личный кабинет или утилита) — отправить успешный платёж с нашим `tracking_id` / `purchase_id` и проверить обработку на бэкенде (статус paid, создание pass_instance, комиссия).
- Альтернатива: **локальный туннель** (ngrok и т.д.) на роут webhook и повторная оплата в sandbox — перехватить тело запроса и при необходимости воспроизводить его для отладки.

### 8.3 Чек-лист перед продом

- [ ] Все сценарии выше проходят в sandbox с тестовыми картами.
- [ ] Конфиг прод: только боевые URL и ключи провайдера; нигде не осталось sandbox.
- [ ] Webhook URL в личном кабинете провайдера указывает на прод-сервер; проверена подпись/секрет.
- [ ] Идемпотентность: повторная доставка одного и того же webhook не создаёт дубликаты `pass_instance` и не двойной учёт выплат (проверка по `payment_external_id` / `transaction_id`).
- [ ] Пробный период: лимит «один trial на тренера» работает; после истечения trial ограничения применяются.
- [ ] В проде один-два реальных тестовых платежа (минимальная сумма) с последующим возвратом при необходимости.

## 9. Резюме

| Вопрос | Ответ |
|--------|--------|
| Можно ли брать 2% с каждой оплаты клиента за абонемент/занятие? | Да: клиент платит нам, в БД фиксируем комиссию и сумму тренеру, тренерам платим по реквизитам (или через split, когда онбординг тренеров как мерчантов станет возможен). |
| Как выставлять счета тренерам за подписку? | Счета по реквизитам (ЕРИП/банк) или ежемесячная ссылка на оплату картой (checkout); автоматизация напоминаний и блокировок по дате окончания подписки. |
| Лучший UX оплаты для клиента | Один шаг: выбор абонемента/занятия → «Оплатить» → переход на проверенный checkout (bePaid) с возвратом в приложение и ясным сообщением об успехе. |
| Подписка и пробный период | При регистрации — подписка «Пробный» (0 BYN, 14 дней). После истечения — past_due и ограничения (нет в каталоге, нет приёма платежей). Оплата подписки — ссылка на checkout или счёт; продление — активная подписка снова. |
| Как тестировать? | Sandbox провайдера + тестовые карты; сценарии: оплата абонемента → webhook → комиссия и выплаты; trial → истечение → ограничения → оплата подписки → снятие ограничений. Чек-лист перед продом — в п. 8. |
| Что делать первым делом | Договор эквайринга (платформа) → интеграция создания платежа и webhook → учёт комиссии и сумм к выплате в БД → экран выплат для тренера; модель подписки + пробный период + выставление счёта/ссылки на оплату подписки. |

Документ можно дополнять по мере выбора провайдера (bePaid / банк) и появлении автовыплат или split в продукте.
