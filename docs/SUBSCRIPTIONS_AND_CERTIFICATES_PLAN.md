# План: абонементы и сертификаты (best practices)

Идея: тренер настраивает виртуальные абонементы и цены → клиент покупает абонемент у тренера через платформу → получает сертификат (email + QR) → на занятии тренер сканирует/вводит код и списывает занятие. Позже — отдельные сертификаты (подарочные, разовые). Ниже — архитектура, разделение бот/сайт и пошаговый план.

---

## 1. Цели и принципы

- **Тренерам:** инфраструктура для продажи абонементов и оптовых занятий без ручного учёта.
- **Клиентам:** покупка у конкретного тренера через платформу, один документ (сертификат с QR) вместо «договорились в чате».
- **Платформа:** единый поток выдачи (email + QR) и погашения (сканирование/ввод кода тренером), общий для абонементов и будущих сертификатов.
- **Разделение зон:** бот — уведомления, быстрые действия, точка входа; сайт/Mini App — настройка продуктов, покупка, сканер/погашение; API — единый слой прав и бизнес-логики.

---

## 2. Доменная модель (кратко)

### 2.1. Продукт тренера (что он настраивает)

- **Pass product (абонемент)** — шаблон: «N занятий у меня за цену X».  
  Поля: `trainer_id`, название (например «5 занятий»), `sessions_total` (сколько занятий), `price_cents`, опционально `service_id` (привязка к услуге), `is_active`, сортировка.  
  Хранить в таблице `trainer_pass_products` (или `pass_products`).

- **Позже: Certificate product (сертификат)** — разовый или подарочный продукт (1 занятие, N занятий, фиксированная сумма). Можно обобщить до одной сущности «sellable product» с типом `pass` | `certificate`, но на первом этапе достаточно только абонементов.

### 2.2. Покупка и экземпляр

- **Purchase (покупка)** — факт оплаты клиентом: `client_id`, `trainer_id`, `product_id` (ссылка на pass product), `amount_cents`, `payment_id` (внешняя платёжка), `status` (pending | paid | refunded), `created_at`.  
  Таблица `pass_purchases` (или `purchases` с `product_type = 'pass'` для будущего расширения).

- **Pass instance (экземпляр абонемента)** — то, что клиент «носит» и тренер списывает: `purchase_id`, `client_id`, `trainer_id`, `sessions_total`, `sessions_left`, `product_id` (snapshot названия/услуги на момент покупки), `activated_at`, `expires_at` (опционально).  
  Таблица `pass_instances`.  
  Один purchase → один pass instance (для абонемента). Для сертификата позже может быть 1 purchase → 1 certificate instance.

### 2.3. Погашение (redemption)

- **Redemption (списание занятия)** — одно списание с абонемента: `pass_instance_id`, `trainer_id` (кто списал), `redeemed_at`, опционально `booking_id` (если привязали к конкретной записи), `redemption_code_used` (код/токен из QR).  
  Таблица `pass_redemptions`.  
  При списании: `sessions_left -= 1`, запись в `pass_redemptions`.  
  Для защиты от повторного использования одного и того же QR: код в QR — одноразовый токен (или код + номер списания), при первом погашении помечаем использование.

- **Код/QR:** хранить в `pass_instances` поле `redemption_token` (уникальный, например UUID), по нему находим pass instance. Для каждого списания можно генерировать одноразовый код (например `redemption_token` + nonce или отдельная таблица `redemption_codes`: code, pass_instance_id, used_at). Проще на старте: один долгоживущий QR на абонемент (например ссылка `https://platform.com/r/<token>`), а «списание» — это действие тренера «списать 1 занятие» на странице, открытой по этому QR; защита от дубля — только идемпотентность по (pass_instance_id, booking_id) или лимит по времени (одно списание в минуту с одного токена), либо переход на одноразовые коды позже.

Рекомендация для MVP: один токен на pass instance, страница по QR показывает абонемент и кнопку «Списать одно занятие»; тренер должен быть авторизован (и совпадать с trainer_id абонемента). Защита от случайного двойного нажатия — подтверждение и блокировка кнопки на 5–10 сек после списания.

## 3. Что в боте, что на сайте / Mini App

Следуем [BOT_VS_SITE_SPLIT.md](BOT_VS_SITE_SPLIT.md): бот — уведомления, 1–3 тапа, быстрые действия; сайт/Mini App — каталог, формы, много полей, сканер/страница погашения.

| Функция | Где | Обоснование |
|--------|-----|-------------|
| Настройка абонементов тренером (название, кол-во занятий, цена) | **Сайт или Mini App** | Много полей, список продуктов. Лучше единая точка: либо ЛК тренера на сайте, либо новая страница Mini App «Мои абонементы» (как расписание/заявки). Текущий стиль проекта — многое у тренера в Mini App; логично добавить страницу `trainer-pass-products.html` и кнопку в боте «Абонементы» → Web App. |
| Покупка абонемента клиентом | **Mini App (клиент)** | Аналогично записи: клиент уже в боте, выбор тренера/продукта и оплата в Mini App (`client-buy-pass.html?trainer_id=…`). С сайта можно дать ссылку «Купить абонемент» → тот же Mini App с `trainer_id`. |
| Выдача сертификата (email + QR) | **Бэкенд** | После успешной оплаты: генерация PDF или ссылки на страницу с QR, отправка на email клиента. Без UI в боте/сайте для этого шага. |
| Уведомления о покупке / напоминания по абонементу | **Бот** | Клиенту: «Вы купили абонемент у …», «По абонементу осталось N занятий». Тренеру: «Клиент X купил абонемент». Только в боте. |
| Просмотр своих абонементов клиентом | **Бот + Mini App** | В боте — короткий список «У вас 2 абонемента» + кнопка «Подробнее» → Mini App. В Mini App — список, остаток занятий, QR для предъявления тренеру (или ссылка «Показать тренеру»). |
| Сканирование / погашение (списать занятие) | **Web (страница redeem)** | Тренер сканирует QR клиента или вводит код → открывается **страница** (не обязательно внутри Telegram). На странице: проверка токена, показ абонемента (клиент, остаток), кнопка «Списать одно занятие» (с подтверждением). Тренер должен быть авторизован: при открытии из бота — Web App с initData; при открытии по прямой ссылке с QR — запрос авторизации (например «Открыть в боте» или отдельный login для тренеров). Итог: **одна страница** `redeem.html` (или `trainer-redeem.html`), роут `/webapp/trainer-redeem?token=…` или `/r/<token>` (публичный редирект, затем страница с проверкой). |
| Точка входа «Списать занятие» у тренера | **Бот** | Кнопка в боте «Списать занятие» / «Сканер» открывает Mini App: страница с полем ввода кода или камерой (QR). После скана — переход на ту же страницу погашения с `?token=…`. Так тренер остаётся в Telegram, но логика погашения — на сайте. |

Итог по зонам:

- **Бот (тренер):** уведомления о продажах, кнопка «Абонементы» → Mini App (настройка продуктов), кнопка «Списать занятие» → Mini App (ввод кода / сканер → страница redeem).
- **Бот (клиент):** уведомления о покупке и остатках, кнопка «Мои абонементы» → Mini App (список, QR).
- **Mini App / Web:** настройка продуктов (тренер), покупка (клиент), «Мои абонементы» (клиент), страница погашения (тренер, по QR или из бота).
- **API:** CRUD продуктов, создание покупки, создание pass instance, redemption (списание), отдача данных для списков и для страницы redeem.

## 4. Поток данных (end-to-end)

1. **Тренер** в Mini App создаёт продукт: «5 занятий, 200 BYN», сохраняется в `trainer_pass_products`.
2. **Клиент** в каталоге/карточке тренера или в боте нажимает «Купить абонемент» → Mini App с выбором продукта у этого тренера → оплата (внешняя платёжка; при успехе callback от платёжки вызывает бэкенд).
3. **Бэкенд** при подтверждении оплаты: создаёт `pass_purchases`, создаёт `pass_instance` (sessions_total, sessions_left, redemption_token), формирует сертификат (страница с QR или PDF), отправляет email клиенту. QR ведёт на `https://<webapp_base>/r/<redemption_token>` (или `/webapp/trainer-redeem?token=…`).
4. **Клиент** получает письмо и может открыть «Мои абонементы» в боте → Mini App, видит QR/ссылку для тренера.
5. **Тренер** на занятии: нажимает в боте «Списать занятие» → открывается Mini App (ввод кода или сканер). Либо клиент показывает QR → тренер сканирует камерой телефона → открывается браузер на `/r/<token>`. На странице redeem: если тренер не авторизован — показать «Откройте ссылку из бота» или форму входа; если авторизован (initData с бота или сессия) — показать абонемент и кнопку «Списать одно занятие». По нажатию: API `POST /api/webapp/trainer/redeem` с `token` и (опционально) `booking_id` → создаётся `pass_redemption`, `sessions_left` уменьшается.
6. **Уведомления:** клиенту в боте «С абонемента списано 1 занятие. Осталось N.» (опционально); тренеру при покупке — «Клиент X купил абонемент».

## 5. Сайт vs бот: где что живёт (сводка)

| Роль | Действие | Где |
|------|----------|-----|
| Тренер | Настроить абонементы (название, кол-во, цена) | Mini App (страница «Мои абонементы») |
| Тренер | Уведомление «Клиент X купил абонемент» | Бот |
| Тренер | Списать занятие (сканер / ввод кода) | Mini App или отдельная веб-страница redeem (вход из бота по кнопке или по QR) |
| Клиент | Купить абонемент | Mini App (страница покупки с выбором продукта тренера) |
| Клиент | Уведомление «Вы купили абонемент», «Списано занятие, осталось N» | Бот |
| Клиент | Посмотреть абонементы, показать QR тренеру | Mini App |
| Платформа | Выдача сертификата (email + QR) | Бэкенд (после оплаты) |

Единая точка погашения — веб-страница (redeem); тренер попадает туда из бота (Web App) или по ссылке из QR. Так не дублируется логика и не возникает «каши» между ботом и сайтом.

## 6. Будущие сертификаты

- **Подарочный сертификат:** один продукт «1 занятие» или «N занятий» без привязки к клиенту при покупке; после покупки создаётся certificate instance с токеном, покупатель получает email с QR; тот, кому подарили (или сам покупатель), приходит к тренеру, тренер сканирует — тот же поток redeem (тип сущности: certificate вместо pass, списание одноразовое или N раз по аналогии с абонементом).
- Общая инфраструктура: таблицы `certificate_products`, `certificate_instances`, одна и та же страница redeem и тот же API redemption с типом «pass» или «certificate»; в UI тренера «Списать занятие» обрабатывает оба типа.

Чтобы не раздувать первый этап, в плане ниже — только абонементы; схему БД и API можно сразу заложить с полем `product_type` или отдельными таблицами под сертификаты позже.

## 7. Пошаговый план реализации (абонементы)

### Фаза 1: Модель и настройка продуктов тренером

1. **Миграции и модели**
   - Таблицы: `trainer_pass_products` (trainer_id, name, sessions_total, price_cents, service_id nullable, is_active, sort_order), `pass_purchases` (client_id, trainer_id, product_id, amount_cents, payment_external_id, status), `pass_instances` (purchase_id, client_id, trainer_id, sessions_total, sessions_left, product_snapshot JSONB, redemption_token unique, activated_at, expires_at nullable), `pass_redemptions` (pass_instance_id, trainer_id, redeemed_at, booking_id nullable, redemption_code_used nullable).
   - Модели в `models.py`, при необходимости — репозитории или use cases с raw SQL в стиле текущего проекта.

2. **API (webapp, тренер)**
   - `GET /api/webapp/trainer/pass-products` — список своих продуктов.
   - `POST /api/webapp/trainer/pass-products` — создать продукт.
   - `PATCH /api/webapp/trainer/pass-products/{id}` — изменить (название, кол-во, цену, is_active).
   - `DELETE /api/webapp/trainer/pass-products/{id}` — деактивировать или удалить (с учётом уже купленных).

3. **Mini App: страница «Мои абонементы» (тренер)**
   - `static/webapp/trainer-pass-products.html`: список продуктов, добавление/редактирование (название, количество занятий, цена), авторизация через initData (тренер).
   - В тренерском боте: кнопка «Абонементы» → Web App на эту страницу.

### Фаза 2: Покупка клиентом и выдача сертификата

4. **API (webapp, клиент)**
   - `GET /api/webapp/client/pass-products?trainer_id=…` — список активных продуктов тренера (для выбора при покупке).
   - `POST /api/webapp/client/pass-purchase` — создание покупки (trainer_id, product_id, amount_cents). На первом этапе без реальной платёжки можно эмулировать «оплату» (статус paid после создания) или делать статус pending и отдельный webhook от платёжки.
   - При переходе покупки в paid: создание `pass_instance`, генерация `redemption_token`, отправка email с ссылкой на страницу сертификата (с QR). Страница сертификата: `/webapp/pass-view?token=…` (только просмотр, без списания) — клиент может показать её тренеру или скопировать ссылку; QR ведёт на `/r/<token>` для погашения.

5. **Генерация сертификата и email**
   - Сервис: по `pass_instance_id` сформировать ссылку `https://<base>/r/<redemption_token>` и либо HTML-страницу с QR (библиотека qrcode в бэкенде или генерация на фронте по ссылке), либо PDF. Отправка письма клиенту (существующий или новый механизм отправки email).

6. **Mini App: покупка абонемента (клиент)**
   - Страница `client-buy-pass.html?trainer_id=…`: выбор продукта тренера, отображение цены, кнопка «Оплатить» (пока заглушка или интеграция с платёжкой). После успеха — сообщение «Абонемент куплен, на почту придёт сертификат» и кнопка «Мои абонементы».

7. **Mini App: «Мои абонементы» (клиент)**
   - `client-passes.html`: список pass instances (тренер, название, осталось N из M), по тапу — экран с QR или ссылкой «Показать тренеру». В боте — кнопка «Мои абонементы» → Web App.

### Фаза 3: Погашение (списание занятия)

8. **Публичный редирект и страница redeem**
   - Роут `GET /r/<token>` — редирект на `/webapp/trainer-redeem?token=<token>` (чтобы QR вел на короткий URL).
   - Страница `trainer-redeem.html`: по `token` запрос к API `GET /api/webapp/redeem/info?token=…` (публичный или с ограничением по rate limit) — возвращает минимальную инфу для отображения (название продукта, остаток, имя клиента без персональных данных при необходимости). Если тренер не авторизован — показать «Откройте эту ссылку из бота тренера (кнопка «Списать занятие»)» или форму входа. Если авторизован (initData от тренерского бота) — проверить, что trainer_id абонемента совпадает с текущим тренером, показать кнопку «Списать одно занятие».

9. **API погашения**
   - `POST /api/webapp/trainer/redeem` — body `{ "token": "<redemption_token>", "booking_id": null }`. Проверка: токен валиден, pass_instance.sessions_left > 0, текущий пользователь — тренер и совпадает с pass_instance.trainer_id. Создать запись в `pass_redemptions`, уменьшить `sessions_left`. Ответ — обновлённый остаток.

10. **Точка входа в боте у тренера**
    - Кнопка «Списать занятие» в меню или в разделе «Записи»: открывает Mini App `trainer-redeem.html` без token (экран ввода кода или сканер QR). После ввода/скана — переход на ту же страницу с `?token=…`.

11. **Уведомления**
    - Клиенту (бот): при покупке — «Вы купили абонемент «…» у тренера …»; при списании — «По вашему абонементу списано 1 занятие. Осталось N.» (опционально).
    - Тренеру (бот): при покупке — «Клиент … купил абонемент «…»».

### Фаза 4 (опционально): привязка к записи и оплата

12. При создании записи (booking) дать возможность «оплатить абонементом» (выбор своего pass instance у этого тренера); при подтверждении тренером или при «отметке проведено» — автоматически списать одно занятие и привязать redemption к booking_id.
13. Интеграция реальной платёжки: webhook при успешной оплате переводит покупку в paid и запускает создание pass instance и отправку email.

## 8. Риски и упрощения

- **Оплата:** пока в проекте нет платёжки; на первом этапе можно сделать «тестовую оплату» (кнопка «Оплатить» сразу переводит в paid) или заглушку с ручным подтверждением в админке.
- **QR:** один токен на абонемент — проще; при необходимости позже введём одноразовые коды для каждого списания (отдельная таблица кодов, при погашении код помечается использованным).
- **Права:** страница redeem по публичной ссылке не должна раскрывать личные данные клиента сверх необходимого (имя, название продукта, остаток); списание разрешено только авторизованному тренеру этого абонемента.

Этот план даёт чёткое разделение: бот — уведомления и точки входа, сайт/Mini App — настройка, покупка, просмотр и погашение, API — единая логика и права; сертификаты позже вписываются в ту же схему redeem и продуктов.
