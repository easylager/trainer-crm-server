# Анализ проекта и план продукта: CRM для тренеров

> Анализ текущего состояния трёх ботов и дорожная карта до продаваемого продукта.

---

## 1. Текущая архитектура (три бота в связке)

| Бот | Роль | Точка входа | Основной функционал |
|-----|------|-------------|----------------------|
| **Клиентский** | Публичный | `/start` или deep link с сайта | Каталог (город → услуга → арена → тренеры), запись на слот, «мои записи», заявка «не нашёл тренера», отзывы/рейтинг, напоминания 24ч/2ч, уведомление об отмене |
| **Тренерский** | Только тренеры | `?start=link_<token>` с сайта | Привязка по токену, расписание (шаблоны + слоты), список записей (подтвердить/отклонить, написать, отменить), отклики на заявки, уведомления о новых записях/заявках, «занятие прошло» → запрос отзыва |
| **Админский** | Только `admin_telegram_ids` | Отдельный токен | `/pending` — очередь тренеров на модерацию: Одобрить / Отклонить / Нужны правки (фидбек в БД, показ на сайте в ЛК) |

**Связка:** Сайт создаёт тренера и после оплаты выдаёт ссылку на тренерского бота. Клиент ищет тренера в каталоге (через бота или с сайта по deep link), записывается; тренер подтверждает в боте. Админ модерирует карточки тренеров. Общая БД (PostgreSQL), API (FastAPI), S3 для фото.

## 2. Чего не хватает для полноценной CRM

### 2.1 Клиент как сущность (база CRM)

**Реализовано в продукте:**
- Таблица **`clients`**, связи с записями и заявками; приватные заметки — **`trainer_client_notes`** (API: `GET/POST /api/webapp/trainer/clients/...`).
- **Мини-приложение «Обзор»** (`/webapp/trainer-home`): хаб с ближайшими записями и плитками переходов в расписание, клиентов, заявки и др.; команда бота `/home`, кнопка в приветствии после привязки (HTTPS).
- **Мини-приложение «Мои клиенты»** (`/webapp/trainer-clients`): список клиентов с записями к тренеру, поиск, карточка с историей занятий, следующей записью, заметкой, переход к выдаче абонемента и к записи в расписание.
- **Тариф CRM:** команда `/clients` и раздел в меню открывают этот экран; без подписки CRM раздел недоступен.
- **Связность с ботом (UX):** после автоматического «занятие завершено» — кнопка Web App «Карточка и заметка» с `?client_id=`; в детали записи в чат-режиме — кнопка в карточку клиента; deep link `trainer-clients?client_id=` открывает сразу карточку; переход «Записать» из CRM ведёт на `schedule-editor?client_id=` с предвыбором клиента при выборе слота.

**Опционально позже:** отдельный экран «Мои клиенты» вне Telegram (веб-ЛК), экспорт базы, массовые рассылки.

### 2.2 Отчёты и аналитика

**Базово в боте:** список записей; расширенная статистика — по команде `/stats` (см. ниже).

**Реализовано (статистика):**
- **Для тренера:** команда `/stats` в меню («Статистика»): занятия за эту неделю (проведено / предстоит) и за месяц, загрузка расписания (слотов/занято %), новые клиенты за 30 дней, рейтинг. См. `src/application/stats_use_cases.py`, хендлер в тренерском боте.
- **Для админа:** команда `/stats`: тренеры по статусам, записей за 30 дней, заявок за 30 дней (и в работе). См. хендлер в админ-боте.

**Опционально позже:** конверсия заявка→запись, экспорт в ЛК.

### 2.3 Монетизация и юридическая база

**Сейчас:** В плане, но не реализовано (PROJECT_PLAN 1.3, 1.4):
- **Соглашение (B2B):** текст соглашения, показ тренеру, «Я согласен» + фиксация (audit). Нужно для продажи как продукта.
- **Оплата подписки:** тарифы в БД, интеграция с платежами (ЕРИП/ЮKassa/Stripe), активация тренера после оплаты, напоминание об окончании подписки, ограничение функционала при неоплате.

Без этого нельзя уверенно «продавать» продукт: нет ни денежного контура, ни юридической основы.

### 2.4 Админка за пределами модерации

**Сейчас:** Админ-бот только модерация тренеров (`/pending`). Справочники (города, арены, услуги) — сиды/БД; управление ими не в ботах.

**Не хватает:**
- Управление справочниками: добавление/редактирование городов, арен, услуг (в админ-боте или отдельном API/сайте).
- Просмотр платформенной статистики (тренеры, записи, заявки) — см. п. 2.2.
- При инцидентах: возможность «заморозить» тренера или отключить запись (частично есть через статус, но без отдельного runbook для админа).

### 2.5 Производственная готовность

По PROJECT_PLAN и PRODUCTION_PLAN:
- **CI:** тесты есть; нет pre-commit, полноценного lint/typecheck, проверки миграций в CI.
- **Деплой:** нет Dockerfile / docker-compose.prod, нет описанного деплоя на выбранную платформу.
- **Резервирование БД** (3.2.4) — не настроено.
- **Runbook и документация:** процедуры есть в PRODUCTION_PLAN; отдельный RUNBOOK.md и пользовательские инструкции для тренеров/клиентов — не оформлены.
- **Аудит в БД:** опциональная таблица `audit_events` не реализована (логи в stdout есть).

Для продажи продукта нужен предсказуемый деплой, бэкапы и ясные действия при сбоях.

### 2.6 UX и инструкции

По BOTS_UX_AND_INSTRUCTIONS_PLAN: стартовые кнопки у тренера, `/help` у обоих ботов, fallback с кнопками, вынос строк ошибок в `messages.py` — частично или в плане. Для продажи важно: стабильный UX и короткая инструкция «как пользоваться» (текст + при желании картинка).

### 2.7 Прочее из плана

- Загрузка диплома/сертификата (1.2.6) — опционально для первого коммерческого релиза.
- Unit-тесты domain/application (3.3.1), E2E критичных сценариев — повышают уверенность при изменениях и при продаже «качественного продукта».

## 3. Сводка: что есть vs чего не хватает

| Область | Есть | Не хватает |
|--------|------|------------|
| **Клиент** | Сущность `clients`, карточка в Mini App, история у тренера, заметки, deep link из бота | Расширенная CRM (массовые действия, веб-ЛК вне Telegram) — по продуктовым приоритетам |
| **Записи** | Создание, подтверждение, отмена, напоминания, отмена-уведомление, «прошло» + отзыв | — |
| **Тренер** | Профиль, расписание, записи, заявки, рейтинг, `/stats` (занятия, загрузка, новые клиенты) | Дашборды уровня BI — опционально |
| **Каталог** | Города, арены, услуги, тренеры с рейтингом | Админское управление справочниками |
| **Модерация** | Очередь, одобрить/отклонить/правки, фидбек в БД | — |
| **Деньги и право** | — | Соглашение, подписка, платежи, напоминания |
| **Аналитика** | `/stats` тренер и админ, Mini App `trainer-stats` при тарифе | Расширенные отчёты и экспорт — опционально |
| **Продакшен** | Health, audit в лог, rate limit | CI (lint, миграции), Docker, деплой, бэкапы, Runbook |
| **Документация** | Планы в docs/ | Runbook, пользовательские инструкции, API/ER для партнёров |

## 4. План: как сделать мощный продаваемый продукт

### 4.1 Целевой образ продукта

- **Название/позиция:** CRM для тренеров (Беларусь), Telegram-first: запись клиентов, расписание, клиентская база, рейтинг, модерация, монетизация по подписке.
- **Целевые пользователи:** тренеры (подписка), клиенты (бесплатно), админ платформы.
- **Ценность:** тренер получает один канал для записей, напоминаний, отзывов и базовой статистики; платформа — контроль качества (модерация) и доход с подписок.

### 4.2 Фазы до и после старта продаж

#### Фаза A: «Продукт готов к оплате» (must-have перед продажей)

1. **Юридическая база**
   - Хранение текста соглашения (версии в БД).
   - Показ тренеру (сайт/бот) и фиксация согласия (чекбокс + timestamp, audit).

2. **Платежи и подписка**
   - Тарифы в БД (месяц/квартал/год).
   - Интеграция с одной платёжной системой (ЕРИП / ЮKassa / Stripe — под юрисдикцию).
   - После успешной оплаты: активация тренера, выдача ссылки на бота (как сейчас по токену).
   - Напоминание об окончании подписки (за N дней).
   - Ограничение функционала при неоплаченной подписке (например, только просмотр, без новых слотов).

3. **Клиент как сущность (минимум для CRM)**
   - Таблица/модель Client (telegram_id, имя, телефон; опционально первый визит).
   - При первой записи — создание/обновление клиента; при повторной — связь с тем же клиентом.
   - В тренерском боте: по выбранной записи показывать «этот же клиент записывался N раз» (история к этому тренеру). Опционально: экран «Мои клиенты» с краткой историей.

4. **Минимальная аналитика**
   - Тренер: в боте команда или раздел «Статистика»: занятий за текущую/прошлую неделю (или месяц), сколько слотов занято.
   - Админ: в админ-боте или отдельном отчёте: кол-во тренеров по статусам, записей за период (например, за месяц).

5. **Продакшен**
   - CI: тесты + проверка миграций (и при возможности lint) на каждый PR.
   - Dockerfile + docker-compose (или аналог) для API и трёх ботов; деплой на выбранную платформу; секреты из окружения.
   - Резервное копирование БД по расписанию и проверка восстановления.
   - Краткий RUNBOOK: деплой, откат, типовые инциденты (API 503, бот не отвечает, миграции).
   - Алерты при падении сервисов или /health 503.

6. **UX и инструкции**
   - Реализовать пункты из BOTS_UX_AND_INSTRUCTIONS_PLAN: старт с кнопками (клиент + тренер), /help с текстом «как пользоваться», fallback с кнопками.
   - Вынести оставшиеся жёсткие строки в `messages.py`.

После фазы A продукт можно **начинать продавать**: есть оплата, соглашение, базовая CRM по клиентам, цифры для тренера и админа, предсказуемый деплой.

#### Фаза B: «Сильный продукт» (следующие 2–3 месяца)

1. **Расширенная CRM для тренера**
   - Заметки по клиенту (короткое поле в боте после занятия или в списке записей).
   - Экран «Мои клиенты»: список с количеством занятий и последним визитом.

2. **Админка**
   - Управление справочниками (города, арены, услуги) через админ-бот или отдельный API для будущего сайта.
   - Дашборд/отчёт: тренеры, записи, заявки за период (можно в боте или в отдельном простом веб-интерфейсе).

3. **Качество и доверие**
   - Таблица `audit_events` в БД + запись ключевых событий (по AUDIT_LOGGING_PLAN) для разбора и отчётности.
   - Unit-тесты для domain/application; 1–2 E2E сценария (запись → подтверждение → напоминание или отмена).

4. **Документация**
   - Пользовательские инструкции (PDF или страница на сайте): для тренеров, для клиентов.
   - API/ER диаграмма для партнёров или интеграций (если планируется кабинет на сайте).

5. **Опционально**
   - Загрузка диплома/сертификата в карточку тренера.
   - Расширение тарифов (например, лимиты на количество «активных» слотов или клиентов).

#### Фаза C: Масштаб и новые каналы

- Сайт/ЛК тренера: дублирование ключевых действий (расписание, записи, статистика) с бота на веб.
- Маркетинг: лендинг, кейсы, онбординг новых тренеров.
- При необходимости: мобильное приложение (как в PROJECT_PLAN Phase 2) или расширение географии.

### 4.3 Приоритеты (кратко)

| Приоритет | Что делать |
|-----------|------------|
| 1 | Соглашение + платежи/подписка + ограничение при неоплате |
| 2 | Клиент как сущность + история у тренера (хотя бы «N записей у тебя») |
| 3 | Минимальная статистика (тренер + админ) + продакшен (CI, Docker, деплой, бэкапы, Runbook) |
| 4 | UX/инструкции (кнопки, /help, fallback) |
| 5 | Заметки по клиенту, «Мои клиенты», админские справочники, audit_events, тесты |

### 4.4 Оценка по времени (ориентир)

- **Фаза A:** 4–8 недель (1 разработчик full-time), в зависимости от выбора платёжки и объёма доработок сайта (если сайт в другом репо).
- **Фаза B:** 4–6 недель.
- **Фаза C:** по мере спроса и ресурсов.

## 5. Связь с существующими документами

- **PROJECT_PLAN.md** — чеклисты 1.3 (соглашение), 1.4 (оплата), 3.2.4 (бэкапы), 3.4 (документация) и раздел 4 (боевой режим) остаются актуальными; данный документ уточняет приоритеты для продажи.
- **docs/PRODUCTION_PLAN.md** — базовый процесс деплоя, отката и мониторинга; фаза A включает его выполнение.
- **docs/BOTS_UX_AND_INSTRUCTIONS_PLAN.md** — задачи по кнопкам, /help, fallback и инструкциям входят в фазу A.
- **docs/AUDIT_LOGGING_PLAN.md** — расширение до таблицы `audit_events` отнесено к фазе B.

После закрытия фазы A систему можно позиционировать как **готовый к продаже продукт**: CRM для тренеров с записью, отслеживанием клиентов и монетизацией по подписке, с юридической основой и эксплуатационной готовностью.
