# Каталог как отдельный раздел: прозрачный жизненный цикл публикации

Дата: 2026-09-27
Статус: дизайн одобрен, план реализации не создан

## Проблема

Управление публикацией в каталоге живёт тумблером `is_catalog_visible` в «Настройках» экрана «Профиль». Экран «Профиль» совмещает три роли: рабочие данные (телефон, окно записи), витрину для каталога и статус модерации. Самое публичное решение тренера спрятано глубже всего.

Аудит текущего поведения нашёл три пути, по которым тренер выпадает из каталога **без единого уведомления**:

1. **Авто-демоушен.** `_demote_status_if_profile_incomplete` (`src/application/trainer_use_cases.py:179`) на каждом PATCH профиля/услуг/арен/образования проверяет 8 критериев публикации и при провале сбрасывает `active → pending_profile`. Вся реакция — `logger.info` (:197). Для активного тренера срабатывает на: стирании телефона, обнулении города, удалении последней услуги или арены, выходе длительности занятия / окна записи за границы. Тренер получает `{"ok": true}` и узнаёт о выпадении только если снова откроет экран «Анкета».

2. **Скрытые площадки.** `PATCH /trainer/arenas/{id}/public` (`src/api/routes/webapp.py:1223`) не меняет статус, потому что агрегат `arena_ids` содержит и приватные строки (`trainer_repository.py:611`). Скрыв все площадки, тренер остаётся `active + is_catalog_visible`, тумблер горит, хинт говорит «Клиенты находят вас в общем списке» (`trainer-profile-main.js:3810`) — но каталог с фильтром по арене требует `ta.is_public = true` (:1358), а триггер `trg_trainer_cities_arena` (`migrations/versions/0197_trainer_cities.py:117`) выбрасывает арендованные города из `trainer_cities`. Тренер исчезает из арена- и город-фильтров, оставаясь в общем списке.

3. **Пустой фидбек модератора.** `on_admin_message` (`src/bot/handlers/admin_handlers.py:2464`) висит на `@router.message()` без фильтра по типу. Нетекстовое сообщение в момент ожидания правок даёт `text = ""` → pending-тренер демоутится, у active откатывается черновик, пуш не отправляется (:2601 требует непустой текст).

Плюс два системных изъяна:

- **Возврат требует ручного ресабмита.** Повторная заявка уходит только через `POST /trainer/onboarding/submit-for-moderation`, а вызывают его три места: сохранение анкеты, включение тумблера, REST. Если полнота восстановилась другой поверхностью, тренер стоит в `pending_profile` с полной анкетой и пустой очередью, пока не зайдёт в «Анкету» и не нажмёт «Сохранить».
- **`status` перегружен.** Один и тот же `pending_profile` означает и «новичок не дозаполнился», и «работающий тренер стёр телефон». При этом `trainers.status` уже почти чистый флаг каталога: доступ к инструментам давно живёт на `TrainerAccessState`, и это зафиксировано в коде — `src/api/routes/webapp.py:3604`: «`is_active` = listed in the public catalog (moderation passed). It no longer gates the trainer's own tools».

## Принятые решения

| Решение | Выбор | Отклонённые варианты |
|---|---|---|
| Содержание карточки | **Линза на анкету.** Раздел «Каталог» отвечает за публикацию, состояние и превью; контент берётся из существующих полей профиля | Отдельная сущность объявления со своими полями (вторая правда о тренере); гибрид с блоком «оффер» |
| Место в навигации | **Постоянная 5-я вкладка нижнего бара**, четвёртой по порядку, перед «Ещё» | Появление после онбординга (бар меняется под ногами); пункт в шторке «Ещё» (сохраняет исходную проблему) |
| Модель состояния | **Явный `catalog_state` + журнал событий**, отвязанный от `trainers.status` | Только журнал и уведомления поверх текущих полей; отдельный listing со снапшотом (отложил бы и цены с площадками) |
| Мобильный формат | Оставляем как есть: submission tier требует ≥1 арену, тренер «выезжаю к клиенту» в каталог не попадает. Отдельная задача | — |
| Порог приглашения в хабе | **1 реальная запись** вместо 5 | — |
| Отмена правок тренером | **Даём.** Серверная часть существует (`discard_active_trainer_text_revision_with_feedback`), сегодня её дёргает только модератор | — |

## Машина состояний

Одно поле `catalog_state`, шесть значений, у каждого ровно одна фраза для тренера.

| Состояние | Фраза на экране | В каталоге |
|---|---|---|
| `draft` | «Вас пока нет в каталоге» | нет |
| `pending_review` | «На проверке — обычно отвечаем в течение рабочего дня» | нет |
| `published` | «В каталоге — клиенты вас находят» | **да** |
| `hidden` | «Снято вами <дата>» | нет |
| `paused` | «Приостановлено: <причина>» | нет |
| `needs_revision` | «Модератор попросил поправить: <комментарий>» | нет |

Имя `needs_revision`, а не `rejected`: в продукте нет «отказано навсегда». Админ-бот различает «Нужны правки» (комментарий, карточка ждёт исправлений) и «Отклонить» — второе есть деактивация аккаунта и для активных запрещено (`admin_handlers.py:2306`). Жёсткий отказ остаётся событием уровня аккаунта: `status = deactivated` → каталог уходит в `draft`.

Правки уже опубликованной карточки — **не состояние**, а признак поверх него: `published` + «правки на проверке». Карточка остаётся в каталоге со старыми значениями. Иначе любая опечатка выбивала бы тренера из выдачи на сутки.

### Переходы

| Из → В | Причина | Как тренер узнаёт |
|---|---|---|
| `draft` → `pending_review` | тренер нажал «Отправить на проверку» | экран меняется под рукой |
| `pending_review` → `published` | модератор одобрил | пуш «Вы в каталоге» + журнал |
| `pending_review` → `needs_revision` | модератор попросил правки | пуш с комментарием + баннер с кнопкой |
| `pending_review` → `draft` | тренер отменил заявку | журнал |
| `published` → `hidden` | тренер снял | диалог подтверждения + журнал |
| `hidden` → `published` | тренер вернул | **мгновенно, без модерации** — карточку уже проверяли, контент не менялся |
| `published` → `paused` | система: пропал обязательный признак | пуш с точной причиной + жёлтый баннер + точка на вкладке |
| `paused` → `published` | признак восстановлен, контент не менялся | автоматически, без модерации, пуш «карточка снова в каталоге» |
| `paused` → `pending_review` | признак восстановлен, но менялся текст или фото | на проверку, с объяснением почему |
| любое → `draft` | аккаунт `deactivated` | пуш |

### Два инварианта

**Из каталога нельзя выпасть молча.** Единственный способ изменить состояние — `set_catalog_state(trainer_id, state, reason, actor)`, которая в одной транзакции пишет строку в `trainer_catalog_events` и ставит уведомление. Прямой `UPDATE` колонки запрещён и проверяется тестом.

**Возврат не требует модерации, если опубликованный контент не менялся.** Восстановление телефона возвращает карточку само: проверять нечего, модератор это уже видел.

### Что перестаёт происходить

Неполная карточка **не роняет аккаунт** в `pending_profile` — в `paused` уходит только карточка. `status` возвращается к смыслу «состояние аккаунта» и становится липкой вехой «прошёл модерацию»: одобрение по-прежнему ставит `active` (на ней висят аналитика `admin_analytics_use_cases.py:1491` и создание триала), но назад её никто автоматически не откатывает.

### Мягкие предупреждения — отдельный слой

Не всё, что мешает находиться, должно снимать с публикации. Скрытые площадки в `paused` **не** переводим: тренер всё ещё в общем списке и в фильтре по городу, падает только фильтр по арене. У экрана два независимых слоя: одно состояние и список ненавязчивых предупреждений с ссылкой на исправление.

### Не тренер

Модератор, админ через REST (`src/api/routes/trainers.py:222`) и студия (для `studio_access_mode = admin_only`) меняют состояние той же функцией — значит, с автором в журнале. Тренер студии видит экран в режиме чтения: «Публикацией управляет <студия>», состояние и история видны, кнопок нет.

## Экран

### Вкладка

Бар: `Главная · Расписание · Клиенты · Каталог · Ещё`. Точка-индикатор только когда нужно действие тренера: `paused`, `needs_revision`. На `pending_review` точки нет — ждём мы, а не он.

### Первое знакомство: три канала, ни один не единственный

1. **Вкладка с первого дня.** Тренер узнаёт о каталоге из навигации, а не из хинта, который можно смахнуть. Пустое состояние объясняет, что это: список, который смотрят новые ученики; что даёт размещение; что карточку один раз проверяет модератор. Кнопка «Разместить карточку» и ссылка «Сначала посмотреть, как выйдет» — превью из того, что уже заполнено, снимает страх «опубликуется что-то кривое».
2. **Хаб — приглашение.** Порог 5 реальных записей (`trainer_next_step.py:17`) снижается до 1: с постоянной вкладкой каталог больше не давит, и обе существующие ветки (`ACTION_ENABLE_CATALOG`, `ACTION_OPEN_CATALOG_PROFILE`) сливаются в одну `ACTION_OPEN_CATALOG`, ведущую на вкладку.
3. **Мягкие пуши D+1/D+8/D+21** меняют адресата с профиля на раздел «Каталог». Новых пушей на старте не добавляем.

### Размещение: карусель не переносим

У карусели уже есть механизм возврата — `focusedTaskReturnUrl()` (`static/webapp/trainer-profile-main.js:2771`), и он отдельно обрабатывает `task=catalog`. «Разместить карточку» делает `navigate('trainer-profile?task=catalog&return=trainer-catalog')`: визард открывается поверх профиля в фокус-режиме, рельс собирается из `missing_fields` (`PROFILE_FOCUSED_TASKS` + `OB_FLOW_STEP_DEFS`, :2528/:2591 — они уже покрывают все 8 критериев), по завершении возвращает на «Каталог». Ноль переносов DOM-блоков.

Меняется одно: последняя кнопка визарда — «К предпросмотру», а не «Готово». Публикация не должна быть побочным эффектом сохранения поля.

```
Каталог (draft) → «Разместить карточку»
   → карусель: только пропущенное → «К предпросмотру»
   → Каталог: превью + «Отправить на проверку»
   → pending_review
```

Если пробелов нет — карусель пропускается, сразу превью.

### Экран подтверждения

Превью строки каталога + «Открыть карточку целиком». Ниже два **визуально разведённых** списка: «Готово к проверке» (галочки по 8 обязательным) и «Можно усилить — необязательно» (описание, образование). Сегодня на экране «Профиль» оба списка идут одним потоком и тренер не понимает, что блокирует публикацию.

### Опубликованное состояние

Состояние и дата · превью карточки · «Открыть как клиент» · метрики за 7 дней · мягкие предупреждения · «Изменить карточку» с объяснением, что проходит проверку, а что применяется сразу · «История изменений» · строка про подписку · «Снять с публикации» текстовой ссылкой внизу (деструктивное и редкое не должно конкурировать по весу с «Изменить»).

Метрики — ровно те, что уже считаются (`static/webapp/trainer-stats-main.js:135`): просмотры профиля, переходы в Telegram, сейчас в избранном. Ничего нового не выдумываем.

Строка про подписку — прямым текстом: «Подписка на каталог не влияет: если она закончится, карточка останется, отключится только самозапись». Это уже правда в коде (`trainer_repository.py:1329`), но нигде не сказана, а страх «не заплатил → пропал» стоит дорого.

### Остальные состояния

`paused` и `needs_revision` дают кнопку, запускающую ту же карусель: для `paused` рельс из пропавших признаков, для `needs_revision` — анкета целиком с повторённым комментарием модератора над формой (свободный текст модератора нельзя разложить по полям, и притворяться, что можно, хуже, чем честно открыть анкету).

`hidden`: «Запись по вашей ссылке работает как обычно. Вернём сразу, без проверки».

### Диалог снятия

Две группы прямым текстом. **Изменится:** вас не будет в списке и фильтрах; новые заявки из каталога перестанут приходить. **Не изменится:** запись по вашей ссылке; уже назначенные занятия; клиенты, абонементы, история. И вывод: «Вернуть можно в один тап, без повторной проверки».

### История

Журнал `trainer_catalog_events` как простой список — ответ на «как следить, что я в каталоге»: дата, что произошло, причина, кто сделал.

### Что уезжает с экрана «Профиль»

Тумблер `is_catalog_visible`, пилюля статуса, `modHint` со списком недостающих полей, баннер фидбека модератора. Подпись в шторке «Ещё» меняется с «Анкета, услуги и модерация» на «Анкета, услуги и настройки».

Остаётся одно: над блоками, видимыми клиенту, короткая строка «Эти поля показываются в каталоге → Каталог». Иначе тренер правит имя и не понимает, что правит публичную карточку.

## Данные

Миграция `0206_trainer_catalog_state` (последняя занятая — 0205):

```sql
ALTER TABLE trainers
  ADD COLUMN catalog_state varchar(24) NOT NULL DEFAULT 'draft',
  ADD COLUMN catalog_state_reason varchar(64),
  ADD COLUMN catalog_state_changed_at timestamptz;

CREATE TABLE trainer_catalog_events (
  id            bigserial PRIMARY KEY,
  trainer_id    int NOT NULL REFERENCES trainers(id) ON DELETE CASCADE,
  from_state    varchar(24),
  to_state      varchar(24) NOT NULL,
  reason        varchar(64),   -- missing_phone | moderator_revision | trainer_hidden | ...
  reason_detail text,          -- комментарий модератора либо список пропавших признаков
  actor_type    varchar(16) NOT NULL,  -- trainer | moderator | system | studio | api
  actor_id      varchar(32),
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ix_trainer_catalog_events_trainer
  ON trainer_catalog_events (trainer_id, created_at DESC);
```

`reason` — машинный код для тестов и аналитики, `reason_detail` — человеческий текст для экрана и пуша. Разделение нужно, чтобы UI не парсил строки.

### Backfill

| Сейчас | Становится |
|---|---|
| `active` + `is_catalog_visible` | `published` |
| `active` + не видим | `hidden` |
| `pending_*` + видим + есть `moderation_submitted_at`, фидбека нет | `pending_review` |
| `pending_profile` + непустой `moderation_feedback` | `needs_revision` |
| остальные `pending_*` | `draft` |
| `deactivated` | `draft` |

`active` + не видим → именно `hidden`, а не `draft`: статус `active` можно получить только через одобрение модератора, значит карточку уже проверяли и повторная проверка ей не нужна. Так этот тренер получает работающую в один тап кнопку «Вернуть в каталог».

### Один гейт вместо одиннадцати

Публичное условие становится `t.catalog_state = 'published'` — одна константа `CATALOG_LISTED_SQL` и один Python-предикат вместо продублированного `status='active' AND is_catalog_visible=true` в `trainer_repository.py:1331`, `arena_public_use_cases.py` (:365, :372, :382, :482, :1056, :1140), `training_group_use_cases.py` (:1398, :1547, :1668), `public.py:182`, `public.py:659`.

`is_catalog_visible` держим ещё один релиз как производное (`= state == 'published'`), пишет его только `set_catalog_state`, помечаем deprecated — иначе пришлось бы одним махом править админку и аналитику.

Защита: `set_catalog_state('published')` отказывает, если `status = 'deactivated'`.

## Модерация правок

Механику не меняем, только называем и делаем видимой.

| Что правит тренер | Когда видит клиент |
|---|---|
| имя, фамилия, описание, опыт (`profile_pending`) | после одобрения |
| фото (`photo_pending`) | после одобрения |
| услуги, цены, площадки, длительность, окно записи | сразу |
| телефон | сразу, но это обязательный признак: стёр — значит `paused` |

При наличии правок состояние остаётся `published` + признак «правки на проверке», и превью показывает **обе версии**: «Сейчас клиенты видят» / «После проверки станет». Сегодня тренер загружает фото, оно лежит в `photo_pending`, и он не знает, что клиент до сих пор видит старое. Плюс кнопка «Отменить правки» для тренера.

## Уведомления

Новые:

1. **`paused`** — «Карточка ушла из каталога: <причина>. Вернуть — один шаг» + кнопка на раздел. Не срочное, уважает тихие часы (`push_notification_start_hour/end_hour`).
2. **Автовозврат** — «Карточка снова в каталоге».
3. **Правки опубликованы** — короткий пуш. Сейчас повторное одобрение намеренно молчит (`admin_handlers.py:2252`), но «доехало ли моё новое фото» — законный вопрос.

Сохраняются: первая публикация, «нужны правки» с текстом, деактивация. На `pending_review` не пушим — тренер только что сам нажал кнопку.

Правится один существующий текст: дайджест-ветка `TRAINER_DIGEST_DROUGHT_CATALOG_HIDDEN` перестаёт быть одной на два случая — «вы сами скрылись, включить обратно?» для `hidden` и «одно поле, и вы снова в списке» для `paused`.

| № | Слайс | Что даёт |

| 5 | Перенос с «Профиля»; хаб и next_step → `ACTION_OPEN_CATALOG`; порог 5 → 1 | профиль разгружен |
| 6 | Двойное превью, мягкие предупреждения, отмена правок, ветки дайджеста | полировка прозрачности |

Слайсы 1 и 2 самостоятельны и релизятся до появления экрана: тихое выпадение из каталога перестаёт существовать раньше, чем тренер увидит новую вкладку.

## Тесты

- **Инвариант журнала:** тест, запрещающий `UPDATE trainers SET catalog_state` где-либо кроме `set_catalog_state`.
- Каждый переход из таблицы выше: состояние, событие с автором, факт уведомления.
- Публичные поверхности: `paused` / `hidden` / `needs_revision` не отдаются ни в `/api/public/trainers`, ни в карточке арены, ни в счётчиках города, ни в подборке групп.
- Backfill: снимок «кто в каталоге» до миграции равен снимку после.
- Возврат без модерации: `paused` → восстановили телефон → `published`, два события, модератору ничего не ушло.
- Возврат с модерацией: `paused` + новое фото → `pending_review`.
- `deactivated` не может стать `published`.
- Заодно: `ta.is_public` в счётчике тренеров на арене (`arena_public_use_cases.py:363`) — сегодня арена показывает завышенное число, правим, раз трогаем тот же SQL.

## Открытое, не входящее в этот дизайн

- Мобильный формат (`arena_work_format`): submission tier требует ≥1 арену (`trainer_profile_completeness.py:135`), поэтому тренер «выезжаю к клиенту» в каталог не попадает вообще. Решено оставить как есть, отдельной задачей.
- Пустой фидбек модератора из нетекстового сообщения (`admin_handlers.py:2464`) — чинится в слайсе 2 как побочный эффект перехода на `set_catalog_state`, но сам фильтр типа сообщения в админ-боте стоит поправить отдельно.
