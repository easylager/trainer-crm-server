# Мультипрофиль: запись ребёнка + раздельная статистика

**Статус:** дизайн одобрен, готов к реализации.  
**Зафиксировано:** 2026-09-04.  
**Основание:** EPIC1 (`.ai/EPIC1-client-multi-profile.md`, `.ai/DECISION-multi-profile-clients.md`) + живой UX-разрыв: переключатель на хабе есть, экран «Записаться» не показывает кого записывают, брони часто уходят на self.

---

## 1. Проблема

Родитель добавляет профиль ребёнка и выбирает его на хабе, но:

1. На форме записи **не видно**, кого записывают (только телефон аккаунта).
2. Фронт **не шлёт** `X-Profile-Id`, если выбранный профиль = `is_default` → сервер без заголовка резолвит **self** (Telegram), не default из `client_profile_links`. После «Добавить ребёнка» ребёнок как раз становится default → записи тихо идут на родителя.
3. Списки записей / куски хаба / часть истории всё ещё смотрят на `telegram_id` аккаунта → прогресс выглядит общим.
4. У тренера не гарантировано отдельное «лицо» ребёнка как клиента с собственной историей при том же канале связи (один Telegram родителя).

---

## 2. Решение (одобрено)

**Подход:** всегда идентифицировать действующий профиль + UI «Кого записываем?» на форме + добить чтение списков/статов по `client_id` профиля.

### 2.1 Модель (без новой схемы)

- Аккаунт = один Telegram / `account_telegram_id`.
- Профиль = `clients` row (`self` или `guardian`, у ребёнка `telegram_id IS NULL`).
- Связь: `client_profile_links`.
- Брони, абонементы, сертификаты, activity — по `client_id` профиля.
- Пуши и deep-link в чат — всегда на Telegram аккаунта.
- Телефон на форме / в карточке тренера у ребёнка — контакт аккаунта (родителя).

### 2.2 Хаб

- Переключатель меняет **default** (`PATCH .../default`) + активный id в `localStorage` (`cw_active_profile_id_v1`).
- Чип всегда показывает, от чьего имени сейчас работает приложение.

### 2.3 Экран «Записаться» (`book.html`)

- Блок **«Кого записываем?»**: список профилей; предвыбор = активный/default с хаба.
- Можно сменить профиль или добавить ребёнка **без** возврата на хаб.
- Смена только на форме = **override на эту бронь** (не обязана менять default хаба).
- Текст кнопки: «Записаться за {Имя}» для guardian; «Записаться» для self.
- `X-Profile-Id` уходит **всегда**, когда известен выбранный профиль (в т.ч. если он default / self).

### 2.4 Тренер

- Бронь ребёнка → отдельный `client_id` (карточка с именем ребёнка).
- Не primary-аккаунт: нет своего Telegram; контакт = телефон родителя; при необходимости пометка «через родителя».
- Родитель остаётся отдельным клиентом со своей историей.
- Уведомления в один чат; в тексте — имя профиля («запись для Леры»).

### 2.5 Прогресс / статистика

**По профилю:** upcoming/history bookings, requests list, activity-stats, passes, certificates, соответствующие куски hub bootstrap.

**На аккаунт (не трогаем):** family-access, self-register, доставка пушей.

### 2.6 Технический минимум

1. Fetch-patch: слать `X-Profile-Id` для любого выбранного профиля, не только «≠ default».
2. UI селектора на `book.html` + подпись кнопки.
3. Эндпоинты списков/хаба, ещё завязанные на `telegram_id` → `resolve_acting_client_id` + `client_id`.
4. Trainer-facing payload: имя профиля-ребёнка; контакт = аккаунт.
5. Тесты: бронь на ребёнка → другой `client_id`; статы не смешиваются; default-ребёнок без бага «пишем на родителя».

---

## 3. Вне скоупа

- Мультиучастник одной брони (`companion_client_id`).
- Переделка `client_family_access_members`.
- Полноценный редизайн всего хаба/каталога под мультипрофиль сверх необходимого для корректности данных.
