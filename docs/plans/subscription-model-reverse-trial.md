# Subscription-модель: Reverse trial + Starter / Pro

**Статус:** зафиксированное продуктовое решение (не спека на имплементацию, но уже готова к разбивке на фазы).
**Зафиксировано:** 2026-04-23.
**Связано с:** [telegram-paywall-daily-digest-monetization.md](./telegram-paywall-daily-digest-monetization.md).

Этот документ — канонический ответ на вопрос «как устроена монетизация продукта». Всё остальное (paywall copy, digest anchor, триггеры) — расширения этой модели.

---

## 1. Суть решения (в одном абзаце)

Новый тренер сразу получает **14 дней Pro без карты, без заявки, без трений**. За это время он видит полный digest, пользуется автоповторами, видит «клиентов без следующей записи» — и эти инструменты становятся частью его ежедневной рутины. На 14-й день — переход: оставил заявку и оплатил через ЕРИП/ЕПОС → Pro (или Starter по желанию); не оставил → **Free-орбита** (read-only + еженедельный digest-напоминание). Два тарифа, без конструктора. Paywall живёт не на отдельной странице, а в `digest` и в **моментах боли** из связанного документа.

**Платёж в v1 — ручной.** Пользователь жмёт «Оставить заявку» → мы пишем ему в Telegram с реквизитами ЕРИП/ЕПОС → он оплачивает → оператор включает тариф. Автоматизация платежей — осознанно отложенная задача (см. §9).

## 2. Состояния пользователя (entitlement states)

Одно поле `plan_state`, конечный автомат:

| State | Как попадает | Что видит | Что платит |
|---|---|---|---|
| `trial` | Регистрация | Полный Pro на 14 дней | 0 |
| `pending` | Оставил заявку на Pro/Starter, ещё не оплатил | Текущий уровень продлевается до +3 дней, чтобы не прерывать работу, пока оператор не подтвердил | 0 (оплата ожидается) |
| `pro` | Заявка оплачена, оператор активировал Pro | Полный Pro | 49 BYN / мес или 390 BYN / год |
| `starter` | Заявка оплачена на Starter (или даунгрейд с Pro) | Ограниченный набор (см. §3) | 19 BYN / мес или 159 BYN / год |
| `free` | Trial истёк и заявка не пришла / не оплачена в срок; подписка кончилась и не продлена | Read-only + еженедельный «что ты теряешь» digest | 0 |

**`pending` — важное состояние для v1.** Между «тренер нажал кнопку» и «оператор включил тариф» может пройти несколько часов / ночь. В это время продукт **не ломается**: показывает заглушку «заявка на Pro в обработке, пока работает текущий уровень».

**`free` — не тариф, а re-engagement канал.** Не рекламируем, не показываем «Free» в UI. Просто «пауза подписки».

## 3. Финальный feature map

### Starter (19 BYN/мес)
- Расписание: слоты, шаблон недели (один), переносы.
- Клиенты: карточка, контакт, заметки, история, **до 25 активных**.
- Ручная запись / отмена / перенос.
- Учёт абонементов (остаток занятий — видим, списание ручное).
- Базовое напоминание клиенту за N часов (единый шаблон, без кастомизации).
- Post-session отметка (пришёл / не пришёл / оплата).
- **Короткий digest**: 3 строки — сегодня / завтра / выручка за день. Без anchor-строки потерь.
- **Тизеры Pro** в digest и UI (числа без деталей: «6 клиентов без следующей записи — посмотреть → Pro»).

### Pro (49 BYN/мес)
Всё из Starter плюс:
- **Безлимит клиентов**, несколько шаблонов недели (лёд утром/вечером/выходной).
- **Автоповтор записей** (тот же клиент → та же неделя / то же время).
- **Заполнение пустых слотов** (подбор клиентов + massaction «предложить»).
- **Список «клиенты без следующей записи»** (детализированный + действия).
- **Защита от отмен**: авто-подтверждение за 24ч, правила «поздняя отмена списывается с абонемента».
- **Полный digest** с anchor-строкой «потери / риск / +Z BYN при правилах Pro».
- **Групповые тренировки**: запись, посещаемость, списание с абонементов группой.
- **Сертификаты / подарочные занятия**.
- **Аналитика выручки**: динамика 3+ мес, топ-клиенты, retention, at-risk revenue.
- **Публичная ссылка / mini-app для онлайн-записи клиентами**.
- **Кастомизация уведомлений** (тайминг, тон, каналы).

### Сознательно вне тарифной сетки (v1)
- Team / мультитренер — будущий отдельный тариф (Pro Team), не сейчас.
- Встроенные платежи клиентов (приём денег от клиентов тренера) — отдельный продукт.
- Модульные add-ons — не делаем, ломает простоту.
- Купоны / промокоды — шум, портит восприятие цены.

## 4. Цены и биллинг

### Цены (якорь — BYN)

| | Месяц | Год (−30%, списание сразу) | Логика |
|---|---|---|---|
| Starter | **19 BYN** (~490 ₽ / ~$6) | **159 BYN** (≈13 BYN/мес) | ~0.5–1% месячной выручки тренера |
| Pro | **49 BYN** (~1 290 ₽ / ~$15) | **390 BYN** (≈33 BYN/мес) | Окупается 1 сохранённым слотом в месяц |

Годовой — главный рычаг LTV. Формулировка в UI: **«зафиксировать цену на год, −30%»**.

### Платёжный канал (v1 — единственный)

**ЕРИП / ЕПОС, ручное включение оператором.** Никаких Telegram Stars, Telegram Payments, внешних провайдеров в v1.

Почему так:
- Белорусский тренер доверяет ЕРИП больше, чем карте в боте. Это снимает барьер первого платежа, особенно у старшей аудитории.
- Нулевая интеграция на старте — время, которое можно потратить на продуктовую ценность, а не на платёжку.
- Manual-flow легко даёт честный refund и разбор спорных случаев (реальный человек с реальным оператором).

Цена риска: процесс не масштабируется бесконечно. Пороговое значение для перехода на автоматизацию — см. §9, Phase +1.

### Trial-механика

- **14 дней Pro, без карты, без заявки.** Trial включается автоматически при регистрации, никаких форм.
- Оплата (точнее — заявка) доступна с Day 1. **Ранняя заявка + оплата в первые 3 дня trial → +30 дней Pro бонусом** после активации. Механика «reward early payer», не скидка — цена на ценнике та же.
- **Один TG user_id = один trial.** Повторная регистрация с того же аккаунта trial не даёт.

### Отмена, возврат, смена тарифа

- **Отмена.** Tariff работает до конца оплаченного периода. В Telegram: «Pro оплачен до 12 мая. Продлевать сам не будет — напомню за неделю.» Активного «отменить» нажимать не нужно: в manual-flow нет автосписания.
- **Refund.** Первые 3 дня после первой оплаты — полный возврат по запросу через обратный перевод ЕРИП. Годовой — pro-rated возврат первые 30 дней. После этого — только в исключительных случаях по решению оператора.
- **Pro → Starter** mid-cycle: Pro до конца оплаченного периода, потом при следующей заявке — Starter.
- **Starter → Pro** mid-cycle: оператор считает доплату вручную (остаток Starter × дней / 30 вычитается из счёта Pro), отправляет сумму в следующей ЕРИП-заявке.
- **Конец периода без продления:** за 7/3/1 день напоминаем, в день X — даём ещё 24 часа grace (продукт работает), потом downgrade в `free`. Никаких «забанили среди дня» — отключение в 00:00 следующего дня.

## 4a. Процесс заявки и оператор

### Поток на стороне пользователя

1. **Жмёт «Оставить заявку на Pro»** (или Starter / годовой). В момент нажатия в mini-app собирается мини-форма: тариф, период (мес/год), контактный ник в Telegram (pre-filled).
2. **Бот отвечает мгновенно:** «Принял заявку на Pro, 49 BYN/мес. Оператор напишет сюда в течение 1 рабочего дня и пришлёт реквизиты ЕРИП. Если срочно — @support.»
3. **Оператор пишет лично** в тот же Telegram-чат: реквизиты (номер услуги в ЕРИП / ссылка на ЕПОС), сумма, что указать в назначении платежа (user_id или короткий код).
4. **Пользователь оплачивает** и отправляет подтверждение (или просто «оплатил»).
5. **Оператор проверяет** поступление в админке ЕРИП и выполняет в боте команду активации (см. §8).
6. **Бот пишет пользователю:** «Pro включён до 12 мая. Полный digest придёт завтра утром. Спасибо.»

### Поток на стороне оператора

- **Канал операций.** Отдельный Telegram-чат, куда бот пушит каждую новую заявку структурированным сообщением:
  ```
  Новая заявка: @username (id=12345)
  Тариф: Pro (монтль)  →  49 BYN
  Назначение ЕРИП: "TC-12345-PRO"
  Текущее состояние: trial, до 2026-05-07
  История платежей: первая заявка
  [Открыть чат] [Активировать] [Отклонить]
  ```
- **SLA.** 1 рабочий день на первый ответ. Если позже — извинение + бонусный день к подписке.
- **Команды в боте** (для оператора, скрыты от пользователя):
  - `/grant user_id pro month` — активировать Pro на месяц от сегодня.
  - `/grant user_id pro year` — активировать Pro на год.
  - `/extend user_id days` — продлить текущий тариф на N дней (для бонусов / компенсаций).
  - `/refund user_id` — пометить возврат и откатить в предыдущий стейт.
- **Лог всех действий** оператора — в `billing_events`, с оператором-автором. Нужно для разбора спорных случаев.

### Состояния заявки (pending_applications)

```
submitted → contacted → awaiting_payment → paid → activated
     │           │              │             │
     │           │              │             └──→ (терминал)
     │           │              └──→ timeout → expired
     │           └──→ no_response_48h → reminded → expired
     └──→ cancelled_by_user
```

- `submitted → contacted` — оператор написал.
- `awaiting_payment` — реквизиты отданы, ждём поступление. Таймаут: 3 дня. Потом автоматическое напоминание от бота (1 раз), ещё 2 дня — `expired`.
- `paid → activated` — оператор подтвердил и включил. Между `paid` и `activated` интервал должен быть минутами, не часами.
- `expired` заявки можно «оживить» повторным нажатием «Оставить заявку» — это создаёт новую заявку, а не reactivates старую. Старая остаётся в логах.

### Защита от перегрузки оператора

- Бот показывает пользователю **честное ожидаемое время ответа** на основании текущей очереди («обычно отвечаем в течение дня», а не «мгновенно»).
- Если в очереди больше N заявок за час — бот автоматически пишет в канал операторов «перегрузка», в UI пользователя — «оператор перезвонит в течение 3 часов».
- Когда таких предупреждений больше 2 раз в неделю — триггер на автоматизацию платежей (Phase +1).

## 5. Trial timeline (что видит пользователь)

| День | Канал | Смысл | Черновик copy |
|---|---|---|---|
| 0 | Бот welcome | Онбординг | «Ты в Pro на 14 дней — без карты, без обязательств. Давай настроим расписание за 2 минуты.» |
| 1–3 | Активационные нуджи (бот) | Довести до первого digest и первого автоповтора | «Отметь, кто был на тренировке — сразу увидишь, кого записать на следующую неделю.» |
| 3 | Первый полный digest | Показать «продукт видит мой бизнес» | (стандартный Pro digest) |
| 7 | Mid-trial | Показать накопленную ценность | «За эти 7 дней автоповторы создали 14 записей. Обычно на это уходит час руками.» |
| 11 | Soft reminder | Без давления, с конкретикой | «Через 3 дня Pro закончится. Хочешь оставить как есть — оставь заявку сейчас, пришлю реквизиты ЕРИП.» |
| 13 | Finale | Выбор явный | «Завтра trial заканчивается. Pro — 49 BYN / Starter — 19 BYN / пауза. Решить сейчас?» |
| 14 | Переход | Жёсткий момент | см. §6 |
| 14+ | Weekly re-engagement (только если Free) | Возврат | «За эту неделю у тебя было 4 пустых окна и 6 клиентов без следующей записи. Вернуть Pro на 14 дней?» |

**Правило: никаких push/SMS.** Всё в Telegram, в `digest` или в карточке бота. Это и есть ценность канала.

**Важно про копирайт в manual-flow:** слово «оплатить» в кнопках избегаем. Честное — **«Оставить заявку»**. Кнопка «Оплатить» подразумевает мгновенный платёж через встроенный провайдер; нарушение ожидания = потеря доверия.

## 6. Момент X (Day 14) — экран решения

**Один экран, три кнопки, без хитростей.**

```
Trial Pro заканчивается сегодня.

За 14 дней: 38 тренировок, 12 автоповторов, 3 пустых окна заполнены.
Примерно 420 BYN, которые раньше могли бы уйти — остались у тебя.

[ Оставить заявку на Pro — 49 BYN/мес ]     ← primary
[ Оставить заявку на Starter — 19 BYN/мес ]
[ Поставить на паузу ]                       ← free-орбита
```

После нажатия на любую «Оставить заявку»:

```
Принял заявку на Pro, 49 BYN/мес.
Напишу сюда с реквизитами ЕРИП в течение рабочего дня.
Пока заявка в обработке — Pro продолжает работать, 
ничего не выключаем.
```

**Важно:**
- Цифры — только из реальных данных пользователя, без магии (правило из существующего плана digest).
- «Пауза» — честная кнопка. Не прячем её и не пугаем потерей данных. Данные сохраняем 90 дней.
- Нет таймеров, нет «осталось 2 часа». Давление разрушает доверие, которое мы 14 дней строили.
- Между «оставил заявку» и «оплатил» продукт не ломается — держим в `pending` до 3 дней на текущем уровне.

## 7. Copy-пак для контекстных paywall (итерация существующего плана)

Все тексты — в тоне `Product-voice.mdc`: без давления, без канцелярита, с конкретным следующим шагом.

| Триггер | Где | Текст | CTA |
|---|---|---|---|
| Пустые слоты | Хаб + digest | «На этой неделе 4 свободных окна — это ≈ 280 BYN по твоей средней.» | `Подобрать клиентов → Pro` |
| Post-session repeat | После отметки тренировки | «Записать Максима на следующую неделю, то же время?» | `Да, одним нажатием` (Pro: ещё и «повторять автоматически») |
| Клиент без следующей записи | Digest | «6 клиентов не записаны на след. неделю. Посмотреть кого и предложить мягко?» | `Открыть список → Pro` |
| Неподтверждённые | Карточка занятия за 24ч | «3 тренировки не подтвердил клиент. Включить авто-подтверждение и правила поздней отмены?» | `Настроить → Pro` |
| Лимит 25 клиентов | При добавлении 26-го | «У тебя уже 25 активных клиентов — отличная загрузка. В Pro лимита нет, плюс появятся автоповторы.» | `Перейти на Pro` / `Не сейчас` |
| Digest anchor (Starter → Pro) | Низ короткого digest | «Pro мог бы оценить, сколько ушло из-за отмен и пустых окон. Посмотреть одним экраном?» | `Попробовать Pro` |

**Чего не пишем никогда:** «Вы теряете деньги!», «Только в Pro!», «Срочно!», «Осталось X часов!».

## 8. Entitlement в коде (инженерная часть)

Описание модели, не имплементация.

### Состояние подписки пользователя

- `plan_state: enum(trial, pending, pro, starter, free)`
- `plan_source: enum(trial_auto, erip_manual, epos_manual, admin_granted, none)`
- `trial_started_at`, `plan_valid_until`, `plan_activated_at`, `plan_activated_by` (оператор)
- `trial_used: bool` (защита от повторного trial на одном user_id)
- `pending_until: timestamp?` — до какого момента держим текущий уровень в ожидании оплаты (обычно +3 дня от заявки)

### Заявки (отдельная таблица)

```
pending_applications
├── id
├── user_id
├── tier: enum(starter, pro)
├── period: enum(month, year)
├── amount_byn
├── erip_code (генерируется: "TC-{user_id}-{tier}-{seq}")
├── status: enum(submitted, contacted, awaiting_payment, paid, activated, expired, cancelled)
├── submitted_at
├── contacted_at
├── activated_at
├── operator_id (кто активировал)
└── notes (свободный текст оператора)
```

### Гейты фич

- **Soft gate** (кнопка/блок с замком, ведёт в paywall-копирайт) — везде, где это повышает конверсию и не ломает UX.
- **Hard gate** (просто нет опции) — только там, где soft gate даст невалидное состояние данных.
- Принцип гейта — функция от `plan_state`, а не от `plan_source`. Оператор включил через `admin_granted` — доступ ровно такой же, как у платного Pro.

### Digest-worker

- Принимает `plan_state` как первый параметр. Шаблон digest — **один конфиг с условными блоками**, а не 4 параллельных кодовых пути.
- Для `pending` — шаблон как у целевого тарифа (чтобы пользователь уже «жил в Pro» до активации), плюс тихая строка «заявка в обработке».

### Billing events (единый лог)

Все изменения подписки и заявки пишутся в один лог, это источник правды для метрик и разбора спорных случаев:

```
billing_events
├── event_type: application_submitted | operator_contacted | payment_confirmed 
│               | plan_activated | plan_expired | plan_downgraded 
│               | refund_issued | admin_grant | admin_extend
├── user_id
├── actor: enum(user, operator, system)
├── payload (json, зависит от event_type)
└── created_at
```

## 9. Фазированный roll-out

### Phase M — MVP монетизации (P0), полностью ручной
- Entitlement state machine + 14-дневный trial.
- Таблица `pending_applications` + канал операторов.
- Операторские команды: `/grant`, `/extend`, `/refund`.
- Экран «Момент X» и weekly re-engagement digest для `free`.
- Triggers: post-session repeat, empty slots, clients-without-next-booking.
- Digest anchor-строка в Pro + тизер в Starter.
- Единый `billing_events` лог.

### Phase +1 — автоматизация платежей
**Триггер перехода:** 2+ «перегрузки оператора» в неделю, или количество активных заявок превысило 50/месяц, или time-to-activation вышло за 24 часа по медиане.

- Интеграция Telegram Payments с ЕРИП-совместимым провайдером (кандидаты: bePaid, Assist, WebPay).
- Кнопка «Оставить заявку» превращается в «Оплатить через ЕРИП» + остаётся fallback «Написать оператору».
- Автоматическое подтверждение поступления → `plan_activated` без человека в цикле.
- Self-service refund в боте (первые 3 дня).

### Phase +2 — усиление
- Годовой тариф с заморозкой цены (можно и раньше, но требует чёткого рефанд-процесса — делаем после автоматизации).
- Триггер «авто-подтверждение / правила отмен».
- A/B на copy триггеров (когда юзеров ≥500 в месяц).
- Referral: +1 месяц Pro за приведённого тренера.
- Региональные цены (RU, KZ, UA).
- Pro Team (мультитренер) — отдельное продуктовое решение, не этот документ.

## 10. Целевые метрики

### Продуктовые
- **Trial → заявка** — 12–20% (воронка поведения)
- **Заявка → оплата** — 70–85% (если ниже — что-то не так с SLA оператора или с доверием к ЕРИП-инструкциям)
- **Trial → Pro** (оплаченный) — 8–15%
- **Trial → Starter** — 20–30%
- **Overall paid conversion** — 30–45%
- **Pro share of paid** — >60% (если ниже — Starter «съедает» Pro, пересматриваем, что где)
- **MRR per active trainer** — 30+ BYN (взвешенно)
- **Free → Reactivation** — 5–10% в месяц (weekly re-engagement digest)
- **Digest CTR на paywall CTA** — отдельно по каждому триггеру, главный сигнал «какая боль настоящая»

### Операционные (только Phase M, ручной flow)
- **Median time-to-first-contact** (submitted → contacted) — **<4 часа** в рабочее время, **<24 часа** иначе
- **Median time-to-activation** (paid → activated) — **<30 минут**
- **Application expired rate** — <15% (заявка создана, оплаты не последовало)
- **Перегрузок оператора в неделю** — 0 штатно, 1 допустимо, 2+ = триггер Phase +1

## 11. Что специально **не делаем** сейчас

- Страницу `/pricing` в mini-app. Есть только экран «Момент X» и контекстные paywalls.
- Мультитарифный конструктор.
- Купоны/промокоды.
- Free-tier с лимитом клиентов как самостоятельный тариф (в нашей модели `free` — это re-engagement состояние, а не витрина).
- Enterprise / school / клуб-тариф.

## 12. Открытые вопросы (требуют решения при разбивке на фазы)

1. **Юр.лицо / ИП для приёма ЕРИП.** Какой счёт и под каким лицом принимаем платежи — нужно решить ДО первой заявки. Влияет на назначение платежа и закрывающие документы.
2. **Налоги и закрывающие документы.** Нужно ли выдавать чек/акт каждому тренеру-физлицу? Консультация с бухгалтером обязательна до первого BYN.
3. **Оператор и канал операций.** Кто именно обрабатывает заявки в Phase M (основатель / саппорт / подрядчик)? Нужен график покрытия (рабочие часы + выходные).
4. **Длина trial**: 14 дней — базовая гипотеза. После 200 триалов замерить, стоит ли идти в 7 или 21.
5. **Grandfathering цен** при повышении в будущем — policy зафиксировать ДО первых платных юзеров.
6. **Порог перехода на Phase +1.** Зафиксировать конкретные цифры (в §9 предложен набор) и поставить мониторинг.
7. **Payment provider для Phase +1** (bePaid / Assist / WebPay) — финальный выбор в момент, когда придёт время автоматизации.
