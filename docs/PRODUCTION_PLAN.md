# Боевой план: CI, деплой, откат, эксплуатация

Цель: вывести приложение в боевой режим с предсказуемым деплоем, откатом при проблемах и ясными процедурами эксплуатации.

---

## 1. Обзор компонентов и окружений

| Компонент | Описание | Порт/протокол |
|-----------|----------|----------------|
| **API** | FastAPI: каталог, тренеры, загрузка фото, health | HTTP, напр. 8000 |
| **Клиентский бот** | Публичный Telegram-бот (запись, заявки, отзывы) | Polling |
| **Тренерский бот** | Вход по ссылке с сайта (расписание, записи, отклики) | Polling |
| **Админ-бот** | Модерация тренеров (/pending) | Polling |
| **PostgreSQL** | Основная БД | 5432 |
| **S3-совместимое хранилище** | Фото тренеров | По конфигу |

**Окружения:**
- **Production (prod)** — боевое; один инстанс API + по одному процессу каждого бота (или масштабирование по необходимости).
- **Staging (опционально)** — копия прода для проверки релизов перед продом.

## 2. CI (непрерывная интеграция)

### 2.1 Текущее состояние
- GitHub Actions: тесты на push/PR в `master`/`main` (PostgreSQL 16, миграции, pytest).

### 2.2 Рекомендуемое расширение CI

| Этап | Действие | Когда |
|------|----------|--------|
| **Lint** | ruff (или black + isort) | Каждый push/PR |
| **Type check** | mypy (опционально, по мере внедрения) | Каждый push/PR |
| **Unit/Integration tests** | `pytest tests/ -v` | Каждый push/PR |
| **Migrations check** | `alembic check` или прогон upgrade на тестовой БД | Каждый push/PR |
| **Security** | `pip audit` или Trivy для образа | Перед сборкой образа / по расписанию |
| **Build image** | Сборка Docker-образа (если используется) | При мерже в main / по тегу |

Минимальный набор для «боевого» режима: **тесты + миграции в CI обязательно**. Lint и security — по возможностям.

### 2.3 Ветки и защита main
- **main** (или **master**) — ветка для прода. Прямые пуши запрещены; только через PR.
- PR: обязательно прохождение CI (tests green). По желанию: code review, требование апрува.
- Теги вида `v1.2.3` — для версионирования релизов и отката.

## 3. Сборка и артефакты

### 3.1 Версионирование
- **Семантическое версионирование**: `MAJOR.MINOR.PATCH` (напр. 1.0.0).
- Тег в Git = версия релиза. В коде/логах можно выводить `GIT_SHA` и тег (через env при сборке).

### 3.2 Docker (рекомендуется для прода)
- **Один образ** с приложением; **точка входа выбирается через команду** (API или один из ботов), чтобы не плодить три образа.
- Пример структуры:
  - `Dockerfile`: multi-stage, Python 3.12, установка зависимостей, копирование `src/`, `alembic/`, без dev-зависимостей.
  - `docker-compose.prod.yml` (или аналогичный): сервисы `api`, `client_bot`, `trainer_bot`, `admin_bot` (опционально), общий образ, разные `command`.
- В образ не попадают: `.env`, секреты, лишние файлы. Секреты — только через переменные окружения при запуске.

### 3.3 Реестр образов
- GitHub Container Registry (ghcr.io) или другой registry. CI при мерже в main пушит образ с тегами `latest` и `v1.2.3`.

## 4. CD (непрерывная доставка / деплой)

### 4.1 Целевая платформа (на выбор)
- **Railway / Render / Fly.io** — минимальная настройка, один репо → несколько сервисов (API + воркеры ботов).
- **VPS (Ubuntu + Docker Compose)** — полный контроль; деплой через `docker compose pull && docker compose up -d`.
- **Kubernetes** — при росте нагрузки; отдельный манифест и Helm chart не описываем здесь.

### 4.2 Порядок деплоя (без даунтайма по возможности)
1. **Миграции БД** — выполняются **до** переключения трафика на новую версию приложения.
   - Команда: `alembic upgrade head` (отдельный job или init-контейнер с доступом к БД).
   - Важно: миграции должны быть обратно-совместимы (не ломать старый код на время деплоя).
2. **Обновление контейнеров/процессов**: pull нового образа, перезапуск сервисов (API, боты).
3. **Проверка**: запрос на `/health` API; при 200 — деплой считается успешным.

### 4.3 Секреты и конфиг
- **Не хранить** секреты в репозитории. Использовать:
  - GitHub Secrets — для CI (токены ботов, ключи к БД для тестов).
  - Переменные окружения на платформе (Railway, VPS, k8s Secrets).
- Список переменных для прода описать в `.env.example` (без значений) и в Runbook (раздел 8).

### 4.4 Чек-лист перед первым боевым деплоем
- [ ] Все секреты заданы в окружении прода (токены ботов, `DATABASE_URL`, S3, `ADMIN_TELEGRAM_IDS`).
- [ ] Миграции применены к прод-БД.
- [ ] Health API возвращает 200 и `db: ok`.
- [ ] Боты запущены и отвечают (проверка в Telegram).
- [ ] S3 доступно (если используется); загрузка фото работает.
- [ ] Админ-бот доступен только указанным Telegram ID.

## 5. Откат (rollback)

### 5.1 Когда откатываться
- API или боты падают с ошибками после деплоя.
- Резкий рост ошибок в логах или жалобы пользователей.
- Проблемы с производительностью или недоступностью БД/S3.

### 5.2 Откат кода/образа (быстрый)
- **Вариант A (Docker)**: переключить деплой на предыдущий тег образа (напр. `v1.2.2` вместо `v1.2.3`) и перезапустить сервисы.
- **Вариант B (Git)**: откатить ветку main на предыдущий коммит (или тег), заново собрать и задеплоить. Менее удобно, если нет образов по тегам.
- Действие: одна команда или кнопка в панели (например, «Redeploy previous version» в Railway).

### 5.3 Откат миграций БД (осторожно)
- Миграции **вниз** (`alembic downgrade -1`) применяются только если новая миграция уже создала несовместимые изменения и старый код не может работать.
- По умолчанию: **миграции только вперёд**. Новые миграции должны быть обратно-совместимы (новые колонки nullable, не удалять колонки в той же версии кода).
- Если откатили образ и БД уже на новой миграции — либо откатить миграцию вручную (downgrade), либо оставить БД как есть, если старый код умеет с ней работать.

### 5.4 Документирование
- В Runbook (раздел 8) зафиксировать: «Как откатить на предыдущую версию образа» (конкретные команды для вашей платформы).
- Хранить последние 2–3 тега образов в registry, чтобы быстро переключиться.

## 6. Health checks и готовность

### 6.1 API
- Эндпоинт **GET /health** уже есть: проверка БД и опционально S3. При недоступности БД — 503.
- Использовать для:
  - Load balancer / платформы (liveness и readiness).
  - Мониторинга (периодический запрос).

### 6.2 Боты
- Отдельного HTTP health у ботов нет (polling). Готовность = процесс запущен и не падает.
- Мониторинг: проверка что процесс живой (systemd/supervisor/платформа), плюс логи и алерты при падении.

### 6.3 Рекомендации
- Интервал проверки /health: 30–60 сек. При двух подряд 503 — алерт.
- Боты: рестарт при падении (restart policy в Docker/systemd).

## 7. Мониторинг, логи, алерты

### 7.1 Логи
- **Стандартный вывод (stdout/stderr)** — все сервисы пишут в stdout; платформа или агент собирает логи (Railway, CloudWatch, Loki, ELK).
- **Аудит**: логгер `audit` пишет структурированные JSON-строки; удобно парсить и искать по `event`, `actor_id`, `trainer_id`.

### 7.2 Метрики (по возможности)
- Запросы к API: количество, латентность, ошибки (5xx).
- Очереди/задержки ботов — через логи (например, задержка между событием и ответом).

### 7.3 Алерты
- **Критично**: API 503, падение процесса бота, недоступность БД.
- **Важно**: рост 5xx, падение S3 (если отображается в /health).
- Каналы: Telegram-чат для админов, email, или интеграция с PagerDuty/Opsgenie.

### 7.4 Резервное копирование БД (связь с 3.2.4)
- Ежедневные бэкапы PostgreSQL (pg_dump или снимки диска).
- Хранение: минимум 7 дней; периодическая проверка восстановления.
- Перед крупными миграциями — ручной бэкап.

## 8. Runbook: деплой и инциденты

*(Краткий шаблон; детали подставляются под вашу платформу.)*

### 8.1 Обычный деплой (новая версия)
1. Убедиться, что CI зелёный для целевого коммита/тега.
2. Создать тег: `git tag v1.2.3 && git push origin v1.2.3`.
3. Запустить миграции на прод-БД: `alembic upgrade head` (или через CI job с доступом к прод-БД).
4. Задеплоить новый образ/код (через панель или `docker compose pull && docker compose up -d`).
5. Проверить `GET https://<api-host>/health` → 200.
6. Проверить ботов в Telegram (краткий сценарий: /start, один запрос к API).

### 8.2 Откат на предыдущую версию
1. Определить предыдущий рабочий тег (напр. `v1.2.2`).
2. Переключить деплой на образ с этим тегом (или откатить ветку и пересобрать).
3. Перезапустить все сервисы (API, клиентский бот, тренерский бот, админ-бот).
4. Проверить /health и ботов.
5. Если откатывали миграцию — выполнить `alembic downgrade -1` (только при необходимости и с бэкапом).

### 8.3 Инцидент: API не отвечает / 503
1. Проверить /health: если 503 — смотреть деталь (часто БД или сеть).
2. Проверить доступность БД с хоста приложения (подключение, диск).
3. Просмотреть логи API за последние 5–10 минут.
4. При необходимости — откат на предыдущую версию образа.
5. После стабилизации — разбор причин и фикс.

### 8.4 Инцидент: бот не отвечает
1. Убедиться, что процесс бота запущен (статус воркера/контейнера).
2. Проверить логи бота (ошибки, исключения).
3. Проверить доступность API и БД с хоста бота (бот дергает API и БД).
4. Рестарт процесса/контейнера; при повторении — откат версии и разбор.

### 8.5 Инцидент: ошибки в БД или миграции
1. Остановить деплой новых версий.
2. Оценить: нужен ли откат миграции (downgrade) или достаточно отката кода.
3. При откате миграции — предварительно сделать бэкап БД.
4. Выполнить `alembic downgrade -1` (или до нужной ревизии), затем откат образа приложения.
5. После восстановления — анализ и исправление миграции/кода.
