# Ротация секретов при утечке

Краткий runbook: что сделать, если токен бота, пароль БД или ключ S3 могли утечь.

## 1. Telegram Bot Token

1. Открыть [@BotFather](https://t.me/BotFather) → выбрать бота → **Revoke current token** (или перевыпустить токен).
2. В панели деплоя (Railway / другое) обновить переменную `TELEGRAM_BOT_TOKEN_CLIENT`, `TELEGRAM_BOT_TOKEN_TRAINER` и/или `TELEGRAM_BOT_TOKEN_ADMIN`.
3. Перезапустить процессы, которые используют этот токен (соответствующий контейнер бота, при необходимости API).
4. Если используется **webhook**: после смены токена заново выставить webhook на новый URL (для aiogram/long polling обычно достаточно рестарта с новым env).

## 2. База данных

1. Сменить пароль пользователя БД в панели провайдера.
2. Обновить `DATABASE_URL` и `DATABASE_URL_SYNC` в окружении.
3. Redeploy всех сервисов, читающих БД.
4. Проверить, что старые connection string больше нигде не хранятся (CI, бэкапы-скрипты, локальные `.env`).

## 3. S3 / объектное хранилище

1. В консоли провайдера отозвать/удалить скомпрометированный access key.
2. Создать новый ключ с теми же минимально необходимыми правами.
3. Обновить `S3_ACCESS_KEY`, `S3_SECRET_KEY` в окружении и redeploy.

## 4. bePaid / SMTP

- **bePaid:** сменить секрет в личном кабинете провайдера, обновить `BEPAID_SECRET_KEY` (и при необходимости `BEPAID_SHOP_ID`). Те же значения используются для HTTP Basic на webhook уведомлений (`POST /api/webhooks/bepaid`).
- **SMTP:** сменить пароль почтового ящика / app password, обновить `SMTP_PASSWORD`.

## 5. После инцидента

- Зафиксировать время обнаружения и перечень скомпрометированных секретов.
- Просмотреть audit-логи и обычные логи на аномальную активность за период до ротации.
- При массовой утечке — уведомить пользователей по вашей политике (юридически значимый шаг — отдельно с юристом).
