# IP клиента и rate limit публичных страниц (TASK-190)

## Как определяется IP

`src/shared/client_ip.py`, один путь для лимитера, телеметрии каталога, редиректов и гео.

Стратегия по умолчанию `CLIENT_IP_STRATEGY=leftmost`:

1. левая публичная запись `X-Forwarded-For` (пропускаются 10/8, 172.16/12, 192.168/16,
   100.0.0.0/8 включая CGNAT, loopback, link-local, ULA и мусор);
2. иначе `X-Real-IP`;
3. иначе адрес сокета.

### Почему левая запись

Проверено на проде 2026-10-06: 160 параллельных запросов к `/api/public/*`, каждый с другим
`X-Forwarded-For: 198.51.100.N`, дали ровно 120 x 200 и 40 x 429 при лимите 120/60 с. Значит
edge Railway срезает присланный клиентом XFF, а левая запись — реальный IP соединения.
Предпосылка аудита M5 («левый XFF задаёт клиент») на Railway неверна. Правая запись на Railway
может оказаться внутренним хопом, и все посетители схлопнулись бы в одного.

Запасной режим для платформы, которая дописывает адрес справа и не режет заголовок:
`CLIENT_IP_STRATEGY=rightmost_hops` и `TRUSTED_PROXY_HOPS=N` (0 — игнорировать заголовок).

## Лимиты (на IP за 60 с)

| Бакет | Пути | Лимит |
|---|---|---|
| page | `/p /c /ice /r` | 120 |
| image | любой `*.png` под этими путями | 40 |
| bot | те же пути, UA превью/поиска/краулера | 600 |

Настройка: `API_RATE_LIMIT_{PAGE,IMAGE,BOT}_MAX_REQUESTS` и `_WINDOW_SEC`. Счётчики и кэш PNG
(128 шт / 48 МБ) живут в памяти процесса, то есть на каждый инстанс отдельно.
