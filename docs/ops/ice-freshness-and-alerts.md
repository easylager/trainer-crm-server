# Свежесть расписания льда и алерты по источникам

Как часто мы перечитываем сайты катков, когда расписание считается устаревшим, что
об этом видит пользователь и когда админ получает пуш. Код: `src/ingestion/freshness.py`
(правила), `src/ingestion/scheduler.py` (опрос), `src/ingestion/source_alerts.py` (пуши).

## Где это крутится

Всё — в процессе `notification_service` (`python -m src.bot.notification_service`), не в API:

| Цикл | Интервал | Что делает |
|---|---|---|
| `ice_ingest_scheduler` | 60 с | берёт задания с `next_run_at <= now` (не больше 20 за тик), прогон → публикация → коммит **после каждого** задания |
| `ice_source_alert` | 120 с | пуш в админ-бот по арене, чей источник сломан/устарел, напоминания и «восстановлено» |
| `ice_health_alert` / `ice_health_weekly_digest` | 1 ч | прежние сводки: молчащие источники раз в день, воскресный дайджест |
| `ice_scheduler_watchdog` | 5 мин | сторож: «прогонов нет вообще» → 🔴, восстановление → ✅ (см. ниже) |

Если `notification_service` не запущен — расписания не обновляются вообще. Алерты
идут из того же процесса, поэтому «воркер лежит целиком» видно только по флагу
`schedule_stale` в API и по отсутствию пушей; мониторинг живости процесса — отдельно.

### Heartbeat планировщика (TASK-176)

На старте цикл пишет `ice ingest scheduler loop started; tick every 60s`, дальше одна
INFO-строка на **каждый** тик, включая пустые:

```
ice ingest tick acquired=yes due=35 ran=20 ok=18 duration=41.2s
ice ingest tick acquired=yes due=0 ran=0 ok=0 duration=0.0s
ice ingest tick acquired=no (another runner owns the scheduler lock) duration=0.0s
ice ingest tick failed error=RuntimeError duration=0.3s   # плюс traceback строкой выше
```

`due` — сколько заданий просрочено (до потолка 20), `ran` — сколько прогнано. Строки
нет дольше «60 с + длительность тика» — цикл мёртв или висит. Цикл не выходит молча:
`CancelledError` изнутри тика логируется и тик повторяется, наружу он уходит только при
остановке сервиса. Любой фоновый цикл `notification_service`, завершившийся сам,
пишет `Background loop <name> died` (ERROR).

Сбой `pg_advisory_unlock` (соединение с локом умерло за время прогона) не теряет
результаты: WARNING `ice ingest lock: unlock failed`, соединение выбрасывается из пула,
Postgres снимает лок вместе с ним.

**Инцидент 2026-10-04…05.** Прод собран Nixpacks на Python **3.11** (`runtime.txt`),
CI и локальные venv — 3.12. `scheduler_lock.py` использовал синтаксис PEP 695
(`def f[T]()`), импорт шёл внутри цикла до `try` → `SyntaxError` убивал задачу при первом
тике, исключение лежало в задаче до остановки сервиса, в логах — ничего. С 10-03 вечера
прогоны делались только вручную (`run_ice_ingest_once.py`). Защита:
`tests/ingestion/test_scheduler_loop.py::test_code_parses_on_production_python_version`
парсит `src/`, `scripts/`, `migrations/` под версию из `runtime.txt`.

## Как часто опрашиваем

Каденс задания (`hourly`/`daily`/`weekly` в `ice_parser_jobs.cadence`) больше **не**
определяет опрос — раньше weekly-источник перечитывался раз в неделю, а упавший прогон
повторялся через тот же каденс. Теперь:

| Исход прогона | Следующий прогон |
|---|---|
| `ok` / `empty`, день (07:00–23:00 Минск) | через 45 мин |
| `ok` / `empty`, ночь | через 120 мин, но не позже 07:00–07:30 (смещение по `job_id`) |
| `error` | 15 → 30 → 60 → 120 → 180 мин по длине серии сбоев |
| `blocked` (нет BY-egress на воркере) | через 6 ч |

На всё — джиттер ±15%, чтобы источники не били залпом. Прогоны идут строго по
одному (без параллельных запросов), таймаут HTTP — 20 с.

**Публикация сразу.** Успешный (`ok`) прогон в том же тике заменяет `ice_sessions`
арены в своём горизонте дат и коммитится — новое расписание видно в API через секунды
после прогона, ежедневной джобы публикации нет. `empty`/`error`/`blocked` будущие
сеансы **не удаляют** (защита от сломанного парсера) — поэтому и нужны флаг и алерты.

Ручные настройки в `ice_parser_jobs.config`:

| Ключ | Смысл |
|---|---|
| `poll_minutes` | фиксированный интервал опроса для сайта, который просит реже (ошибки тоже не чаще) |
| `stale_after_hours` | порог устаревания для этого источника (по умолчанию 6) |
| `alerts_muted` | `true` — не слать алерты по источнику (известная проблема, уже в работе) |

## Состояние источника

Колонки `ice_parser_jobs` (миграция `0211_ice_source_state`), пишет планировщик:
`last_ok_at`, `last_ok_slot_count`, `failing_since`, `failure_streak`,
`last_error_code`, `last_error_summary`. Алертные `alert_state` (`ok`/`failing`) и
`alert_sent_at` пишет только тик алертов — дедуп переживает рестарт воркера.

Что считается сбоем: `error`, `blocked` и `empty` **при непустой витрине** (источник
отдал 0 сеансов, а у нас висят прошлые — код `empty_after_slots`). Пустой источник при
пустой витрине (межсезонье) — честное «нечего показывать», не сбой.

При первичном backfill миграция `0211` не может точно восстановить, сколько сеансов
было видно на момент каждого исторического `empty`: история прогонов это число не
сохраняет. Поэтому backfill использует текущие видимые сеансы парсера как proxy:
`empty` считается сбоем, только если такие сеансы остаются видны при миграции;
иначе он сбрасывает серию. Это приближение, а не точное воспроизведение прошлых
состояний, и оно может не посчитать сбой, если старые сеансы уже перестали быть видны.

## Публичный API: поле `freshness`

Есть в карточке `GET /api/public/arenas/{ref}` (рядом со старыми `schedule_valid_until`,
`source_*`, `verified_at`, `profile_updated_at`), в каждом элементе ленты
`GET /api/public/ice/arenas` и в ответе `GET /api/public/arenas/{ref}/sessions`:

```json
"freshness": {
  "schedule_observed_at": "2026-10-01T11:00:00+00:00",
  "schedule_auto": true,
  "schedule_stale": true
}
```

| Поле | Значение |
|---|---|
| `schedule_observed_at` | когда расписание последний раз подтверждено: последний `ok` парсера, а без парсера — самое свежее `observed_at` показанных сеансов; `null` — неизвестно |
| `schedule_auto` | у арены есть включённый парсер (расписание обновляется само) |
| `schedule_stale` | парсер есть, но не читал сайт успешно дольше порога (6 ч по умолчанию). Без парсера всегда `false` |

Для UI: при `schedule_stale: true` и непустом списке сеансов честно сказать, что
расписание могло измениться, и показать дату подтверждения — например «Расписание
от 1 окт, 14:00 — могло измениться, уточните на сайте катка». Без сеансов флаг можно
не рендерить.

## Алерты в админ-бот

Получатели: `ICE_ALERT_CHAT_IDS` (JSON-массив, например общий чат `[-100…]`), иначе
`ADMIN_TELEGRAM_IDS`. Бот — `TELEGRAM_BOT_TOKEN_ADMIN`. Без токена или получателей
текст алерта пишется в лог (WARNING), состояние двигается как обычно.

Правила:

- источник «сломан», если сбоев подряд ≥ 2 (первый повтор через 15 мин, то есть алерт
  примерно через 15 минут после первого сбоя) **или** расписание устарело при непустой
  витрине (ошибок нет, но прогонов тоже — например, планировщик не доходит);
- переход в «сломан» → один пуш 🔴 в любое время суток;
- пока сломан → напоминание 🟠 не чаще раза в 4 часа и только 09:00–22:00 Минск;
- починился (или выключен / заглушён) → один пуш ✅;
- несколько арен за тик — одним сообщением (режется по лимиту Telegram).

Примеры:

```
🔴 Лёд: сломался источник
Минск-Арена (Минск) · minskarena_saleframe_v1
Что: парсер упал при чтении сайта — HTTP 503 Service Unavailable
С: 1 окт, 12:40 (20 мин, попыток подряд: 2)
Пользователи видят: расписание от 1 окт, 12:00 — 12 сеансов
```

```
✅ Лёд: источник восстановлен
Минск-Арена (Минск) · minskarena_saleframe_v1
Пользователи видят: расписание от 1 окт, 18:40 — 14 сеансов
```

Что делать по алерту: открыть сайт катка, сравнить с тем, что видят пользователи;
если сайт поменял вёрстку — чинить парсер (`data/parsers/*.md`, адаптер в
`src/ingestion/adapters*.py`); на время починки можно поставить `alerts_muted` или
выключить задание (`is_enabled = false` — витрина перестанет считаться автоматической).

### Сторож планировщика (TASK-176)

Пер-источниковые алерты не называют ситуацию «планировщик мёртв целиком». Сторож —
отдельный цикл (`src/ingestion/scheduler_watchdog.py`), раз в 5 минут:

- **🔴 «Планировщик льда стоит»**, если нет ни одного завершённого `ice_scrape_runs`
  дольше **2 ч** и есть включённые задания, просроченные дольше **15 мин**. Ночью, когда
  ничего не due, тишина — норма;
- **✅ «Планировщик льда снова работает»** — появился прогон новее момента 🔴;
- состояние в таблице `ice_ops_alerts` (ключ `ice_scheduler_stalled`, миграция 0216),
  поэтому рестарт воркера не даёт повторного 🔴; недоставленный алерт повторяется на
  следующем тике. Канал — тот же (`ICE_ALERT_CHAT_IDS`, иначе `ADMIN_TELEGRAM_IDS`).

По 🔴: в логах `ice-platform-notification` искать `ice ingest tick` и
`Background loop … died`. Сторож живёт в том же процессе: если процесс лежит целиком,
не будет и сторожа.

## Белорусский выход (BY_EGRESS_PROXY_URL)

Некоторые сайты (Юность, СДЮШОР/ledlife, часть областных) отвечают 403 любому небелорусскому
IP. Задания таких катков помечены `requires_by_egress`. Без `BY_EGRESS_PROXY_URL` у процесса
`notification_service` они не запускаются (статус `blocked`, алерт «нужен выход из BY»).
С ним — ходят через этот прокси; остальные задания по-прежнему напрямую.

Формат: `http://user:password@host:port` (HTTP-прокси с CONNECT; aiohttp, `src/ingestion/source_io.py`).
Объём — десятки запросов в сутки, так что подходит самый дешёвый белорусский IPv4-прокси или VPS в РБ
с tinyproxy/squid под паролем.

**Ноутбук в РБ (без VPS):** на Railway `BY_EGRESS_PROXY_URL` не задавать; с Mac в Беларуси (VPN выкл.)
`bash scripts/local_by_egress_proxy.sh setup` → в отдельном терминале `start`, затем `check` / `ingest`
(прод-БД: `ingest` = `run_ice_ingest_once.py --i-know-this-is-prod`). Прокси слушает только `127.0.0.1`.
`ingest` включает `ledlife_origin_html_v1` и `junost_origin_html_v1` (СДЮШОР / Юность). Свежие HTML:
`bash scripts/fetch_minsk_by_origin_fixtures.sh` (VPN выкл., tinyproxy запущен).

TLS-доверие — по хранилищу ОС через `truststore` (на Mac за VPN/антивирусом встроенный набор
корней Python даёт «self-signed certificate in certificate chain», хотя браузер сайт открывает).
