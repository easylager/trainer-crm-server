# Сервис уведомлений (notification_service)

Источник правды по интервалам и окну отправки: `src/bot/notification_loops.py`, часовой пояс и границы окна — `src/shared/notification_hours.py` (**Europe/Minsk**, **08:00–22:00**, полуинтервал: 22:00 уже не отправляем).

Запуск: `python -m src.bot.notification_service` (отдельный процесс; клиентский и тренерский боты только polling).

Дополнительно: [NOTIFICATION_JOBS.md](./NOTIFICATION_JOBS.md) — история решений и рекомендации по продакшену.

## Smoke checklist после деплоя (5–7 пунктов)

Выполнять с **запущенным** `notification_service` и корректным `DATABASE_URL`/токенами ботов.

1. **Процесс**: в логах старта есть строка вида `Notification service started (client=…, trainer=…, other=…)`.
2. **Окно**: в интервале 08:00–22:00 Минск создать тестовую запись и убедиться, что тренер получил уведомление о новой записи в разумные сроки (минуты); вне окна — сообщения **не** уходят (можно проверить логами отсутствия send или отложенной доставкой утром).
3. **P0 клиент**: за сутки/два часа до слота (по настройке reminders) приходит напоминание с датой/временем слота (без обещания «ровно через N часов» в тексте).
4. **P0 клиент**: после `end_time` слота в пределах ~5 мин + окна приходит «Занятие завершено» (или утром, если слот кончился ночью).
5. **P0 тренер**: новая заявка по городу/услуге → уведомление тренеру с кнопками отклика.
6. **P0 клиент**: отклик тренера → клиент получает уведомление (и при наличии HTTPS — кнопка в мини-приложение заявок).
7. **Отмена**: тренер отменяет подтверждённую запись → клиент получает сообщение об отмене в окне 08–22.

При сбое: проверить, что не упали только боты, а **отдельный** воркер уведомлений тоже запущен на том же окружении, что и БД.
