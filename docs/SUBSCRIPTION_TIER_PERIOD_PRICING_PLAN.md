# План: цены «тариф × период» в админке (9 ячеек)

**Контекст:** команда `/speckit.plan` — целевой артефакт для последующего `/speckit.tasks` / реализации.  
**Дата:** 2026-03-29

## Краткое резюме

**Цель:** админ в мини-приложении «Тарифы подписки» должен задавать **отдельную цену для каждой комбинации** из 3 тарифов (crm / online / analytics) и 3 периодов (1 / 3 / 12 месяцев) — **9 независимых цен**, согласованных с тем, что видит и оплачивает тренер (сначала период, потом тариф).

**Сейчас это не так:** в таблице `subscription_tier_pricing` **одна строка на тариф** и одно поле `price_cents` + `period_days` (из миграции 0066 по сути «месячная» база под 30 дней). В `trainer-subscription.html` цены за 3 и 12 месяцев считаются **в браузере** через фиксированные `periodDiscounts` (10% / 20%). Админка правит только **3** цены. Бэкенд `POST /api/webapp/trainer/subscription/mock-checkout` принимает в теле `period_months`, но модель **`SubscriptionTierMockCheckoutBody` содержит только `tier`** — период на сервере **не используется**; срок подписки берётся из `get_tier_pricing` → `period_days` одной строки тарифа.

## Текущее состояние (факты из кода)

| Область | Поведение |
|--------|-----------|
| **Схема БД** | `subscription_tier_pricing`: `UNIQUE(tier)`, поля `price_cents`, `period_days`, тексты, буллеты. |
| **Каталог для тренера** | `get_subscription_tier_catalog` → 3 записи; фронт считает «со скидкой» сам. |
| **Админка** | `GET/PATCH /api/webapp/admin/subscription-tiers` — правка по `tier`, одна цена. |
| **Оплата (демо)** | `set_subscription_after_mock_payment` — срок `expires_at = started_at + timedelta(days=pricing["period_days"])` из **одной** строки тарифа. |

## Целевое состояние

1. **Данные:** для каждой пары `(tier, billing_period_months)` с `billing_period_months ∈ {1, 3, 12}` хранится **согласованная с продуктом цена** (и при необходимости срок в днях для продления подписки).
2. **Тренерское мини-приложение:** убрать (или свести к минимуму) **жёсткие** `periodDiscounts`; отображаемые суммы и итог оплаты берутся из **API** для выбранного периода и тарифа.
3. **Админское мини-приложение:** UI «матрица 3×3» (или 3 блока по тарифу с тремя полями цены) + сохранение через API с аудитом.
4. **Checkout и подписка:** сервер принимает `(tier, period_months)`, валидирует, что для пары есть цена; выставляет `expires_at` по правилам периода (например 30 / 90 / 365 дней или календарные месяцы — **нужно зафиксировать в реализации одно правило**).

## Предлагаемая модель данных

**Вариант A (рекомендуется): отдельная таблица цен по периоду**

- Таблица, например `subscription_tier_period_pricing`:
  - `tier` (`subscription_tier_enum`, FK-логика на справочник тарифов)
  - `period_months` (`smallint`, CHECK `IN (1, 3, 12)`)
  - `price_cents` (`int` ≥ 0) — **итоговая сумма к оплате за выбранный период** (проще стыковать с «Оплатить X BYN (3 мес)»)
  - опционально `period_days` для расчёта `expires_at`, если не хотим выводить дни только из месяцев
  - `updated_at`, опционально `is_active` на уровне ячейки
  - `UNIQUE (tier, period_months)`

- Таблица `subscription_tier_pricing` **оставить** для **общих** полей тарифа: `name_ru`, `short_description_ru`, `bullets_json`, `display_order`, `is_active` (без дублирования этих текстов 9 раз). Поля `price_cents` / `period_days` в старых строках: **миграция** — либо удалить из использования в пользу новой таблицы, либо заполнить новую таблицу из текущих значений и пометить legacy-поля deprecated.

**Вариант B:** `JSONB` с ключами периодов в одной строке тарифа — хуже для ограничений, индексов и аудита по полю.

## API (черновик контракта)

- **Тренер:** ответ `GET /api/webapp/trainer/subscription/catalog` расширить, например:
  - `tiers[]`: как сейчас метаданные + **`prices_by_period`: `{ "1": 190000, "3": 500000, "12": ... }` в центах** (или массив объектов).
- **Админ:**
  - `GET /api/webapp/admin/subscription-tiers` — те же 3 тарифа + **все 9 цен** (или отдельный `GET .../period-prices`).
  - `PATCH` — либо один эндпоинт с телом «патч матрицы», либо `PATCH .../subscription-tiers/{tier}/periods/{months}` для одной ячейки.
- **Mock checkout:** тело `{ "tier": "...", "period_months": 1|3|12 }`; сервер подставляет `price_cents` и `period_days` из новой таблицы; при несовпадении суммы с клиентом — **считать сумму только на сервере** (клиент для UX может слать ожидаемую сумму опционально, решение принимает бэкенд).

## UI админки (`admin-subscription-tiers.html`)

- Сетка: строки = тарифы (название из текущих данных), столбцы = 1 мес / 3 мес / 12 мес.
- В каждой ячейке: поле ввода цены (BYN), валидация ≥ 0.
- Сохранение: по кнопке «Сохранить» или автосейв по ячейке — на усмотрение UX; аудит уже есть для tier pricing — **расширить аудит** на изменения по `(tier, period_months)`.

## UI тренера (`trainer-subscription.html`)

- Удалить или заменить `periodDiscounts` на данные из каталога.
- `renderTiers` / `updateCheckoutButton`: брать цену для `(selectedTier, selectedPeriod)` из ответа API.
- Итог и кнопка оплаты — из тех же данных.

## Тесты и инварианты

- Юнит/интеграция: для каждой из 9 комбинаций цена из БД попадает в каталог и в mock-checkout; `expires_at` соответствует выбранному периоду.
- Регрессия: старые подписки в `trainer_subscriptions` не ломаются.

## Зависимости и риски

- **Миграция данных:** из 3 строк заполнить 9 ячеек (например продублировать текущую месячную цену в колонку 1 мес; для 3 и 12 — либо формула на момент миграции, либо вручную задать в админке после деплоя).
- **Согласованность с реальной оплатой:** если позже подключается эквайринг, сумма должна браться с сервера — план это закладывает.
