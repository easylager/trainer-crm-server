# План оптимизации: каталог тренеров — скорость без задержек

**Цель:** карточки тренеров (список + деталь со слотами и фото) открываются мгновенно. Пользователь в Беларуси, готовность вкладываться в инфраструктуру.

**Текущая схема (почему медленно):**
- Сервер локально, доступ через **cloudflared tunnel**.
- Фото в **Railway S3 (Германия)**.
- Каждое фото: браузер → туннель → наш API → S3 (Германия) → наш API → туннель → браузер = **двойной круг + далёкий S3**.
- Слоты: при открытии карточки отдельный запрос `/client/slots`; внутри — `get_trainer()` + `list_slots()` = два обращения к БД и ещё один round-trip по туннелю.

---

## 1. Фото: убрать proxy, отдавать прямые URL (критично)

**Сейчас:** фронт дергает `/api/public/photos/{file_key}` → бэкенд качает из S3 и отдаёт тело. Все запросы идут через твой сервер и туннель.

**Нужно:** браузер грузит фото **напрямую** с быстрого источника (CDN или S3 с близким регионом), без proxy через API.

### Варианты

| Вариант | Описание | Плюсы | Минусы |
|--------|----------|--------|--------|
| **A. Presigned GET URL** | При выдаче списка/тренера подставлять в каждый `file_key` готовый временный URL (presigned) на S3. Фронт использует его в `img.src`. | Не нужно менять S3, только бэкенд отдаёт URL вместо пути. | S3 в Германии — первый запрос всё равно далёкий; подходит как быстрый шаг, потом добавить CDN. |
| **B. Публичный бакет + CDN** | Сделать чтение бакета публичным (или через один публичный домен). Перед S3 поставить CDN (Cloudflare, Bunny, KeyCDN). В API отдавать URL вида `https://cdn.yourdomain.com/photos/...`. | После прогрева кэша фото отдаются с edge, один раз тянем из S3. | Нужен домен и настройка CDN. |
| **C. Cloudflare R2 + CDN** | Хранить фото в R2, раздавать через Cloudflare (бесплатный egress в сторону клиента). В API отдавать `https://<r2-public-domain>/...` или кастомный домен. | Низкая задержка, предсказуемая стоимость. | Миграция с Railway S3 на R2 (скрипт копирования). |

**Рекомендация:**  
- **Краткосрочно:** A (presigned URL). Добавить в S3 слой `presign_get_url(file_key, expires_in=3600)` и в ответах API для тренеров отдавать не путь `/api/public/photos/...`, а готовый `photo_url` (и при необходимости `photo_list_url` для превью). Фронт везде использует эти URL. Фото перестают идти через твой сервер — сразу видимое облегчение.  
- **Среднесрочно:** B или C. Либо публичный бакет + CDN перед текущим S3, либо перенос в R2 и раздача через Cloudflare. Тогда в API отдавать уже CDN/R2 URL вместо presigned S3.

**Реализация (шаг A):**
- В `src/infrastructure/s3.py`: функция `presign_get_url(file_key, expires_in=3600)` → возвращает URL.
- В репозитории/use case, где собирается ответ с тренерами (список и один тренер), для каждой фотки добавлять поле `url` (и при необходимости `list_url`) из presign, не меняя логику хранения `file_key`.
- Конфиг: опция `PHOTO_PRESIGNED_EXPIRES_SEC` (по умолчанию 3600). Если S3 не настроен — оставлять текущий вариант через `/api/public/photos/`.
- Фронт (catalog, везде где есть `photoUrl(fileKey)`): если в объекте тренера/фото пришло `photo_url` / `list_url` — использовать его, иначе fallback на `photoUrl(fileKey)`.

## 2. CDN для фото (обязательно для «без задержек»)

- **Без CDN:** даже с presigned URL запрос идёт в Германию → для Беларуси RTT большой.
- **С CDN:** первый запрос по ключу уходит в origin (S3/R2), ответ кэшируется на edge; последующие — из POP (Польша/Европа/при наличии — ближе к СНГ).

**Практично:**
- Либо **Cloudflare** перед Railway (если Railway отдаёт статику по своему URL): проксируешь только путь к фото через Cloudflare, кэш по `Cache-Control`.
- Либо **перенос фото в R2** и раздача через тот же Cloudflare — egress бесплатный, один раз настроил и фото всегда с edge.
- Либо отдельный **Bunny CDN** (есть POP в Варшаве и др.) с origin = S3 или свой storage.

В API тогда отдаёшь не прямой URL S3, а URL вида `https://photos.yourdomain.com/...` (или домен CDN), чтобы браузер всегда ходил в CDN.

## 3. Слоты и карточка тренера: меньше round-trip и лишних запросов

**Сейчас:** открытие карточки → `loadSlotsForTrainer(t.id)` → `GET /api/webapp/client/slots?trainer_id=X` → на бэкенде `get_trainer()` (для `min_hours_before_booking` и имени) + `list_slots()`.

**Что сделать:**
1. **В ответ списка тренеров** добавить в `profile` поле `min_hours_before_booking` (уже есть в БД в `trainer_profiles`). Тогда при открытии карточки фронт уже знает `min_hours`.
2. **Эндпоинт слотов** оставить один запрос, но внутри **не вызывать `get_trainer()`** для имени и `min_hours`, если они могут прийти от клиента (опционально query-параметры `min_hours`, `trainer_name`). Либо всегда отдавать `min_hours` и имя в ответе слотов, беря их из кэша или одного лёгкого запроса только к `trainer_profiles` (без фото и услуг).
3. **Опционально — объединённый запрос:** один эндпоинт вида `GET /api/webapp/client/trainer-card?trainer_id=X`, который возвращает `{ trainer (минимальный набор полей), slots }`. Тогда открытие карточки = один запрос вместо «слоты + неявный get_trainer». Можно ввести позже, после того как фото и CDN уже дадут основной выигрыш.

Приоритет: пункт 1 (дать `min_hours` в списке) и по возможности убрать лишний `get_trainer()` в `/client/slots` — меньше работы на бэкенде и стабильнее задержка.

---

## 4. Кэширование на бэкенде

- **Список тренеров** `GET /api/public/trainers`: ответ можно кэшировать на 1–2 минуты (по `city_id`, `service_id`, `arena_id`, `offset`, `limit`). При изменении данных тренера/расписания инвалидировать по ключу или TTL.
- **Слоты** `GET /api/webapp/client/slots?trainer_id=X`: кэш на 1–5 минут по `trainer_id` (слоты меняются не каждую секунду). При создании/удалении слотов или брони — сброс кэша для этого тренера.

Реализация: in-memory (например `cachetools.TTLCache`) для одного инстанса или **Redis** при нескольких воркерах. Ключи вида `trainers:list:{hash(params)}`, `slots:{trainer_id}`.

---

## 5. Фронт: приоритет первой картинки и lazy load

- Для **первой карточки в списке** (или первых 2–3): использовать `<link rel="preload" as="image" href="...">` для превью, чтобы браузер начал качать её сразу.
- Остальные фото оставить с `loading="lazy"` (уже есть в разметке).
- После перехода на прямые URL фото (presigned или CDN) не менять логику lazy — просто источник станет быстрее.

---

## 6. Инфраструктура и туннель

- **Cloudflared tunnel** добавляет задержку и зависимость от одного канала. Для продакшена лучше **нормальный хостинг** (Railway, Fly.io, VPS в EU East и т.п.) с постоянным HTTPS. Тогда API и редиректы на фото/CDN стабильнее.
- **БД:** оставить там, где сейчас (локально или managed). Главное — не гонять через тот же канал большие тела (фото через API уже убираем).
- **Регион:** если клиенты в Беларуси, оптимально API и origin фото в одном регионе (например EU Central/East). Railway Германия приемлемо; основное — фото не через API, а через CDN.

---

## 7. Что уже сделано (код)

- **Presigned GET URL для фото:** в ответах `GET /api/public/trainers` и `GET /api/public/trainers/{id}` у каждого фото добавлены поля `url` и при наличии — `list_url`. Фронт каталога использует их (прямая загрузка с S3), иначе fallback на `/api/public/photos/...`.
- **Preload первой картинки** в списке тренеров.
- **min_hours_before_booking** в ответе списка тренеров; при открытии карточки фронт передаёт `min_hours` и `trainer_name` в `GET /client/slots`, чтобы не вызывать `get_trainer()` лишний раз.
- **Кэш (in-memory TTL):** список тренеров — 90 сек, слоты по тренеру — 60 сек.

## 8. Порядок внедрения (кратко)

1. **Фото не через proxy**  
   - Добавить presigned GET URL в S3, в ответы API с тренерами подставлять `photo_url` / `photo_list_url`.  
   - Фронт использовать эти URL. Замерить: список и карточка без запросов фото через твой сервер.

2. **CDN для фото**  
   - Настроить один домен/путь под фото (Cloudflare перед S3 или R2).  
   - В API отдавать уже URL на этот домен (вместо presigned S3, если origin — S3 за CDN).  
   - Выставить `Cache-Control` для фото (например 1 день).

3. **Слоты и список**  
   - Добавить `min_hours_before_booking` в ответ списка тренеров.  
   - Упростить `/client/slots` (убрать лишний `get_trainer()` где возможно).  
   - Опционально: кэш списка и слотов (in-memory или Redis).

4. **Фронт**  
   - Preload первой (или первых двух) превью в списке.  
   - Остальное уже с lazy.

5. **Продакшен**  
   - Вынести сервер с туннеля на постоянный хостинг с HTTPS.  
   - Оставить туннель только для разработки/тестов.

## 9. Метрики «до/после»

Имеет смысл замерить:

- **Список тренеров (10 карточек):** время до первого отрисованного превью (FCP / время до первого изображения) и до полной отрисовки списка.
- **Открытие карточки:** время до появления слотов и до загрузки большого фото (если есть).
- Количество запросов к твоему API при открытии списка и при открытии одной карточки (цель — минимум запросов и ноль запросов фото через API).

После шага 1 (presigned + фронт) основная задержка от фото через туннель уйдёт; после шага 2 (CDN) задержка загрузки фото станет минимальной за счёт edge-кэша.

## 10. Что нужно от тебя (действия)

1. **Ничего не обязательно для текущего кода**  
   С presigned URL фото уже грузятся напрямую с S3 (мимо твоего сервера и туннеля). Если S3 настроен (Railway), всё заработает после деплоя.

2. **Опционально в `.env`:**
   - `PHOTO_PRESIGNED_EXPIRES_SEC=3600` — срок жизни ссылки на фото в секундах (по умолчанию 3600).

3. **CDN для фото (включено в коде):**
   - В `.env` задай **`PHOTO_CDN_BASE_URL`** — базовый URL, по которому доступны фото (например `https://cdn.yourdomain.com` или публичный URL R2).
   - API будет отдавать ссылки на фото как `{PHOTO_CDN_BASE_URL}/{file_key}` вместо presigned S3. Браузер грузит фото с CDN; в списке и в карточке тренера отображается подпись «Фото: через CDN».
   - **Варианты настройки CDN:**
     - **Cloudflare R2:** создать бакет, включить публичный доступ или привязать свой домен (например `photos.yourdomain.com`). Загружать фото в R2 (или синхронизировать из текущего S3). В `.env` указать `PHOTO_CDN_BASE_URL=https://photos.yourdomain.com` (или публичный URL R2).
     - **Cloudflare перед Railway S3:** поднять прокси/Worker, который по пути вида `/trainers/...` дергает S3 и отдаёт ответ с кэшированием. Домен вида `https://cdn.yourdomain.com` указывает на этот прокси. В `.env`: `PHOTO_CDN_BASE_URL=https://cdn.yourdomain.com`.
   - После настройки перезапусти API и проверь в каталоге: внизу списка и в карточке тренера должно быть «Фото: через CDN».
4. **Продакшен без туннеля:** поднять API на постоянном хостинге (Railway/Fly.io/VPS) с HTTPS и использовать его в боте и Mini App вместо cloudflared.

5. **Проверка, почему «ничего не поменялось»:**
   - **Откуда грузятся фото:** открой каталог, в браузере DevTools → вкладка **Network** → обнови список тренеров. Посмотри запросы к картинкам: если они идут на **твой API** (`/api/public/photos/...`) — значит, прямые URL не используются (S3 не настроен или presign не сработал). Если запросы уходят на **внешний домен** (Railway storage и т.п.) — фото уже грузятся напрямую с S3.
   - **Ответ API:** открой в браузере `GET /api/public/trainers?limit=5` (с тем же origin). В JSON у первого тренера в `photos[0]` посмотри поля: есть ли **`url`** или **`list_url`** (длинная ссылка с `X-Amz-...`)? Если **нет** — у тебя либо локальное хранилище (`LOCAL_STORAGE_PATH` в .env), либо не заданы S3-ключи. Presigned URL выдаётся **только при настроенном S3** (S3_ENDPOINT, S3_ACCESS_KEY, S3_SECRET_KEY).
   - В ответе списка тренеров есть поле **`_photo_source`**: `"direct"` — хотя бы у одного фото есть прямая ссылка, `"proxy"` — все фото отдаются через proxy (значит, S3 не используется для выдачи ссылок).
   - Если фото уже грузятся с S3 напрямую, но всё равно медленно — это задержка до серверов S3 (например, Германия). Ускорит только **CDN** перед S3 (см. план выше).
