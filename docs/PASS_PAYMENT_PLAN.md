# План реализации оплаты абонементов (не реализовано)

Текущий MVP: кнопка «Оплатить» создаёт покупку со статусом `paid` без реального платежа. Ниже — план подключения реальной оплаты.

---

## 1. Общая схема

1. **Клиент** в Mini App выбирает продукт и нажимает «Оплатить».
2. **Фронт** вызывает API `POST /api/webapp/client/pass-purchase-intent` (или оставляем один эндпоинт с флагом): создаётся запись в `pass_purchases` со статусом `pending`, возвращается `purchase_id` и (при выборе платёжки) ссылка на платёжную страницу или `payment_url`.
3. **Клиент** переходит по ссылке на страницу платёжного провайдера (Stripe, ЮKassa, и т.п.), оплачивает.
4. **Провайдер** отправляет **webhook** на наш бэкенд (например `POST /api/webhooks/payment-success`).
5. **Бэкенд** по `payment_external_id` или по `purchase_id` в теле webhook находит покупку, проверяет подпись/сумму, переводит статус в `paid`, создаёт `pass_instance`, генерирует `redemption_token`, (опционально) отправляет email клиенту с ссылкой/QR.
6. **Клиент** видит абонемент в «Мои абонементы» (при следующем открытии или по редиректу после оплаты).

---

## 2. Выбор платёжной системы

- **Беларусь:** ЮKassa (Яндекс), Stripe (если есть юрлицо за рубежом), местные эквайринги (например через банк-интеграцию). Удобно начать с **ЮKassa** (поддержка BYN, webhook, документация).
- **Интеграция:** создание платежа через API провайдера (idempotency key = `purchase_id`), возврат `confirmation_url` клиенту; webhook с типом `payment.succeeded` (или аналог) — по нему обновляем покупку и создаём pass.

---

## 3. Изменения в коде (при реализации)

- **Таблица `pass_purchases`:** уже есть `payment_external_id`, `status` (pending/paid/refunded). Добавить при необходимости `payment_provider`, `payment_created_at`.
- **API:**  
  - Вариант A: отдельный `POST /client/pass-purchase-intent` создаёт покупку `pending`, возвращает `payment_url`; клиент после оплаты попадает на наш URL (success_url), мы показываем «Оплачено» и редирект в «Мои абонементы».  
  - Вариант B: текущий `POST /client/pass-purchase` при наличии настройки «реальная оплата» создаёт `pending`, возвращает `payment_url`; при отсутствии настройки — текущее поведение (сразу `paid`).
- **Webhook:** один роут (например под префиксом `/api/webhooks/`), проверка подписи (секрет провайдера), поиск покупки по `object.id` или `metadata.purchase_id`, переход в `paid`, вызов существующей логики создания `pass_instance` и (позже) отправки email.
- **Безопасность:** не доверять данным из webhook без проверки подписи; не создавать pass дважды (идемпотентность по `payment_external_id` или `purchase_id`).

---

## 4. Email (позже)

После перевода покупки в `paid` можно отправлять клиенту письмо со ссылкой на абонемент (`/r/<token>` или страницу «Мои абонементы») и/или с QR. Для этого нужен сервис отправки (SMTP, SendGrid, и т.д.) и шаблон письма.

---

## 5. Рефанды

При возврате средств провайдер пришлёт webhook (например `payment.refunded`). Реакция: пометить покупку `refunded`, деактивировать или удалить связанный `pass_instance` (по политике продукта).

---

Итог: текущий поток «Оплатить» → сразу `paid` остаётся как тестовый; при подключении оплаты добавляются шаг создания `pending` + `payment_url`, webhook и переход в `paid` с созданием pass и опциональной рассылкой.
