# Подписки: гибкость, группы, аналитика

Черновик для пересмотра политики подписок после появления **когорт (групп)** и запроса на независимые комбинации (например «нужна статистика, группы не нужны»). Источник правды по домену групп: [TRAINING_GROUPS.md](TRAINING_GROUPS.md).

**Реализовано (конструктор):** активная строка `trainer_subscriptions` с каноническим `tier = crm` и JSONB `modules` (`online`, `analytics`, `groups`); надбавки в `subscription_module_period_pricing`; гейты в `get_trainer_entitlements` / `trainer_has_*_access`; в Mini App — `GET /trainer/subscription/catalog` отдаёт `constructor` + legacy `tiers`; mock-checkout принимает `modules` или legacy `tier`.

---

## 1. Как сейчас

- Одна **линейная** шкала: `none` → `crm` → `online` → `analytics` (`SUBSCRIPTION_TIER_LEVELS` в `src/infrastructure/db/models.py`).
- Проверка доступа: `tier_satisfies(current, required)` в `src/application/subscription_tier_use_cases.py` — «выше по лестнице» включает всё ниже.
- **Аналитика / статистика** привязаны к ступени **`analytics`** (не к отдельному флагу).

Ограничение: любая новая «вертикаль» (группы, отдельный модуль) либо **встраивается в ту же линию** (комбинаторный взрыв: `crm+groups`, `analytics_no_groups`…), либо нужна **вторая ось** прав.

---

## 2. Зачем менять

| Персона | Желание |
|--------|---------|
| Индивидуальный тренер | CRM + онлайн + **отчёты**, групп нет |
| Тренер с когортами | CRM + **группы**, отчёты не критичны (или наоборот) |
| «Максимальный» пакет | Всё |

На линейной модели это выражается только ценой **целых ступеней**, а не модулей — неудобно для прайса и для кода.

---

## 3. Целевая модель (набросок)

### 3.1. Два слоя

1. **Базовый тариф (как сейчас)** — `crm` | `online` | `analytics`  
   Описывает **канал работы с клиентами и каталогом**: ручная запись, публикация, базовые сценарии.  
   Можно **оставить** иерархию для этого слоя без изменений.

2. **Модули (entitlements / add-ons)** — независимые флаги или подписки со сроком:

   | Код (пример) | Смысл |
   |--------------|--------|
   | `analytics_module` | Расширенная статистика / отчёты (если выносим из `analytics` tier) |
   | `groups` | Доступ к когортам: API групп, мини-приложение, материализация слотов и т.д. |

Доступ к фиче = **`tier_satisfies(base, min_base_for_feature)` AND `has_entitlement(feature)`** (или эквивалент одной функцией `trainer_can(session, trainer_id, capability)`).

### 3.2. Варианты продуктовой упаковки

- **A. Модули только как add-on** к `online` (или к `crm`): минимальная база + докупка «группы» / «аналитика».
- **B. Старые тарифы = пакеты**: например текущий `analytics` автоматически выставляет `analytics_module=true` при миграции; новые продажи — по новой сетке.
- **C. Группы требуют минимум `crm`** (бессмысленно без расписания/клиентов) — в коде: `tier_satisfies(tier, SUBSCRIPTION_TIER_CRM) and has_groups`.

Конкретные цены и названия тарифов — вне этого документа; здесь только **форма** модели.

---

## 4. Данные (эскиз схемы)

Минимально инвазивные варианты:

1. **JSONB на `trainer_subscriptions` или `trainers`:**  
   `entitlements: {"groups": true, "analytics": true}` + `expires` на уровне строки подписки или отдельные даты на ключ (сложнее).

2. **Таблица `trainer_entitlements`:**  
   `trainer_id`, `code` (enum/text), `expires_at`, `source` (plan | admin | promo).

3. **Отдельные строки «подписок на модуль»** в существующей биллинг-модели — если уже планируется несколько активных продуктов на тренера.

Рекомендация для эволюции: **явная таблица или enum-коды**, чтобы не размазывать логику по JSON без миграций.

## 5. Где трогать код (инвентаризация)

Ниже — точки, где сегодня завязка на **tier**; при введении entitlements их нужно перевести на общий **capability check**.

| Область | Файл (ориентир) | Сейчас |
|--------|------------------|--------|
| Статистика тренера (Mini App API) | `src/api/routes/webapp.py` | `tier_satisfies(..., SUBSCRIPTION_TIER_ANALYTICS)` |
| Статистика / раздел бота | `src/bot/handlers/trainer_handlers.py` | то же для аналитики |
| Меню тренера (показ пунктов) | `src/bot/trainer_menu_commands.py` | `include_stats` = analytics tier |
| Абстракции | `src/application/subscription_tier_use_cases.py` | `trainer_has_tier_access`, `tier_satisfies` |

**Группы (после появления эндпоинтов/UI):** все `POST/PATCH` по когортам, материализация слотов, публичный список групп тренера — отдельный guard: `has_groups` + минимальный базовый tier.

## 6. Стратегия миграции

1. **Фаза 0:** зафиксировать enum capability и функцию `trainer_has_capability(session, trainer_id, cap)` внутри `subscription_tier_use_cases` (или рядом), внутри которой **пока** только `tier_satisfies` (без изменения поведения).

2. **Фаза 1:** для существующих активных подписок с `tier=analytics` выставить в БД entitlement `analytics_module=true` (или считать tier достаточным условием до пересмотра прайса).

3. **Фаза 2:** вынести «статистика» из обязательности именно `analytics` tier в пользу `analytics_module` **или** оставить tier как синоним модуля для обратной совместимости.

4. **Фаза 3:** продавать `groups` отдельно; UI оплаты в `trainer-subscription.html` / админка цен — второй ряд продуктов.

Тесты: расширить `tests/application/test_subscription_tier.py` и интеграционные проверки webapp для stats с моками entitlements.

## 7. Открытые продуктовые вопросы

- Нужен ли **онлайн-каталог** для групп в MVP продаж модуля «группы», или достаточно `crm` + группы внутри CRM?
- **Аналитика** остаётся топ-ступенью базового тарифа или полностью переезжает в модуль (и тогда `analytics` tier = «всё включено» legacy)?
- Один счёт на тренера vs отдельные сроки окончания модулей?

После ответов можно зафиксировать **матрицу capability × минимальный tier** одной таблицей в этом файле.
