# Задачи: абонементы и сертификаты (без приёма оплаты)

Клиент платит тренеру напрямую → тренер выдаёт абонемент/сертификат в приложении → клиент видит и получает уведомление → списание занятий автоматически при проведённом бронировании.

---

## Фаза 1: Модель данных и выдача абонементов

### Задача 1.1 — Таблица экземпляров абонементов (pass instances)
- Таблица `pass_instances`: `id`, `client_id`, `pass_product_id` (FK на trainer_pass_products), `sessions_remaining` (int), `sessions_total` (int, копия на момент выдачи), `issued_at` (datetime), опционально `expires_at`, `status` (active / used_up / cancelled).
- Индексы: по `client_id`, по `trainer_id` (через product), по статусу для выборки активных.
- Миграция Alembic.

### Задача 1.2 — API и use case: выдать абонемент клиенту
- Use case: `issue_pass_to_client(session, trainer_id, client_id, pass_product_id)` — проверка что продукт принадлежит тренеру и активен, что клиент «доступен» тренеру (есть хотя бы одно бронирование или клиент в списке тренера), создание записи в `pass_instances` с `sessions_remaining = product.sessions_total`.
- API: `POST /api/webapp/trainer/clients/{client_id}/pass-issue` body `{ "pass_product_id": 123 }`. Только для тренера (initData).
- Ответ: созданный экземпляр (id, sessions_remaining, product name и т.д.) для отображения в UI.

### Задача 1.3 — Тренер: UI «Выдать абонемент»
- В карточке клиента (trainer-clients) или в разделе «Абонементы» тренера: кнопка «Выдать абонемент» → выбор продукта из списка своих pass products → подтверждение → вызов API из п.1.2.
- После успеха — тост «Абонемент выдан», обновление блока «Абонементы клиента» в карточке (если он там отображается).

## Фаза 2: Клиент видит абонементы и уведомления

### Задача 2.1 — API: список абонементов клиента
- API: `GET /api/webapp/client/passes` (или уже есть аналог) — для текущего клиента (по initData/telegram_id) вернуть список активных (и при желании использованных) pass_instances с полями: product name, trainer name, service name, sessions_total, sessions_remaining, issued_at, expires_at, price за занятие (price_cents / sessions_total).
- Use case: `list_client_pass_instances(session, client_telegram_id)` с join на trainer_pass_products и services, trainer_profiles для имени тренера.

### Задача 2.2 — Уведомление клиенту при выдаче абонемента
- После успешного `issue_pass_to_client` отправить клиенту уведомление в бот (если client.telegram_id есть): «Вам выдан абонемент: [название], [N] занятий. Осталось: [N]. Тренер: [имя].» + кнопка «Мои абонементы» (открыть Mini App или раздел в боте).
- Использовать существующий механизм отправки сообщений клиенту (client bot).

### Задача 2.3 — Меню и раздел «Абонементы» у клиента
- В боте клиента: пункт меню «Абонементы» (или «Мои абонементы»). По нажатию — открыть Mini App страницу `/webapp/client-passes` или отдать список прямо в боте (если без Mini App).
- Страница client-passes (Mini App): заголовок «Мои абонементы», список карточек: тренер, услуга, «N из M занятий», осталось X, цена за занятие, срок действия (если есть). Пустое состояние: «Пока нет абонементов».

## Фаза 3: Автоматическое списание с абонемента

### Задача 3.1 — Правило «занятие проведено»
- Зафиксировать в коде одно правило: списывать занятие при переходе бронирования в статус `completed` (или при установке «проведено»). Либо: слот в прошлом + статус confirmed — и тогда один раз при ночном джобе или при открытии детали бронирования переводим в completed и списываем.
- Рекомендация: явный переход в `completed` (тренер нажал «Проведено» или автоматически после даты слота) — тогда в этом же месте вызывать списание.

### Задача 3.2 — Use case: списать одно занятие с абонемента по бронированию
- Use case: `redeem_pass_session_for_booking(session, booking_id)` (или `on_booking_completed(session, booking)`).
  - Найти booking по id, проверить status = completed (или вызывать только когда статус только что стал completed).
  - Взять `client_id`, `trainer_id`, `service_id` из бронирования.
  - Найти активный pass_instance: client_id + продукт этого тренера с `service_id` = booking.service_id (или service_id IS NULL = любой), sessions_remaining > 0. Если несколько — выбрать по политике (например с минимальным expires_at или минимальным sessions_remaining).
  - Уменьшить `sessions_remaining` на 1. Если стало 0 — обновить status на `used_up`.
  - Опционально: запись в таблицу `pass_redemptions` (booking_id, pass_instance_id, redeemed_at) для истории.
- Вызывать этот use case из места, где бронирование переводится в completed (бот или API).

### Задача 3.3 — Интеграция в поток «проведение занятия»
- В боте тренера (или в API) при действии «Отметить занятие проведённым» / «Завершить» после обновления статуса бронирования на `completed` вызвать `redeem_pass_session_for_booking(session, booking_id)`.
- Если у клиента не нашлось подходящего абонемента — не падать, просто не списывать (занятие прошло «без абонемента»). Опционально: уведомить тренера «У клиента нет абонемента по этой услуге».

## Фаза 4: Сертификаты — продукты, выдача тренером, виртуальные файлы

### Задача 4.1 — Таблицы продуктов и экземпляров сертификатов
- Таблица `certificate_products`: справочник продуктов сертификатов на уровне тренера:
  - `id`, `trainer_id`
  - `name` (например «5 персональных тренировок», «Подарочный сертификат 150 BYN»)
  - `sessions_count` **или** `amount_cents` (на MVP выбрать одну модель; вторую можно добавить позже)
  - `expires_in_days` (nullable)
  - `is_active` (bool)
- Таблица `certificate_instances` (без welcome‑ссылок и без погашения на стороне тренера):
  - `id`, `trainer_id`, `certificate_product_id` (FK)
  - `purchased_by_name` (nullable, текст)
  - `recipient_name` (nullable, текст)
  - `code` (уникальный код, например `CERT-XXXX-YYYY`)
  - `status`:
    - `issued` — создан, не привязан к клиенту
    - `activated` — клиент активировал сертификат, средства/сессии уже на его балансе
    - `cancelled`
    - `expired`
  - `amount_cents` / `sessions_count` (зафиксированный номинал на момент выдачи)
  - `activated_client_id` (nullable, FK на clients)
  - `issued_at`, `activated_at`, `expires_at` (nullable)
- Индексы: `trainer_id`, `code` (unique), `activated_client_id`, `status`.

### Задача 4.2 — API и use case: создание и список продуктов сертификатов
- Use case: `create_certificate_product(session, trainer_id, name, sessions_count | amount_cents, expires_in_days | null)` с проверкой принадлежности тренеру.
- Use case: `list_certificate_products(session, trainer_id)` — вернуть все активные продукты тренера.
- API:
  - `POST /api/webapp/trainer/certificate-products` body `{ "name": "...", "sessions_count": 5, "expires_in_days": 180 }`.
  - `GET /api/webapp/trainer/certificate-products` — список продуктов для UI.

### Задача 4.3 — API и use case: выдать (создать) экземпляр сертификата
- Use case: `issue_certificate_instance(session, trainer_id, certificate_product_id, purchased_by_name | null, recipient_name | null)`:
  - проверить, что продукт принадлежит тренеру и активен;
  - сгенерировать уникальный `code`;
  - рассчитать `expires_at` из `expires_in_days` продукта (если задано);
  - создать запись в `certificate_instances` со статусом `issued`.
- API: `POST /api/webapp/trainer/certificates` body:
  - `{ "certificate_product_id": 1, "purchased_by_name": "Мария", "recipient_name": "Иван" }`.
- Ответ: созданный экземпляр (id, code, название продукта, срок действия, ссылка на виртуальный сертификат — см. 4.4).

### Задача 4.4 — Виртуальный бренд‑сертификат (PDF/картинка)
- Генерировать красивый виртуальный сертификат (PDF/PNG) при создании экземпляра:
  - данные: логотип/имя тренера, название продукта, номинал, `recipient_name` (если есть), `purchased_by_name` (если есть), `code`, `issued_at`, `expires_at`, краткая инструкция.
  - инструкция без welcome‑ссылок: в тексте указать явный сценарий:
    - «Чтобы использовать сертификат, зайдите в бота/веб‑приложение тренера, выберите “У меня есть сертификат” и введите код: XXXX‑YYYY».
- Технически:
  - HTML‑шаблон сертификата + сервис генерации PDF/PNG.
  - Хранить путь/URL к файлу в `certificate_instances.file_url`.
- API: `GET /api/webapp/trainer/certificates/{id}/file` — вернуть ссылку/файл для скачивания.
- Важно: **никаких welcome‑ссылок внутри сертификата** — только код и текстовая инструкция.

### Задача 4.5 — Тренер: UI «Сертификаты»
- В веб‑панели тренера:
  - раздел «Сертификаты»:
    - вкладка «Продукты» — CRUD по certificate_products;
    - вкладка «Выданные сертификаты» — таблица certificate_instances: дата, продукт, код, статус, срок действия, получатель.
  - Форма «Выдать сертификат»:
    - выбор продукта;
    - поля `purchased_by_name`, `recipient_name` (опционально);
    - действие → вызов API из 4.3 → показ кода, кнопка «Скопировать код», кнопка «Скачать сертификат (PDF/PNG)».

## Фаза 5: Активация сертификатов клиентом и интеграция с абонементами/балансом

### Задача 5.1 — Use case: активация сертификата по коду на стороне клиента
- Use case: `activate_certificate_by_code(session, client_id, code)`:
  - найти `certificate_instance` по `code`;
  - проверить:
    - `status == issued`,
    - `expires_at` не в прошлом (если задано);
  - в транзакции:
    - проставить `activated_client_id = client_id`, `status = activated`, `activated_at = now()`;
    - начислить клиенту абонемент/баланс:
      - либо создать `pass_instance` на основе `certificate_product` и связать через `source_certificate_instance_id`;
      - либо пополнить денежный/сессионный баланс клиента у этого тренера;
    - записать событие в историю (лог активации сертификата).

### Задача 5.2 — Точки входа для клиента: «У меня есть сертификат»
- Для **нового клиента** (первый вход):
  - после приветственного экрана в боте/веб‑апке добавить опцию:
    - «У меня есть подарочный сертификат»;
  - сценарий:
    - клиент вводит код;
    - вызываем `activate_certificate_by_code`;
    - показываем результат: «Сертификат активирован, вам начислено N занятий / сумма X у тренера [имя]» + CTA «Записаться на тренировку».
- Для **существующего клиента**:
  - в меню бота или в разделе профиля добавить пункт «Активировать сертификат»;
  - повторно использовать тот же сценарий ввода кода и use case.

### Задача 5.3 — API и UI «Мои сертификаты» у клиента
- API: `GET /api/webapp/client/certificates`:
  - вернуть список certificate_instances, где `activated_client_id = текущий клиент`;
  - поля: тренер, продукт, номинал, код, статус, `issued_at`, `activated_at`, `expires_at`, источник (например, «подарок»).
- В боте/веб‑клиента:
  - пункт меню «Сертификаты»;
  - страница `client-certificates` (Mini App или список в боте):
    - карточки: тренер, название продукта, номинал, статус (активирован / истёк / отменён), даты;
    - пустое состояние: «Пока нет активированных сертификатов».

### Задача 5.4 — Авто‑истечение сертификатов
- Фоновая задача (cron/periodic job):
  - раз в день находить `certificate_instances` со статусом `issued` или `activated`, где `expires_at < now()`;
  - обновлять `status` на `expired`;
  - при необходимости уведомлять клиента/тренера (опционально).

### Задача 5.5 — Интеграция с абонементами/балансом (без явного списания сертификатов тренером)
- При активации сертификата:
  - если используется модель «пакет занятий»:
    - создать `pass_instance` с `sessions_remaining = certificate.sessions_count`;
    - сохранить `source_certificate_instance_id` в pass_instance для аналитики;
  - если используется денежная модель:
    - пополнить денежный баланс клиента у этого тренера на `certificate.amount_cents`.
- Списание занятий/денег при проведении тренировок **остаётся в существующей логике абонементов/баланса**:
  - тренер не «погашает сертификат» вручную;
  - он просто списывает из абонемента/баланса (через уже реализованные механики);
  - сертификат живёт как источник появления этого абонемента/баланса и как сущность для отчётности.

## Порядок выполнения (рекомендуемый)

1. **Фаза 1** (1.1 → 1.2 → 1.3) — чтобы тренер мог выдавать абонементы.
2. **Фаза 2** (2.1 → 2.2 → 2.3) — чтобы клиент видел абонементы и получал уведомление.
3. **Фаза 3** (3.1 → 3.2 → 3.3) — автоматическое списание.
4. **Фаза 4** (4.1 → 4.2 → 4.3 → 4.4 → 4.5) — сертификаты: продукты, выдача и виртуальные файлы у тренера.
5. **Фаза 5** (5.1 → 5.2 → 5.3 → 5.4 → 5.5) — активация сертификатов клиентом и интеграция с абонементами/балансом (без welcome‑ссылок и без ручного погашения сертификатов на стороне тренера).

Зависимости: 2.1 опирается на 1.1–1.2; 3.2 опирается на 1.1; 4.5 опирается на 4.1–4.3; 5.1–5.3 опираются на 4.1–4.3 и на модель абонементов.
