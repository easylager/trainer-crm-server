# Нагрузочное тестирование API

## Методология: масштабируемость (а не rate limit)

**Цель:** оценить, хватит ли приложению и БД ресурсов под ожидаемый **легитимный** трафик, без «лагов» в смысле p95/p99 latency и без роста ошибок.

**Важно:** абсолютной гарантии «в проде не залагает» не даёт ни один прогон — даётся **снижение риска** за счёт повторяемых сценариев, близкого к бою стенда и явных **SLO** (см. ниже).

### 1. Разделить два режима

| Режим | Rate limit | Зачем |
|--------|------------|--------|
| **Capacity / масштабируемость** | `API_RATE_LIMIT_ENABLED=false` на **отдельном стенде** (staging / load env) | Меряете CPU, БД, пул соединений, поведение под RPS **без** искусственного потолка 429 с одного IP. |
| **Production-like** | Как в проде (`true`) | Проверяете, что лимиты и UX (429) соответствуют ожиданиям; это **не** замена capacity-теста. |

Для вопроса «не будет ли лагать» опирайтесь на **capacity** на стенде, максимально похожем на прод.

### 2. Где гонять

- **Локально** — быстрые итерации и регрессии логики; задержки и лимиты (туннель, один процесс) **не** переносятся 1:1 в Railway.
- **Staging на Railway** (тот же тип сервиса БД, тот же регион при возможности, похожий объём данных) — **основной** источник цифр перед релизом.
- **Прод** — только лёгкие smoke / синтетика с мизерным RPS; полноценный load test на проде не рекомендуется.

### 3. Какие виды прогонов

1. **Smoke** — мало запросов, проверка что всё 200 и разумная базовая latency.
2. **Load** — ступенчато растущий RPS до **ожидаемого пика** (например «вечерний каталог»: N запросов/с на публичные эндпоинты).
3. **Stress** — за предел ожидаемого пика, чтобы увидеть **деградацию** (рост latency, очереди, 503), а не только «всё упало».
4. **Soak (выдержка)** — **средний** RPS длительно (30–120+ мин), чтобы поймать утечки, рост latency из‑за GC/пула БД/кэшей.

### 4. Что фиксировать (минимум)

- **Latency:** p95 и p99 для ключевых маршрутов (`/api/public/trainers`, карточка тренера), не только среднее.
- **Ошибки:** доля 5xx и таймаутов; цель — около **0%** под целевой нагрузкой.
- **Сатурация:** CPU приложения и БД, **пул соединений** к PostgreSQL (исчерпание = типичный «лаг»).
- **Контекст:** одновременные пользователи в сценарии — **примерно** как в продукте (доля списка vs карточки vs фото).

### 5. SLO «не лагает» (пример — подставьте свои числа)

Заранее договоритесь о порогах, например:

- p95 latency публичного каталога **ниже X ms** при Y RPS на staging;
- доля ошибок **&lt; 0.1%** в течение Z минут load-теста.

Если прогон не проходит — сначала смотрите **профиль БД** (N+1 в списке тренеров, индексы), затем **размер пула** и воркеры, затем **фото** (presigned/CDN вместо proxy).

### 6. Честные ограничения

- Один генератор нагрузки с одного IP **не** моделирует тысячи клиентов; для распределённой нагрузки — несколько машин / k6 cloud / агенты в разных сетях.
- WebApp с **валидным** `initData` — отдельный сценарий (подпись, срок жизни); без него вы меряете в основном валидацию и 401.

## Куда имеет смысл давать нагрузку (тонкие места)

| Область | Почему важно | Что смотреть |
|--------|----------------|--------------|
| **`GET /api/public/trainers`** | Для каждого тренера в списке вызывается `get_trainer_booking_availability` — классический **N+1 к БД** + тяжёлый JSON. Главный кандидат на узкое горлышко при росте каталога. | p95/p99 latency, рост CPU/DB connections, ошибки пула БД. |
| **`GET /api/public/trainers/{id}`** | Один тренер + education + availability — меньше запросов, чем список, но типичный сценарий открытия карточки. | То же. |
| **`GET /api/public/photos/...`** | Прокси: байты идут **через приложение** (и при необходимости из S3). Удваивает трафик и нагружает воркеры Uvicorn. | Throughput, memory, если без presigned/CDN. |
| **`GET /health`** | `SELECT 1` + опционально `head_bucket` S3. Базовая линия «жив ли стек». | Должен оставаться дешёвым; если тут плохо — сначала БД/сеть. |
| **`GET /api/public/cities`, `/services`, `/arenas`** | Лёгкие справочники — контрольный сценарий «не каталог». | Сравнить с `/trainers`. |
| **WebApp `/api/webapp/...`** | Много эндпоинтов, проверка `initData` (HMAC) на запрос; без **валидного** `X-Telegram-Init-Data` смысловая нагрузка только на 401/422. Для полноценного теста нужны подписанные данные (отдельный стенд/скрипт). | После появления тестовых токенов — отдельный профиль. |
| **Rate limit (Epic D)** | С одного IP лимиты: public **120/мин**, webapp **800/мин** и т.д. Массовые 429 при нагрузочном тесте с одной машины — **ожидаемо**. Для стресс-теста локально: `API_RATE_LIMIT_ENABLED=false`. | Доля 429 vs 200. |

## Быстрый запуск (Python)

Из корня репозитория (нужен запущенный API, например `uvicorn src.api.app:app --port 8000`):

```bash
# Локально без rate limit (в .env или экспортом):
# export API_RATE_LIMIT_ENABLED=false

python scripts/loadtest/run_public_load.py --base http://127.0.0.1:8000 --duration 45 --concurrency 30
```

Опции: `--endpoint trainers|cities|health|mixed`, `--photo-key` (если хотите добить `/api/public/photos/...`).

## k6 (опционально)

Если установлен [k6](https://k6.io/):

```bash
API_RATE_LIMIT_ENABLED=false k6 run scripts/loadtest/k6/public_catalog.js
```

Переменная `BASE_URL` по умолчанию `http://127.0.0.1:8000`.

## Интерпретация

- Рост latency **только** на `/api/public/trainers` при нормальном `/health` → оптимизировать запросы к БД (батч availability, кэш, см. `docs/PERFORMANCE_PLAN_CATALOG.md`).
- Высокая нагрузка на CPU при `/photos` при низком RPS → уход с proxy на presigned/CDN.
- Много **429** → включён rate limit; для измерения «чистой» пропускной способности отключите лимит на стенде или распределите IP (несколько агентов).
